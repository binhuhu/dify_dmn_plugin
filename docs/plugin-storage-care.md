# 插件存储的照看：报错、用量、清理

存着的表都在平台给插件的持久存储里。这块存储有三个先天限制，决定了下面的做法：

- **列不出键**：插件只能按键名读、写、删、问在不在，不能列出自己存了什么。
- **问不出用量**：平台按插件清单里申请的配额限制总量（0.5.33 起 1 GiB，之前 16 MiB），插件既读不到上限，也读不到已用多少。
- **没有事务**：一次存表要写几份，中途任何一份都可能被拒；被拒的那一份也可能其实已经写进去了。

每存一版，表内容写三份：按存表号一份、按版本号一份、头版一份（头版每次覆盖，前两份一直留着）。有时还有闸报告、发布记录、谁存的记录各一份。所以表越大、存得越勤，占得越多；旧版次不会自己消失。

## 一、存储报错分两种（0.5.34）

| 情况 | 状态码 | 错误码 | 回包里多出的 `storage_failure` |
|---|---|---|---|
| 平台因为空间不够拒了一次写入 | 507 | `STORED_TABLE_STORAGE_FULL` | `{"call": "set", "kind": "FULL", …}` |
| 其他存储故障 | 503 | `ROUTE_TABLE_UNAVAILABLE`（文案照旧；存表留了半截或结果不明时换成说该做什么，见第二节） | `{"call": "exist/get/set/delete", "kind": "OTHER", …}` |

- `call` 是失败的那一次存储调用。读正常、只有 `set` 失败，多半是空间；`exist` / `get` 也失败，是存储服务本身。
- 平台的原始报错**只写进插件日志**（`dmn_client.storage_care`，级别 WARNING），不进回包：编辑端点没有登录保护，回包不带平台内部信息。
- 「空间不够」按平台报错里的字样认，只认明确说存储的几种：`max storage size`（开源 Dify 插件守护进程的说法）、`storage quota`、`storage limit`、`insufficient storage`、`no space left`。只说 `quota` 的（比如限流「request quota exceeded」）不算，按其他故障回 503。平台换了说法就认不出，会落到「其他」——这时看日志里的原话。
- 签名模式也一样：签名写入的第一笔是签名使用记录，它因为空间不够被拒时同样回 507，并带 `retry_requires_new_signature: true`。

## 二、存到一半被拒，回包说清楚留下了什么

五张交付链表以外的表（方案层的表等），存表失败时 `storage_failure` 多三项：`version`（这次要存的版本号）、`save_id`（这次的存表号）和 `outcome`。空间满（507）和其他故障（503）都带；503 时文案也按 `outcome` 说该做什么（`NOT_SAVED` 仍以原来的「稍后再试」开头，后面补一句超时写入可能晚到）：

| `outcome` | 什么时候 | 插件做了什么 | 你要做的 |
|---|---|---|---|
| `NOT_SAVED` | 头版之前的某一份写失败 | 把这次已写进去的几份全删掉了 | 腾出空间后照原版本号重存。不是空间满（503，比如超时）时，写入可能在插件放弃之后才落盘（上游守护进程默认最长 10 分钟，AgentHub 待平台确认）：过 10 分钟先读回这张表，再重存。若报「第 n 版刚被别人存了」，说明其实留了半截：照原内容重存不会成功，请负责人按第四节核实后处理 |
| `HALF_WRITTEN` | 同上，但收回时有一份删不掉或确认不了 | 能删的删了：先删按存表号那份和闸报告，最后删版本号那份。版本号那份在，剩下的就能从它找到；版本号那份当初就没写进去时，删不掉的按存表号副本找不到（见已知限制） | 不要反复重存。`usage` 看 `half_written`，请负责人按第四节核实后处理 |
| `UNKNOWN` | 头版那一份写失败 | **什么都不删** | 先不重存、不收拾。读回这张表：头版的存表号和回包里的 `save_id` 一样，就是这次存上了（只比版本号不够：同一时刻别人也可能存了这一版）。**读回仍是上一版，并不能证明没写进去**：宿主可能还在给旧头版，给多久插件不知道。这时重存一定被拒（「第 n 版刚被别人存了」，这一版的版本号那份就是这次写的），不要改了内容再试。等读回的头版变了再定；过了宿主读缓存的时长仍是上一版，请负责人按第四节核实后处理。核实、收拾之后再存，照原内容存：内容摘要不变，按摘要钉着它的表不会断 |

头版写失败时不删，是因为平台可能已经写进去、只是在后面的记账步骤报错，而且一段时间里读到的还是旧头版缓存。这时删掉版本号那份，会留下「头版是第 n 版、历史里却没有第 n 版」。宁可留一个半截版次等人收拾。

**同样的道理也管着人工收拾**：清理计划里的「头版」也是读出来的。所以 0.5.35 起清理对半截版次默认不删，只有负责人逐版写明核过的那几版才删，而且只删版本号那一份（见第四节）。

万一删错了：被删的只是版本号那一份，这一版的整份内容还在按存表号那份里（计划里 `has_copy: true` 时），用 `op=saved` 能读回（见第四节末）。另外有两道兜底，只管五张交付链表以外的表，而且**都要等宿主不再给旧头版之后才有用**：按这一版的版本号读，读到的是头版本身（整份内容）；下一次存表若读到的是真头版，插件发现头版没有版本号那一份，会先用头版把它补回来，再写新的一版。宿主还在给旧头版时就再存，新的一版会占用这个版本号、盖掉真头版，真头版只剩按存表号那份。所以删错之后，确认读回的已是真头版之前不要再存这张表；非存不可就照原内容存。

交付链五张表不做这个回收：它们的首存检查要读「停在半路的存表留下了什么」，保持原样，回包里也没有 `outcome`。

## 三、看一张表占了什么：`op=usage`

只读，任何应用都可调。`table` 写表名。

```json
{"table": "solution.fact.feature.M_P_02_04_01", "head_version": 5, "head_bytes": 81234,
 "versions": [{"version": 1, "save_id": "…", "saved_at": "…", "bytes": 162760, "keys": 3}, …],
 "half_written": [], "keys": 16, "bytes": 894212, "prunable": true, "half_written_prunable": true}
```

- `versions[].bytes`：这一版占的字节：按版本号那份、按存表号那份（按同样大小计，不重读），加上闸报告、发布记录、谁存的记录（实际读出大小）。
- `half_written`：头版之上、没有头版指着的版次：可能是存到一半留下的，也可能是真头版而读到的头版是旧值。只看头版之上 3 个版本号。每一版带 `parent_save_id`（它存表时的头版存表号）、`child_of_head`（它的父版是不是这次读到的头版）、`answered_ok`（插件记过它的存表回了成功：有谁存的记录）、`has_copy`（按存表号那份在不在）、`removable` 和不能删时的 `why_kept`（见第四节）。
- `bytes` / `keys`：这个表名下现在实占多少，加上五张表的草稿和首存记录。**不含**：撤销、删草稿、清理留下的操作记录（键名带随机号，找不到）；签名使用记录（不在表名下）；当初存到一半、连版本号那份都没写进去的零散副本（同样找不到）；收拾掉的头版之上版次留下的按存表号那份、闸报告、谁存的记录（版本号那份没了，插件找不到它们）。
- 这不是平台记的用量：如果平台按累计写入计数（覆盖不减，只有删键才减），平台记的只会比这个多。
- 头版在、但读不出版本号时，回 `ROUTE_TABLE_CORRUPT`，不给用量也不让清理：否则会把真版次当成半截版次。
- 插件列不出键，所以只能一张表一张表地问；表名要自己知道。

## 四、清理旧版次：`op=prune`

两种表例外：

- **交付链五张表**（旧名、标准名都一样）：拒清理（`STORED_TABLE_PRUNE_NOT_SUPPORTED`）。历史是放行依据，首存撤销也要沿着历史走。
- **能力表**（头版是能力表格式的表）：**头版以下的旧版次不删**，只收拾头版之上的半截版次。查询 → 事实表按内容摘要钉着它的某一版（存表时读一次，执行节点以后也可能照着读），插件列不出所有表，找不全哪些版次正被引用。头版之上的版次，按内容摘要找版只从读到的头版往下找、按版本号读也不越过读到的头版，所以**只要读到的头版是真头版、且没有几次存表交错**，就没有表能钉住它们。这两条插件都确认不了：读到的可能是旧头版，那「头版之上」的那一版正是真头版，可能已经被钉住；交错的存表也可能把头版拨回、把回过成功的版次留在上面。所以收拾它们和普通表一样，按下面「收拾存到一半的版次」的规则：默认不删，负责人核过才删，只删版本号那一份。不收拾的话，能力表存到一半以后就再也存不进去。计划里写 `old_versions_kept` 说明这一点。`usage` 的 `prunable` 指旧版次能不能清，`half_written_prunable` 指半截版次能不能收拾。
- 是不是能力表看头版的格式，不看表名：别的格式的表存在这个名字下，照普通表清理。

分两步，第一步只出计划，第二步带着计划摘要才删：

```json
// 第一步：出计划，什么都不删。任何应用可调
{"expected_version": 5, "keep": 2}
// 返回：{"applied": false, "versions": [第 1–3 版…], "keys": 9, "bytes": 487404, "plan_sha256": "…"}

// 第二步：照这个计划删。只有「路由表维护」应用可调；签名模式下要带写手签名
{"expected_version": 5, "keep": 2, "plan_sha256": "…"}
// 返回：{"applied": true, …, "operation_record": {…}}
```

- `keep`：留下最新的几版，1 到 100000 的整数。1 = 只留头版；写成头版版本号 = 旧版次一版都不动，只收拾半截版次。
- `expected_version`：你看到的头版版本号。对不上（中间有人存过）就拒，重新出计划。
- 第二步会重新算一遍计划，和 `plan_sha256` 不一致就拒（`STORED_TABLE_PRUNE_PLAN_CHANGED`），不会删你没看过的东西。
- **旧版次也要存满 1 小时才删**：头版是第 n 版时，若还有实例在给更早的头版（比如第 n−2 版），删掉第 n−1 版会让那个实例的存表通过「版本号已被占」的检查、盖掉头版。还不够 1 小时的列在 `kept_young`；读不出存表时间的也不删。
- 每一版先删它的附属几份，最后删按版本号那份。中途断了，重新出计划再跑一次就接上。别的清理同时删掉了某个键，不算失败。
- 每一版删之前核一次、删版本号那份之前再核一次：还是计划里的那次存表（存表号一样），而且头版之上的版次删之前，头版仍是计划判断时读到的那一个（版本号和存表号都一样：撤销的重试会直接拿这个版本号那份补写头版；同一版本号换成别的存表，这一版的父版就不是头版了）。核不上就不删这一版，回包的 `skipped` 列出跳过的版本号键。计划摘要也算上每一版的存表时间：同样的键带着新的存表时间回来，是另一份计划。
- 签名模式下清理只核写手签名，**不写签名使用记录**：空间满时那份记录写不进去，会把腾空间的清理本身挡住。同一个请求再发，计划已经变了，回 `STORED_TABLE_PRUNE_PLAN_CHANGED`，不会多删。计划里一个键都不删时，什么都不变，也不留操作记录。
- 旧版次删了就没有了，不能恢复。半截版次只删版本号那一份，见下。

**清理前必须自己核的一件事**：有没有流程把这张表钉在要删的某一版上（按版本号钉，或按内容摘要钉）。插件不知道谁钉了哪一版；钉着的版次被删后，那个流程会报「钉的版本不在」，不会回退到最新版。

### 收拾存到一半的版次

请求里加 `"half_written": true`，计划会列出头版之上的版次。插件多数时候分不清「存到一半的」和「已经写进去的真头版、而读到的头版是旧值」，所以一版能不能删按下面几条判断（自上而下，碰到第一条就定），计划里每一版写 `removable`，不能删的写 `why_kept`：

| 这一版 | 删不删 |
|---|---|
| 父版（`parent_save_id`）不是这次读到的头版 | **一律不删**，写明了也不删：头版可能被拨回过（几次存表交错，或写入晚到），这一版可能回过成功。表因此存不进时，见已知限制 |
| 插件记过它的存表回了成功（`answered_ok: true`：有谁存的记录，只在回成功时写） | **一律不删**：它当过头版，读到的头版多半是旧值 |
| 头版之上另有一版以它为父版 | **一律不删**：有存表把它当头版读过，它落了盘，读到的头版是旧值。等读回的头版变了再看 |
| 存了不满 1 小时 | 不删：可能是正在存的那一版，或宿主还在给旧值。读不出存表时间的同样不删 |
| 没有 32 位存表号 | 不删：没法在 `confirm` 里写明 |
| 其余（父版正是这次读到的头版，`child_of_head: true`） | 默认不删。负责人核过、确认它不是真头版后，在 `confirm` 里逐版写明 `{version, save_id}` 才删 |

```json
// 第一步：看有哪些、为什么不删
{"expected_version": 0, "keep": 1, "half_written": true}
// 第二步：负责人核过后写明要删的那几版，再出一次计划（confirm 算进计划摘要）
{"expected_version": 0, "keep": 1, "half_written": true,
 "confirm": [{"version": 1, "save_id": "（32 位存表号，照计划里的抄）"}]}
// 第三步：带第二步的 plan_sha256 执行，confirm 照第二步原样带上
```

- 一张表第一次存就断在半路时，头版不存在，`expected_version` 写 0。写 `confirm` 之前，先读回确认它仍然没有头版。
- 「核过」指：这一版的存表号不是任何一次回过成功的存表的存表号；它的存表时间对得上那次失败的存表；读回的头版已经不可能是旧值（宿主读缓存多久要平台确认，见已知限制）。核不了就别删：留着半截版次的代价是这张表存不进，删错的代价是盖掉真头版。
- 删的只是**版本号那一份**（挡住下一次存表的就是它）。按存表号那份、闸报告、谁存的记录都留着，所以删错了也能读回——前提是 `has_copy: true`；存表失败时收回过的（`HALF_WRITTEN`）可能已经没有按存表号那份，删了就没有了。
- 腾空间时要知道：收拾一版只腾出版本号那一份，留着的那几份插件以后找不到、也删不掉（见已知限制）。
- 时间按版次里记的存表时间和本次调用的时钟比；两台机器时钟差得多时这个判断不准。

### 按存表号读回一版：`op=saved`

只读，任何应用都可调。`{"save_id": "（32 位存表号）"}`，回 `{"table", "save_id", "doc"}`：`doc` 是这次存表的整份内容（按存表号那份），没有就是 `null`。存表号在清理计划、`usage` 的 `half_written`、存表失败回包的 `storage_failure` 里。用来找回删错的半截版次：读出来，照原内容再存一次（先确认读回的已是真头版）。

## 五、空间满了怎么办

1. 先停：别反复重试存表。
2. 对占得多的表逐张 `usage`，看哪些旧版次可以不要。头版之上的版次收拾掉只腾出版本号那一份，腾空间主要靠旧版次。
3. 核对要删的版次没有被流程钉住，`prune` 出计划、确认、执行。
4. 回包里 `outcome` 是 `HALF_WRITTEN` 或 `UNKNOWN` 的那张表，按第二节、第四节的规则处理；`UNKNOWN` 的那一版可能就是真头版，核不了就不收拾。
5. 删够之后重存。
6. 如果五张表以外已经没什么可删，只能请平台放宽这个插件的存储上限。

签名模式下，清理不写签名使用记录，空间满时照样能清。但交付链五张表的草稿删除、发布、撤销仍要先写签名使用记录（几百字节）：空间满到连它都写不下时，这些操作做不了，回 507。这时保留 SIGNED 签名校验，经批准用 `op=prune` 清理允许删除的旧版次，或请平台放宽存储上限；不要通过关闭签名校验绕过配额故障。腾出空间后先核对上次操作是否已经生效，再按回包要求使用新签名重试。如果宿主是「先写进去、再按配额报错」，每次带签名重试都会再多一份记录，别反复重试。

## 已知限制

- 插件问不到平台还剩多少空间，只能在写入被拒时知道满了。平台按什么记用量（累计还是实占、覆盖减不减）没有核实。
- 列不出键，`usage` 和 `prune` 都要给表名；没有「所有表合计」。
- 找不到的零散副本：没有版本号那份指着的按存表号副本和闸报告（0.5.33 及更早存到一半时留下的；本版版本号那份没写进去、收回时又删不掉的；本版清理收拾掉的头版之上版次故意留下的按存表号那份、闸报告和谁存的记录），以及操作记录，都没有办法找到和删除，也不算进 `usage`。按存表号那份能用 `op=saved` 读（要知道存表号）。
- 交付链五张表的旧版次不能清理；它们存到一半留下的版次也没有收拾的操作，之后存表会一直报「第 n 版刚被别人存了」。
- 能力表的旧版次不能清理，只会越存越多；按内容摘要找版只回看最近 50 版，钉在更早版次上的查询 → 事实表本来就存不进去。
- 每版写三份的做法没有改。
- 清理每次从第 1 版扫到要删的最后一版，历史很长的表一次出计划要几千次存储调用。
- 两个进程同时存同一版本号时，回收可能删掉另一个进程刚写的版本号那份（原来就有的竞争：插件没有跨进程的锁）。
- 清理和别的写入交错时，存储没有「核对后再删」的原子操作，核对和删除之间仍有一次往返的空档；为护住版本号那份，旧版次的附属几份可能先被删掉，这时这一版只剩版本号那份和头版（按存表号那份只有 `op=saved` 读，不影响读和存）。
- 「存满 1 小时」按开源插件守护进程 0.5.1 的行为定：读缓存在多个副本间共享，留 5 分钟，命中不续期；写入可能在插件的调用超时（插件端默认 250 秒、守护进程默认 600 秒）之后才落盘。1 小时是两者的六倍以上。AgentHub 是否和上游一样，待平台确认；更长的缓存下，靠的是「父版正是读到的头版就默认不删」这一条。
- 存储没有带条件的写。几次存表在几秒内交错时，头版可能被拨回，一个回过成功的版次留在头版之上；它的父版不是读到的头版，插件不清理它，但这张表此后存不进（报「第 n 版刚被别人存了」），**本版插件里没有解开的操作**：只能由平台在存储里核实真头版后处理（删掉那一版的版本号那份，它的内容仍在按存表号那份里），且处理后若有流程按版本号钉着那一版，会读到之后存进同一版本号的内容。也可能出现两次存表都写了同一个版本号、头版是一次而版本号那份是另一次的情况，那次被答「没有生效」的存表其实成了头版。维护时一张表只由一个人、一处串行地存。
- 不是空间满的存表失败（503，比如超时）回 `NOT_SAVED` 时，插件收回的是它当时看得到的几份；超时的那一笔写入可能之后才落盘。立刻照原版本号重存、而晚到的写入随后落在同一个版本号上时，这一版的版本号那份会换成没存成的那次内容。所以回包让你过 10 分钟先读回再重存。0.5.34 起就是这样。
- 签名模式下，一次存表写到头版那一步时若签名使用记录核对失败，头版其实没写，但插件按「头版写过」处理：不回收，回包是签名记录不明（503 `STORED_TABLE_REPLAY_UNAVAILABLE`），不带 `outcome`。留下的版本号那份按半截版次收拾。0.5.32 起就是这样。
- 撤销首存时，会把引用这张表的五张表以外的路由表重存一版（引用改回旧名）。这一存失败时**不回收**：它的存表号由这次撤销推出，同一撤销的几次重试共用，回收会删掉另一次重试已存上的版本。回包是撤销的，不带 `outcome`；重发撤销就接着做。
- 空间满原来回 503（签名模式下是签名记录不明的 503），现在回 507。只认 503 才重试的调用方要认 507；仓内没有依赖旧码的调用方。
