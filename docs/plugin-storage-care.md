# 插件存储的照看：报错、用量、清理

存着的表都在平台给插件的持久存储里。这块存储有三个先天限制，决定了下面的做法：

- **列不出键**：插件只能按键名读、写、删、问在不在，不能列出自己存了什么。
- **问不出用量**：平台按插件清单里申请的配额限制总量（0.5.33 起 1 GiB，之前 16 MiB），插件既读不到上限，也读不到已用多少。
- **没有事务**：一次存表要写几份，中途任何一份都可能被拒；被拒的那一份也可能其实已经写进去了。

每存一版，表内容写三份：按存表号一份、按版本号一份、头版一份（头版每次覆盖，前两份一直留着）。有时还有闸报告、发布记录、谁存的记录各一份。所以表越大、存得越勤，占得越多；旧版次不会自己消失。

## 一、存储报错分两种（0.5.34）

| 情况 | 状态码 | 错误码 | 回包里多出的 `storage_failure` |
|---|---|---|---|
| 平台因为空间不够拒了一次写入 | 507 | `STORED_TABLE_STORAGE_FULL` | `{"call": "set", "kind": "FULL", …}` |
| 其他存储故障 | 503 | `ROUTE_TABLE_UNAVAILABLE`（文案照旧；存表留了半截或结果不明时换成说该做什么，见第二节） | `{"call": "exist/get/set/delete", "kind": "OTHER", …}` |

- `call` 是失败的那一次存储调用。读正常、只有 `set` 失败，多半是空间；`exist` / `get` 也失败，是存储服务本身。
- 平台的原始报错**只写进插件日志**（`dmn_client.storage_care`，级别 WARNING），不进回包：编辑端点没有登录保护，回包不带平台内部信息。
- 「空间不够」按平台报错里的字样认，只认明确说存储的几种：`max storage size`（开源 Dify 插件守护进程的说法）、`storage quota`、`storage limit`、`insufficient storage`、`no space left`。只说 `quota` 的（比如限流「request quota exceeded」）不算，按其他故障回 503。平台换了说法就认不出，会落到「其他」——这时看日志里的原话。
- 签名模式也一样：签名写入的第一笔是签名使用记录，它因为空间不够被拒时同样回 507，并带 `retry_requires_new_signature: true`。

## 二、存到一半被拒，回包说清楚留下了什么

五张交付链表以外的表（方案层的表等），存表失败时 `storage_failure` 多三项：`version`（这次要存的版本号）、`save_id`（这次的存表号）和 `outcome`。空间满（507）和其他故障（503）都带；503 时文案也按 `outcome` 说该做什么，只有 `NOT_SAVED` 仍是原来的「稍后再试」：

| `outcome` | 什么时候 | 插件做了什么 | 你要做的 |
|---|---|---|---|
| `NOT_SAVED` | 头版之前的某一份写失败 | 把这次已写进去的几份全删掉了 | 腾出空间后照原版本号重存。若报「第 n 版刚被别人存了」，说明宿主当时答错了「在不在」、其实留了半截，按下一行收拾 |
| `HALF_WRITTEN` | 同上，但收回时有一份删不掉或确认不了 | 能删的删了：先删按存表号那份和闸报告，最后删版本号那份。版本号那份在，剩下的就能从它找到；版本号那份当初就没写进去时，删不掉的按存表号副本找不到（见已知限制） | 存满 10 分钟后 `usage` 看有没有半截版次，有就用清理操作收拾（见第四节），再重存 |
| `UNKNOWN` | 头版那一份写失败 | **什么都不删** | 先不重存、不收拾。等宿主的读缓存过期后再读回这张表：头版的存表号和回包里的 `save_id` 一样，就是这次存上了（只比版本号不够：同一时刻别人也可能存了这一版）；仍是上一版才是写到一半，那时按上一行收拾 |

头版写失败时不删，是因为平台可能已经写进去、只是在后面的记账步骤报错，而且一段时间里读到的还是旧头版缓存。这时删掉版本号那份，会留下「头版是第 n 版、历史里却没有第 n 版」。宁可留一个半截版次等人收拾。

**同样的道理也管着人工收拾**：清理计划里的「头版」也是读出来的，「存满 10 分钟」只防正在存的那一版，不管缓存。宿主缓存还没过期就收拾 `UNKNOWN` 留下的版次，可能删掉的正是新头版那一版。不知道宿主缓存多久时，先请平台核实，不要动。

交付链五张表不做这个回收：它们的首存检查要读「停在半路的存表留下了什么」，保持原样，回包里也没有 `outcome`。

## 三、看一张表占了什么：`op=usage`

只读，任何应用都可调。`table` 写表名。

```json
{"table": "solution.fact.feature.M_P_02_04_01", "head_version": 5, "head_bytes": 81234,
 "versions": [{"version": 1, "save_id": "…", "saved_at": "…", "bytes": 162760, "keys": 3}, …],
 "half_written": [], "keys": 16, "bytes": 894212, "prunable": true}
```

- `versions[].bytes`：这一版占的字节：按版本号那份、按存表号那份（按同样大小计，不重读），加上闸报告、发布记录、谁存的记录（实际读出大小）。
- `half_written`：头版之上、没有头版指着的版次，就是存到一半留下的。只看头版之上 3 个版本号。
- `bytes` / `keys`：这个表名下现在实占多少，加上五张表的草稿和首存记录。**不含**：撤销、删草稿、清理留下的操作记录（键名带随机号，找不到）；签名使用记录（不在表名下）；当初存到一半、连版本号那份都没写进去的零散副本（同样找不到）。
- 这不是平台记的用量：如果平台按累计写入计数（覆盖不减，只有删键才减），平台记的只会比这个多。
- 头版在、但读不出版本号时，回 `ROUTE_TABLE_CORRUPT`，不给用量也不让清理：否则会把真版次当成半截版次。
- 插件列不出键，所以只能一张表一张表地问；表名要自己知道。

## 四、清理旧版次：`op=prune`

只用于交付链五张表和能力表以外的表，这几张拒清理（`STORED_TABLE_PRUNE_NOT_SUPPORTED`）：

- 五张表（旧名、标准名都一样）：历史是放行依据，首存撤销也要沿着历史走。
- 能力表 `platform.capability.catalog`：查询 → 事实表按内容摘要钉着它的某一版（存表时读一次，执行节点以后也可能照着读）。插件列不出所有表，找不全哪些版次正被引用，删掉被钉的那一版，引用它的表就存不进去。

分两步，第一步只出计划，第二步带着计划摘要才删：

```json
// 第一步：出计划，什么都不删。任何应用可调
{"expected_version": 5, "keep": 2}
// 返回：{"applied": false, "versions": [第 1–3 版…], "keys": 9, "bytes": 487404, "plan_sha256": "…"}

// 第二步：照这个计划删。只有「路由表维护」应用可调；签名模式下要带写手签名
{"expected_version": 5, "keep": 2, "plan_sha256": "…"}
// 返回：{"applied": true, …, "operation_record": {…}}
```

- `keep`：留下最新的几版，1 到 1000 的整数。1 = 只留头版。
- `expected_version`：你看到的头版版本号。对不上（中间有人存过）就拒，重新出计划。
- 第二步会重新算一遍计划，和 `plan_sha256` 不一致就拒（`STORED_TABLE_PRUNE_PLAN_CHANGED`），不会删你没看过的东西。
- 每一版先删它的附属几份，最后删按版本号那份。中途断了，重新出计划再跑一次就接上。别的清理同时删掉了某个键，不算失败。
- 每一版删之前核一次、删版本号那份之前再核一次：还是计划里的那次存表（存表号一样），而且半截版次没有在这期间成了头版（撤销的重试会直接拿这个版本号那份补写头版）。核不上就不删这一版，回包的 `skipped` 列出跳过的版本号键。计划摘要也算上每一版的存表时间：同样的键带着新的存表时间回来，是另一份计划。
- 签名模式下清理只核写手签名，**不写签名使用记录**：空间满时那份记录写不进去，会把腾空间的清理本身挡住。同一个请求再发，计划已经变了，回 `STORED_TABLE_PRUNE_PLAN_CHANGED`，不会多删。计划里一个键都不删时，什么都不变，也不留操作记录。
- 删了就没有了，不能恢复。

**清理前必须自己核的一件事**：有没有流程把这张表钉在要删的某一版上（按版本号钉，或按内容摘要钉）。插件不知道谁钉了哪一版；钉着的版次被删后，那个流程会报「钉的版本不在」，不会回退到最新版。

### 收拾存到一半的版次

请求里加 `"half_written": true`，计划会把头版之上的半截版次一并列入：

```json
{"expected_version": 0, "keep": 1, "half_written": true}
```

- 一张表第一次存就断在半路时，头版不存在，`expected_version` 写 0。
- 只收存了超过 10 分钟的；更新的可能是别人正在存的那一版，计划里标 `removable: false`，不动它。时间按半截版次里记的存表时间和本次调用的时钟比；两台机器时钟差得多时这个判断不准。
- 读不出存表时间的不动。

## 五、空间满了怎么办

1. 先停：别反复重试存表。
2. 对占得多的表逐张 `usage`，看哪些旧版次可以不要。
3. 核对要删的版次没有被流程钉住，`prune` 出计划、确认、执行。
4. 回包里 `outcome` 是 `HALF_WRITTEN` 或 `UNKNOWN` 的那张表，按第二节收拾。
5. 删够之后重存。
6. 如果五张表以外已经没什么可删，只能请平台放宽这个插件的存储上限。

签名模式下，清理不写签名使用记录，空间满时照样能清。但交付链五张表的草稿删除、发布、撤销仍要先写签名使用记录（几百字节）：空间满到连它都写不下时，这些操作做不了，回 507。这时保留 SIGNED 签名校验，经批准用 `op=prune` 清理允许删除的旧版次，或请平台放宽存储上限；不要通过关闭签名校验绕过配额故障。腾出空间后先核对上次操作是否已经生效，再按回包要求使用新签名重试。如果宿主是「先写进去、再按配额报错」，每次带签名重试都会再多一份记录，别反复重试。

## 已知限制

- 插件问不到平台还剩多少空间，只能在写入被拒时知道满了。平台按什么记用量（累计还是实占、覆盖减不减）没有核实。
- 列不出键，`usage` 和 `prune` 都要给表名；没有「所有表合计」。
- 找不到的零散副本：没有版本号那份指着的按存表号副本和闸报告（0.5.33 及更早存到一半时留下的；本版版本号那份没写进去、收回时又删不掉的），以及操作记录，都没有办法找到和删除。
- 交付链五张表的旧版次不能清理；它们存到一半留下的版次也没有收拾的操作，之后存表会一直报「第 n 版刚被别人存了」。
- 每版写三份的做法没有改。
- 清理每次从第 1 版扫到要删的最后一版，历史很长的表一次出计划要几千次存储调用。
- 两个进程同时存同一版本号时，回收可能删掉另一个进程刚写的版本号那份（原来就有的竞争：插件没有跨进程的锁）。
- 清理和别的写入交错时，存储没有「核对后再删」的原子操作，核对和删除之间仍有一次往返的空档；为护住版本号那份，附属几份可能先被删掉，这时这一版只剩版本号那份和头版（按存表号那份在五张表以外的表上没有读者，不影响读和存）。
- 签名模式下，一次存表写到头版那一步时若签名使用记录核对失败，头版其实没写，但插件按「头版写过」处理：不回收，回包是签名记录不明（503 `STORED_TABLE_REPLAY_UNAVAILABLE`），不带 `outcome`。留下的版本号那份按半截版次收拾。0.5.32 起就是这样。
- 撤销首存时，会把引用这张表的五张表以外的路由表重存一版（引用改回旧名）。这一存失败时**不回收**：它的存表号由这次撤销推出，同一撤销的几次重试共用，回收会删掉另一次重试已存上的版本。回包是撤销的，不带 `outcome`；重发撤销就接着做。
- 空间满原来回 503（签名模式下是签名记录不明的 503），现在回 507。只认 503 才重试的调用方要认 507；仓内没有依赖旧码的调用方。
