## 一、问题：表现在只有「存」，没有「退场」

| 事实 | 出处 |
|---|---|
| 路由表清单（存储键 `route-table-index`）只增不减。路由表第一次存就记进去；只有撤首存（五张表及六个最终名，`index_added` 的）时才拿出来 | `route_table.py` `_index`、`_save`、`_first_store`、`undo` |
| `route_tables()` 返回清单里的每个名字，外加默认路由表，不看还有没有人用。它有三处使用方：①方案状态一致核 `_one_state`（`ROUTE_TABLE_SOLUTION_STATUS_CONFLICT`）；②资源决策表编译核（`RESOURCE_TABLE_ROUTE_COMPILED`）；③旧名引用提醒 `old_name_references`（I15） | `route_table.py` `route_tables` 及三处调用 |
| 另有几处直接读清单键：④撤首存改引用 `_references_to`（I24）；首存、撤销、盘点时的清单维护 | `route_table.py` `_references_to`、`_first_store`、`undo`、`_inventory` |
| 场景整包的 `bundle_check`、`publish` 经 ① 走 | `scene_bundle.py` |
| `op=undo` 只撤首存，首存只有五张表和六个最终名有；新名表回 `ROUTE_TABLE_INVALID` | `route_table.py` `undo` |
| `prune` 最少留头版；交付链表连 prune 都拒 | `storage_care.py` `prune` |
| 运行时读表不看任何状态：`invoke_solution`、`evaluate_stored_table`、决策求值的 `model_loader`，都经 `StorageTables.load` / `version` / `find_content` 读头版、指定版或指定内容 | `solution_invoke.py`、`tools/evaluate_stored_table.py`、`decision_executor.py` |
| 0.5.6 定 `ROUTE_TABLE_SOLUTION_STATUS_CONFLICT`，是为了不让「选哪张表」决定一个被闸挡着的方案跑不跑 | `docs/releases/v0.5.6.md` |

所以一张试验路由表试验完以后，只有两条路：
- 留着，照样参加核：以后会拦正常改动。定 366 实证：把试验表里也有的方案改状态，就拒 `STATUS_CONFLICT`，并点名试验表。
- 存一版清空版：等于在交付链上留一份没人维护的配置。

两条都不是标准该给的答案。

同一类的现网表有两组：
- 试验副本那五张：`trial.triage.dispatch.route`，以及它的资源表、实体表、补充表、受理表；
- 费用组测试应用乙用的旧试验路由表（`trial.route`，第 5 版，登记两个方案应用）。

本设计按类覆盖这两组，不点名。

## 二、做法总述

1. **生命周期记录**：每张表可以有一份，状态四种——`ACTIVE`、`DEACTIVATING`、`DEACTIVATED`、`REACTIVATING`。没有记录就是在用，读回与今天逐字节相同。
2. **组意图记录**：一次停用或恢复是一组表（1 到 16 张），先写组意图，再逐张翻转。
3. **停用**：不改表内容，不出新版次。只写记录，记下停用人、理由、批准依据、停用时的头版。
4. **停用期间**：
   - 不参加方案状态一致核（E1）；
   - 内容冻结（E2）；
   - 运行时读拒（E3）；
   - 维护读照常，带 `lifecycle` 块（E4）；
   - 别的表不能新引用它（E5）；
   - 撤首存要改它的引用时拒（E6）。
5. **恢复**：对现在的头版当作「再存一次」重核，核得过才回到在用；也可以带新内容恢复，新内容走全套闸。
6. **谁能停用**：锚表不能停用；被组外的表引用着的，不能单独停用。
7. **签名**：受控表走 81 入口签名。普通表只认维护应用调用；签名模式下要写手签名、拒 agent 写手。

## 三、谁能停用

### 3.1 按类拒绝：锚表

插件按固定名、或按派生名读的表，停了会让别的核**静默失效**。比如场景与话题表一缺，场景号核就只报黄。所以这些表一律拒 `TABLE_DEACTIVATE_ANCHOR`。判定只用现有的谓词，不另立名单：

| 类 | 判定 | 为什么不能省 |
|---|---|---|
| 交付七张及其最终名 | `save_gate.gated(table)` | 场景与话题表、受理条件表不在五张里；受理条件表在最终名首存以前 `_kept` 是假 |
| 首存链上的名字 | `storage_care._kept(storage, table)` | 旧名（如 `dispatch.route`）不在 `GATED` 里 |
| 能力表 | `capability_catalog.TABLE` 及其旧名 | 不在 `GATED` 里，也不在首存链上 |
| 方案层表 | `SOLUTION_TABLE_RE` | `decision_v2.cross_check` 按派生名读兄弟表，按清单过滤管不到。0.5.44 先拒，要做另立一条 |

场景整包的各部分表、场景与话题表、默认路由表都已经被前两条盖住，不另列。

受控表（`controlled.listed`）今天只有场景与话题表，它属于锚表，所以 0.5.44 里实际不会有受控表被停用。第六节仍按类写全了受控表怎么签，以后有非锚的受控表时不用改设计。

### 3.2 被引用的表要整组停用

有五种引用。组外在用的表，只要有一种引用指着组里的某张表，停用就拒 `TABLE_DEACTIVATE_REFERENCED`。`detail` 列出「谁 · 哪种引用 · 哪个字段 · 指向谁」。

| # | 引用 | 从哪里找引用方 |
|---|---|---|
| ① | 路由表的 `resource_table` | 路由表清单里的每张路由表头版 |
| ② | 资源表的 `route_tables` | 组内每张路由表的 `resource_table` 所指的资源表，以及清单里路由表所指的资源表 |
| ③ | 决策表 `declare` 里的能力表引用 | 能指向组内表的只有试验能力表（`capability_catalog.TRIAL_TABLE`）；引用方从用例集的读表记录与清单里的路由表找 |
| ④ | `search.info` 一类按内容摘要钉住的引用 | 同 ③ |
| ⑤ | 用例集：存着的用例集，它的读者参数或记下的读表里有组内的表 | 只查锚表的用例集键（`route-table:<表>:c`），以及组内表自己的用例集。别的表的用例集没法反查（存储列不出键），这是已知限制：用例集运行不走 E3，读到停用表也照样跑 |

组内互相引用不管，比如路由表和它的资源表互指，只能一起停。

### 3.3 其余前置核（按这个次序，第一条不过就停）

0. 先看组意图：派生的组号（4.1 第 2 步）已有组意图、而且不是 `DONE` 或 `ABORTED`，就是同一请求的重发，从组意图记的进度接着做，不再跑下面几条。
1. 请求格式：`tables` 1 到 16 张、不重复；`reason`、`approval_ref` 各 3 到 200 字。不合格拒 `TABLE_LIFECYCLE_INVALID`。
2. 锚表：拒 `TABLE_DEACTIVATE_ANCHOR`（3.1）。
3. 每张表都要有头版：拒 `ROUTE_TABLE_MISSING`。
4. 每张表的 `expected_version` 等于头版版次：拒 `ROUTE_TABLE_STALE`。
5. 已有生命周期记录不是 `ACTIVE`：拒 `TABLE_ALREADY_DEACTIVATED`（已停用）或 `STORED_TABLE_IN_PROGRESS`（正在翻转、而且不是这个请求的）。
6. 组外引用：拒 `TABLE_DEACTIVATE_REFERENCED`（3.2）。

### 3.4 能停用的类别，以及各自的效果

| 类 | E1（不进跨表核） | E2（冻结） | E3（运行时读拒） | 说明 |
|---|---|---|---|---|
| 路由表（v2/v3，不是锚表） | 是 | 是 | 是 | 试验路由表都在这一类 |
| 资源表（不是锚表） | 不涉及：别的表靠引用找它，靠清单找不到 | 是 | 是 | 一般和它的路由表整组停用 |
| 决策表、决策集（不是锚表，也不是方案层表） | 不涉及 | 是 | 是 | 试验副本的实体表、补充表、受理表 |
| 试验能力表 | 不涉及 | 是 | 是 | 被钉住时要和引用方整组停用 |

对路由表以外的类别，停用只管冻结、运行时读拒和维护读；它们本来就不在按清单的跨表核里。

## 四、停用

### 4.1 次序

1. 跑 3.3 的前置核。
2. 写组意图记录：`table-lifecycle:group:<组号>`，记下成员、各自的 `expected_version`、请求号、`phase: DEACTIVATING`。
   - 组号从请求派生：op、成员、各自版次、各自当时的生命周期 `epoch`（没有记录记 0）、`reason`、`approval_ref` 合起来算 sha256。带上 `epoch`，停用 → 恢复 → 再停用就不会算出同一个号。
   - 组意图写到 `DONE` 以前，成员对跨表核（E1）当在用算。
3. 按引用方向逐张写 `DEACTIVATING`：**引用方在前，被引用方在后**。比如先路由表，再它的资源表。
4. 再读一次每个成员的头版：
   - 有动过的（存表在这期间落下了），把已写的成员退回 `ACTIVE`、组意图写 `ABORTED`，拒 `ROUTE_TABLE_STALE`；
   - 都没动，就逐张写 `DEACTIVATED`，组意图写 `DONE`。
5. 写操作记录（第七节）。

从成员自己的记录写成 `DEACTIVATING` 那一刻起：
- 对跨表核（E1）仍算在用；
- 冻结（E2）、运行时读拒（E3）、不能新引用（E5）已经生效。

冻结核放在 `_save` 写头版之前那一下（`_before_head` 处），不放在存前闸之前。已经过了这一下的存表仍会落下，由下面存表那一侧的回读和恢复重核兜住。

**停用中途断了**：同一请求重发，从组意图的进度接着做（3.3 第 0 条）；或者发 `op=deactivate`、带 `abort: true` 和同一个组号，把已写的成员退回 `ACTIVE`、组意图写 `ABORTED`。

**存表那一侧**：`_save` 写完头版以后，再读一次生命周期记录，照 I19、I20 读首存记录的做法。
- 读到 `DEACTIVATING`，而且记录里的头版不是自己刚写的：这次存表照样成立，回执报黄 `TABLE_DEACTIVATION_CROSSED`。停用一方第 4 步要是还没读头版，就会看到头版动了、自己退回；已经读过了，就落到下一条。
- 读到 `DEACTIVATED`（停用已经走完第 4 步，在这之后才落下这次存表）：这次存表照样成立，同样报黄。表留在停用状态；恢复时对现在的头版重核（第五节），不会卡死。

### 4.2 停用以后的效果

**E1 两处跨表核不再看它**

只改方案状态一致核 `_one_state`，改用 `active_route_tables()`：`route_tables()` 去掉 `DEACTIVATED` 的表。
- `DEACTIVATING`、`REACTIVATING` 都算在用。
- 被跳过的表报一条 `warnings`：码 `CROSS_CHECK_SKIPPED_DEACTIVATED`，列出表名。
- 生命周期记录读不出来时回 503（`STORED_TABLE_UNAVAILABLE`），不当它在用，也不当它停用。

资源决策编译核、旧名引用提醒（I15）、撤首存改引用（I24）**不过滤**：
- 资源决策编译核：停用路由表 A 时，它指的资源表 T 一定列着 A（存 A 时就要求），按 3.2 第 ② 种引用必须同组，T 也冻结了，编译核不会因为 A 拦到在用的表；
- 旧名引用提醒照样列出停用表，并在那一条上注明 `lifecycle: DEACTIVATED`；
- 撤首存改引用见 E6。

**E2 内容冻结**

这几个 op 对 `DEACTIVATING`、`DEACTIVATED` 的表，以及不持有记录的 `REACTIVATING` 表，回 `TABLE_DEACTIVATED`（提示「先恢复再改」）：
- `save`（包括草稿回滚经过的同一次存表）；
- `cases_save`；
- `cases_check`。

草稿那几个 op 只对五张表开着，五张表是锚表，所以照旧先回 `STORED_TABLE_DRAFT_NOT_SUPPORTED`。`prune` 只删旧版次、不动头版，照旧可以做。

**E3 运行时读拒**

运行时读另立一个包装 `RuntimeReads`：
- 写法照 `alias_reads.Counting`，包住 `load`、`version`、`find_content`；
- 生命周期状态是 `DEACTIVATING`、`DEACTIVATED`、`REACTIVATING` 时，抛 `RouteTableError("TABLE_DEACTIVATED")`。

只给三处运行时入口用：
- 方案调用工具（`invoke_solution`，它已经把 `RouteTableError` 的码原样带进回执）；
- `tools/evaluate_stored_table.py`；
- 决策求值的 `model_loader`。

不用它的读：
- `StorageTables.load` 本身；
- 存表时的跨表核；
- 存前闸里的覆盖读；
- 用例集运行；
- 维护读。

这些照旧读得到停用表。

几条细则：
- 按版次或按内容摘要钉住的读一样拒。
- `DEACTIVATING` 期间运行时也拒，这样停用一开始就生效，不留窗口。
- 记录读不出来：运行时拒，回 `FAILED ROUTE_TABLE_UNAVAILABLE`（失败即关；与现有的存储读失败同一个码，流程可以重试）。

这一条兑现 0.5.6 的约定：表都不参加一致核了，就不能再拿它调方案。

被拒的运行时读计数：
- 做法照 `alias_reads`，尽力而为、只增不减；
- 键 `route-table:<表>:lifecycle-reads`，按天记次数，记最后一次的调用应用号；
- 读回经 `op=lifecycle`；
- 计数写失败不影响回答。

**E4 维护读带停用状态**

逐个读 op 的口径：

| op | 停用表的回答 |
|---|---|
| `table`、`history`、`version`、`check`、`saved` | 200，多一个 `lifecycle` 块 |
| `ledger`、`usage` | 200，表那一行多 `lifecycle.state` |
| `cases` | 200，多 `lifecycle` 块 |
| `cases_check` | `TABLE_DEACTIVATED`（同存表，E2） |
| `draft` | 照旧 `STORED_TABLE_DRAFT_NOT_SUPPORTED`（五张表以外没有草稿） |
| `alias_reads`、`v2_vocabulary`、`catalog`、`scene_catalog` | 不变（不针对某一张停用表） |
| `lifecycle` | 见第七节 |

`lifecycle` 块：

```json
"lifecycle": {
  "state": "DEACTIVATED",
  "since": "2026-11-24T02:10:00Z",
  "epoch": 3,
  "group": "6c1f…",
  "head_version": 1,
  "head_save_id": "…",
  "reason": "换号窗口试验链试验完毕，表留存不参加跨表核",
  "approval_ref": "协调定 368"
}
```

- 操作人与操作记录号只给维护应用看，口径同历史里的存表人。
- 从来没有生命周期记录的表，上面每个读的回答都和 0.5.43 逐字节相同。恢复过的表带 `state: "ACTIVE"` 与最近一次停用、恢复。

**E5 不能新引用停用表**

`_cross_check` 加一条：要存的新内容里，3.2 五种引用里有任一种指向生命周期不是 `ACTIVE` 的表，就拒 `TABLE_REFERENCES_DEACTIVATED`，点名那张表与字段。这一条覆盖存表、`cases_save` 与带内容的恢复。

**E6 撤首存遇到停用表**

撤首存要改引用（I24）时，要改的头版里有停用表，撤销就拒 `TABLE_DEACTIVATED`，点名那张表，提示先恢复再撤。不绕过冻结替它改引用：改引用就是改内容，停用表的内容不能改。

## 五、恢复

### 5.1 次序

请求带：
- `tables`：要和停用时的组成员**完全相同**，不能只恢复一部分；
- 每张表的 `expected_epoch`；
- `reason`、`approval_ref`；
- 可选的每张表新内容 `doc`。

恢复的组号用 4.1 同样的算法另算：op 是 `reactivate`，成员各自的 `epoch` 是停用写完那一刻的值。

1. 前置核：
   - 先看组意图：这个组号已有组意图、而且不是 `DONE` 或 `ABORTED`，就是重发，从记的进度接着做；已经是 `ACTIVE` 的成员跳过；
   - 组成员对得上，否则拒 `TABLE_LIFECYCLE_INVALID`；
   - 每张都是 `DEACTIVATED`，否则拒 `TABLE_NOT_DEACTIVATED`；
   - `epoch` 对得上，否则拒 `ROUTE_TABLE_STALE`。
2. 写组意图 `phase: REACTIVATING`。逐张写 `REACTIVATING`，**被引用方在前**，记录的持有者是这个请求。从这一刻起，别的表的跨表核看得到这一组（E1 只跳过 `DEACTIVATED`）。
3. 重核，组内的表都按在用算：
   - 不带 `doc` 的表：对**现在的头版**跑 `_cross_check`（包括 `_one_state` 对照在用的路由表、按引用的核、E5），再跑它的用例集（有用例集的才跑）；
   - 带 `doc` 的表：由持有者走正常 `_save`，全套闸都跑，`expected_version` 用重核那一刻读到的头版版次。存表号从恢复请求派生，重发认得出自己存过的那一版。
   - 有红就拒，码与存表时同一个（比如 `ROUTE_TABLE_SOLUTION_STATUS_CONFLICT`），回执注明「恢复时重核」；组内记录退回 `DEACTIVATED`，组意图写 `ABORTED`。
4. 逐张写 `ACTIVE`。不带 `doc` 的表，版次与内容摘要都不变。组意图写 `DONE`。
5. 写完以后，再读一次别的路由表的头版：
   - 有表在第 3 步之后动过的，对它们重跑这一组的 `_one_state`；
   - 有冲突就在回执里报红 `TABLE_REACTIVATION_RACED`，点名两张表与方案。这时表已在用，由人改其中一张。

### 5.2 `REACTIVATING` 的规则

- 运行时照拒（E3）。
- 只有持有记录的恢复请求能存这张表，别的存表拒 `TABLE_DEACTIVATED`。
- 中途断了，处理办法二选一：
  - 同一请求再发，从断的地方接着做；
  - 发 `op=reactivate`，带 `abort: true` 和恢复的组号，退回 `DEACTIVATED`。已经写成 `ACTIVE` 的成员不退（它已经过了重核），只退还在 `REACTIVATING` 的；回执列出哪些已在用。
- 退回也是一次带比对的写，失败了可以再发。

### 5.3 已知限制

- 插件存储没有事务。恢复第 4、5 步之间，另一张路由表的存表可能同时落下。第 5 步会再读、报出来，但不会自己撤回。
- 这个窗口不比现有「两张路由表同时存」的窗口宽：今天两次并发存表也可能都过 `_one_state`。

## 六、签名与授权

`deactivate`、`reactivate` 在 `two_state` 里另立一个分支，照 prune 落实那一段写：

1. 总是 `check_caller`：只认「路由表维护」应用调用，否则拒 `STORED_TABLE_WRITERS_APP_REJECTED`。
2. 签名模式下：`parse_writers`、`verify`（写手签名覆盖 op、表、版次、请求体）、`_agent_may`（agent 写手拒）。
3. 进 `_MUTATION_LOCK`，同一进程里一次只做一个。
4. **开放模式（现网）下唯一的闸是第 1 条**：开放模式没有写手身份，认不出 agent。这一点照实写进发布说明。

受控表（`controlled.listed`）：`two_state.controlled_target` 加一个分支，op 是这两个、组里有受控表时，返回它的存名。
- 于是要 81 入口签名（RS256），签名覆盖 op、表参数、版次、请求体摘要（含 `reason`、`approval_ref`）、入口号、时刻。
- 入口号只能用一次。
- 组里只要有一张受控表，整组按受控表签。
- 0.5.44 里受控表都是锚表，实际不会出现这种情况（3.1）。
- 81 侧要做的：入口能签这两个新 op；放行句写「停用 / 恢复 + 存名」；台账记一笔。这些交协调派。

`op=lifecycle` 是读，不要签名。

依据（`reason`、`approval_ref`）原文进生命周期记录与操作记录。插件不核批准真不真：受控表靠 81 入口放行句，普通表靠维护应用台账。

## 七、存储

**生命周期记录**
- 键 `route-table:<storage_name>:lifecycle`。按 `storage_name` 存，所以全名、旧名拼法都落在同一份上；表名里不会有 `:`，不会和现有键撞。
- 格式 `dmn-json.table-lifecycle/v1`，字段：`table`、`state`、`epoch`（记录每写一次加 1，同 `_put_record`）、`owner`（持有的请求号）、`group`、`head_version`、`head_save_id`、`content_sha256`、`reason`、`approval_ref`、`at`、`history`（最近 50 次翻转，照 `settings.write`）。
- 写法照首存记录的 `_put_record`：
  1. 先读标记（state、epoch、owner）；
  2. 已经是目标状态就当做完了；
  3. 不是预期的标记就拒 `STORED_TABLE_IN_PROGRESS`；
  4. 写完再读回比对。
- 记录不删。

**组意图记录**
- 键 `table-lifecycle:group:<组号>`。
- 字段：`op`、成员与各自的 `expected_version` 或 `expected_epoch`、`owner`、`phase`（`DEACTIVATING`、`REACTIVATING`、`DONE`、`ABORTED`）、`at`。
- 写法同上。

**停用清单**
- 键 `table-lifecycle-index`，只增不减。
- 先写进清单、再读回核对，然后才写组意图。
- `op=lifecycle`（不带表名）列出现在不是 `ACTIVE` 的表：靠这份清单，再对路由表清单里的名字逐个查记录键兜底，所以清单丢了一条也列得出来。

**操作记录**
- 一组一份：`route-table:<第一张表>:operation:<操作号>`，操作号就是派生的请求号。重发落在同一个键上，已存在就不再写。
- 内容：op、actor、组号、每张表的 `head_version` 与 `head_save_id`。
- 在 `two_state._record` 里加这两个 op。

**其他**
- `storage_care.usage` 与 `_table_keys` 要认识新后缀；`prune` 不动这几类键。

**存储格式**：0.5.44 **会写新键**，不能像 rc2 那样说「不写新键」。没停用过任何表的时候一个新键都不写，存储与回答都和 0.5.43 逐字节相同。

## 八、回退到 0.5.43

0.5.43 不认识生命周期记录，装回以后停用表会静默回到在用：重新参加一致核，运行时也能读了。停用期间别的表可能已经把共有方案改了状态，所以这会在运行时破坏 0.5.6 的约定。因此：

1. 回退前先 `op=lifecycle`，列出不是 `ACTIVE` 的表。
2. **每一组都要先恢复**（会重核）。恢复不了的组（撞冲突），先改别的表，或者带新内容恢复，直到恢复成功。
   有一组恢复不了，就不回退。
3. 都恢复了才装回 0.5.43。生命周期记录和清单留在存储里，没人读；以后再装 0.5.44，它们都是 `ACTIVE`，不起作用。

发布说明写明：带着停用表回退，会破坏 0.5.6 的约定。

## 九、对两类现网表的用法

- **试验副本五张**：试验完，在换号窗口之后整组停用一次，`approval_ref` 写协调的定号。
  - 组内有路由表和它的资源表（两张互指）。
  - 停用前查组外引用：在用的路由表、资源表、用例集都不能指着这五张。
  - 停用以后，路由表再改方案状态，就不会因为试验表拒 `STATUS_CONFLICT`。
- **费用组的旧试验路由表**：同一类做法，但停用前要先确认没有调用方：
  - 81 台账里登记的读表关系；
  - 发布中流程的节点参数里有没有这个表名；
  - 它登记的两个方案应用近几天的 AgentHub 运行日志。
  确认没有调用方，再由费用组给批准句，协调写进 `approval_ref`，再停用。它若有资源表或别的引用，整组停用。

## 十一、用例清单（实现时逐条写成单测）

**停用**

1. 普通路由表停用成：记录 `DEACTIVATED`，版次与内容摘要不变，组意图 `DONE`，操作记录一份。
2. 锚表各拒 `TABLE_DEACTIVATE_ANCHOR`，每条谓词至少一个只有它盖得住的名字：
   - `gated()`：空存储上的受理条件表（最终名还没首存，`_kept` 是假）；
   - `_kept()`：旧名 `dispatch.route`；
   - 能力表：`target.capability.catalog` 与旧名 `platform.capability.catalog`；
   - 方案层表：一张 `solution.…` 表。
   另有交付七张其余几张、六个最终名、默认路由表各一条。
3. 路由表被组外在用的资源表 `route_tables` 列着：单独停用拒 `TABLE_DEACTIVATE_REFERENCED`，`detail` 点名；整组停用就成。
4. 试验能力表被组外决策表的 `search.info` 钉住：拒 `REFERENCED`；和引用方整组停用就成。
5. 组外的用例集读者点名组内的表：拒 `REFERENCED`（第五种引用）。
6. `expected_version` 不对，拒 `STALE`；没有头版，拒 `MISSING`；格式不对，拒 `INVALID`；几条同时不过时，按 3.3 的次序回第一个。
7. 已停用：同一请求再发，照答已停用，不写第二份操作记录；不同的请求，拒 `ALREADY_DEACTIVATED`。
8. 组里一张前置核不过：整组不停，一份记录都不写。
9. 整组写到一半断了：重发补完（先认组意图，不撞 `STALE`）；或者 `abort` 退回 `ACTIVE`。补完以前，已写 `DEACTIVATING` 的成员对跨表核算在用、运行时拒、存表拒。断了又有一次存表落下，重发照样接着做。
9a. 停用 → 恢复（不带内容）→ 用同样的理由与依据再停用：算出新的组号，是一次新的停用，写新的操作记录。
10. **竞态**：停用写完 `DEACTIVATING` 后，同一张表的一次存表落下头版。停用第 4 步看到头版动了，退回 `ACTIVE`、拒 `STALE`；存表回执带 `TABLE_DEACTIVATION_CROSSED`。
11. **竞态**：停用走完以后，一次早先过了冻结核的存表才落下头版。表留在停用；恢复时对新头版重核，恢复成。

**停用效果**

12. 定 366 那一例：试验路由表停用以后，把试验表里也有的那个方案改 CANDIDATE 照存 200，`warnings` 有 `CROSS_CHECK_SKIPPED_DEACTIVATED`。
13. 反例：没停用时同一改动照拒 `STATUS_CONFLICT`。
14. 场景整包 `bundle_check`、`publish` 不再因停用表拒 `STATUS_CONFLICT`。资源决策编译核照旧看停用表，路由表与资源表整组停用以后存在用的表，不会被它误拦。
15. 旧名引用提醒照样列出停用表，并注明 `lifecycle`。
16. 停用表的 `save`、`cases_save`、`cases_check` 拒 `TABLE_DEACTIVATED`；`prune` 照做；草稿 op 回 `STORED_TABLE_DRAFT_NOT_SUPPORTED`。
17. `invoke_solution` 读停用表回 `REJECTED TABLE_DEACTIVATED`，钉版次、钉内容摘要也拒，计数加 1；`DEACTIVATING` 期间同样拒。
18. `evaluate_stored_table` 与决策求值的 `model_loader` 读停用表：拒，码同上。
19. 维护读、存表时的跨表核、用例集运行照旧读得到停用表的头版（证明 E3 没放进 `StorageTables`）。
20. E4 表里每个读 op 的回答。非维护应用调用时看不到操作人。
21. 金样：从没停用过的表，E4 表里每个读 op 的回答都和 0.5.43 逐字节相同；没停用过任何表时，存储里一个新键都没有。
22. E5：存一张路由表，让它的 `resource_table` 指向停用表，拒 `TABLE_REFERENCES_DEACTIVATED`；`cases_save` 的读者点名停用表，同拒。
23. E6：撤首存要改的引用里有停用表，撤销拒 `TABLE_DEACTIVATED`；恢复以后再撤就成。
24. 生命周期记录读不出来：运行时回 `FAILED ROUTE_TABLE_UNAVAILABLE`；一致核回 503。
25. 计数写失败：运行时回答不变。

**恢复**

26. 停用后没人改过别的表：恢复成，`epoch` 加 1，版次与摘要都不变，一致核重新看它。
27. 停用期间别的路由表把共有方案改了状态：恢复拒 `STATUS_CONFLICT`，注明「恢复时重核」，记录退回 `DEACTIVATED`。
28. 同 27 的情形，带新内容恢复：走全套闸，存成以后在用。新内容也冲突就拒，退回 `DEACTIVATED`。
29. 带内容恢复，存成以后、写 `ACTIVE` 之前断了：重发就做完，不存第二版；`abort` 退回 `DEACTIVATED`。恢复写 `ACTIVE` 写到一半断了：重发跳过已在用的成员；`abort` 只退还在 `REACTIVATING` 的。
30. `REACTIVATING` 期间：运行时拒；别的请求存这张表拒；别的路由表的存表看得到它。
31. 只恢复组里一部分：拒 `TABLE_LIFECYCLE_INVALID`。
32. 恢复第 4、5 步之间，另一张路由表落下冲突的存表：回执报 `TABLE_REACTIVATION_RACED`。
33. 停用 → 装回 0.5.43 → 改了那张表 → 再装 0.5.44：记录仍是 `DEACTIVATED`；恢复对现在的头版重核，成。

**签名与授权**

34. 开放模式下，不是维护应用调用的拒 `STORED_TABLE_WRITERS_APP_REJECTED`；维护应用调用的就成，不管调用者是不是 agent。
35. 签名模式下：没有写手签名的拒；agent 写手拒；人类写手签名成。
36. 受控表（用测试夹具把一张非锚表登记为受控）：没有 81 入口签名的拒；签名覆盖的请求体被改一个字（比如 `reason`）的拒；同一入口号第二次用拒。
37. 操作记录：一组一份，列出每张表的版次与存表号；重发不写第二份。

**存储**

38. 记录写入时另一个请求抢先写了：拒 `STORED_TABLE_IN_PROGRESS`，不覆盖。
39. 停用清单丢一条（直接删掉那一项）：`op=lifecycle` 仍靠逐个查键列出那张路由表。
40. `usage` 认识新后缀；`prune` 不删生命周期相关的键；`history` 留最近 50 次，第 51 次挤掉最早一次。
41. 用全名（`support.`）或旧名拼法请求，落在同一份记录上。
42. 0.5.43 的代码读有生命周期记录的存储：表当在用，回答同 0.5.43（这条证明第八节写的回退行为）。

## 十三、要并进标准的条文（交标准维护人）

在 DMN 结构与维护标准「存表两种模式」之后加一节「表的生命周期：停用与恢复」，要点：

1. 表只能停用，不能删除。停用不改内容、不出新版次。
2. 停用的表：
   - 不参加按清单的跨表一致核；
   - 运行时读一律拒；
   - 内容冻结，不能被新引用；
   - 维护读照常，并标明停用。
3. 插件按固定名或派生名读的表不能停用：交付七张及其最终名、首存链、场景整包各部分、场景与话题表、能力表、方案层表。被在用的表引用着的表，要和引用方整组停用。
4. 恢复时，对现在的头版当作再存一次来重核，核不过不恢复；可以带新内容恢复。
5. 受控表的停用与恢复走受控入口签名；普通表只认维护应用。两者都要写理由与批准依据。
6. 试验表试验完，用停用退场，不存「清空版」占位。
7. 插件回退到不认识停用的版本之前，先把所有停用表恢复。
