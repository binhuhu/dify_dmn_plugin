# v0.5.30: solution segment in solution-layer table names

This is a **pre-release**, continuing v0.5.29's single-operator, serial-maintenance scope and OPEN/SIGNED risks. Target-host installation/upgrade, real business API integration and production acceptance remain **NOT_RUN**. Publication and CI are not deployment acceptance.

## What changed

A solution-layer table name may carry a **solution segment** after the scene id:

```
solution.<search.fact|fact.feature|feature.reality|reality.strategy>.<scene_id>[.<solution>][.<part>]
solution.fact.feature.M_P_02_04_01.56d3c0c5
```

- `<solution>` is the first segment of the owning solution app's id: the 8 lower-case hexadecimal digits before the first hyphen of `owner.app_id`.
- A name that carries a segment is stored only when the segment equals the first segment of the document's `owner.app_id`. Anything else is refused with `STORED_TABLE_NAME` (path `table`) and nothing is written. This applies to every version, so a later save cannot move a chain to another app.
- Two solution apps of one scene therefore keep separate tables and separate version chains. Reading, evaluating and history work on these names as on other solution-layer names. As before, drafts and publication cover only the five delivery-chain tables, and undo is refused for solution-layer names.
- A resource-targets list (`dmn-json.resource-targets/v1`) carries no owner and is refused under a name with a segment.
- The older solution-layer names `solution.disposal.strategy.<scene_id>` and `solution.disposal.status.<scene_id>` accept the segment under the same rule.
- The role a table must declare still follows the name prefix; the segment does not change it.

## Compatibility

- Names without a segment behave as in v0.5.29, including the absence of an owner check on them; only the wording of the name-rule refusal message changed (same code and path). Existing stored tables are not renamed, migrated or re-validated.
- A fifth name segment of exactly 8 lower-case hexadecimal digits is now always read as the solution segment and can no longer be used as a part name. A document stored under such a name by v0.5.29 or earlier stays readable; saving a new version is refused unless the segment matches its owner. No such name is known to be in use; this was not checked against any host.
- Table names remain limited to 64 characters. With a three-level scene id and the segment, the room left for a part is 21 (`search.fact`), 20 (`fact.feature`), 17 (`feature.reality`) and 16 (`reality.strategy`) characters.
- The segment is not a registered identifier. Two apps whose ids share the first 8 digits share a segment, and the plugin does not tell them apart: either may store under it. Do not run two such apps on one scene.
- An app id changes when an app is rebuilt or moved to another environment; tables stored under the old segment are then not found under the new one and must be stored again.
- Downgrading: v0.5.29 and earlier refuse a segment that starts with a digit, so those tables stay in storage but cannot be read or stored until upgrading again. A segment that starts with a–f is read by v0.5.29 as a part name: those tables stay readable, and any solution app can store under them because v0.5.29 has no owner check.

## Not in this release

Routing one scene to several solution apps by share is **not** implemented. A route table row still names exactly one target.

## Verification scope

Tests cover the name grammar with and without a segment and a part, the 64-character bound, the owner check on first and later versions, two apps of one scene keeping separate chains, unchanged behavior of names without a segment, and the name-to-role rule. Exact test counts and package identity are recorded with the release artifacts.
