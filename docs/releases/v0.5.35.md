# v0.5.35: conservative storage recovery and cleanup

Based on public v0.5.34 (`da9bb58`). This release keeps the existing storage keys, table formats, evaluation behavior and 1 GiB storage allowance. No table migration is required.

## Changes

- Uncertain versions above the observed head are preserved by default. Cleanup requires a one-hour minimum age and an explicit `confirm` list of `{version, save_id}` entries.
- A version is not eligible for cleanup if its parent differs from the observed head, a successful-save record exists, or another scanned version identifies it as its parent. The head version and save ID are rechecked before deletion.
- Cleanup of such a version removes only its version-number key. Existing save-ID copies and related records are retained. The new read-only `op=saved` operation retrieves an existing copy by save ID.
- Capability-table versions below the observed head remain protected because other tables can pin their content digests. Ordinary old versions must also be at least one hour old before cleanup. The five delivery-chain tables remain excluded from cleanup.
- Reads by version stop at the observed head. When the head's own version-number copy is missing, reads can return the head, and a later save repairs that copy before writing the next version.
- Failure messages distinguish a definitely incomplete write from a head write with an unknown outcome, and no longer suggest that reading an old head proves the write did not land.

## Safety boundary

This release is intended for single-operator, serial maintenance. It does not add storage transactions, compare-and-swap, or a cross-process lock.

A one-hour delay is a conservative margin, not proof that a deployment's cache or delayed writes have expired. Verify the deployment's actual cache and write-timeout behavior before confirming cleanup. If the authoritative state cannot be established, leave the uncertain version in place, even if this blocks further saves.

An incorrect `confirm` can still remove the real head's version key while a stale head is being served. Saving different content at that point can reuse the version number and break content-digest or version-number references. The old content is recoverable through `op=saved` only when its save-ID copy exists and is intact (`has_copy: true` indicates existence, not a content-integrity guarantee). If that copy is absent, deleting the version key can remove the last recoverable copy. Do not confirm such cleanup without an independently verified backup and authoritative state.

Some concurrent or delayed-write sequences can leave a previously successful version above the observed head and block future saves. This release preserves that version; it does not provide an automatic repair operation. Platform-assisted reconciliation may be necessary. Retained copies without version keys are not discoverable by the plugin and are not included in `usage` totals.

See [storage care](../plugin-storage-care.md) for operation details. Do not use cleanup to free space by guessing which uncertain versions are safe to remove.

## Upgrade and verification

1. Back up the relevant tables and record the installed plugin identifier, storage allowance and current table versions.
2. Upgrade from the GitHub release using the host's supported upgrade path. This publication does not itself install the plugin or change any production tables.
3. Verify the installed version and plugin identifier, then read back table versions and compare representative evaluation results.
4. Treat any recovery of existing incomplete saves as a separate maintenance operation. First establish the authoritative head and check that no workflow pins the version being removed.

## Rollback

The stored formats remain compatible with v0.5.34. Before rollback, inspect `op=usage`: if a table's `head_version` is absent from `versions`, establish the authoritative head and repair its missing version copy before downgrading. Reading `op=version` alone cannot detect this condition because v0.5.35 can return the head as a fallback.

v0.5.34 does not support `confirm` or `op=saved`, and its cleanup can delete both version and save-ID copies after only ten minutes. Do not use v0.5.34 cleanup to recover unknown-outcome saves after rollback. Rollback to v0.5.33 additionally requires checking compatibility with table formats introduced since that version.

## Validation scope

The release checks cover Python regression, engine checks, adapter/DOM tests, manifest permissions, formatting, source checksums, package/source parity, and fault-injection sequences for stale heads, delayed writes and cleanup. Required GitHub checks must complete for the published commit.

Target-host installation, live storage recovery and production acceptance are separate checks and are not implied by local tests or publication. No production tables are changed by the release process.
