# v0.5.29: best-effort change attribution (`saved_by`)

This is a **pre-release**, continuing v0.5.28's single-operator, serial-maintenance scope and OPEN/SIGNED risks. Target-host installation/upgrade, real business API integration and production acceptance remain **NOT_RUN**. Publication and CI are not deployment acceptance.

## Attribution and trust

Successful saves, draft saves and publishes attempt to store attribution beside the result. Undo and draft discard attempt to store a separate operation record. This is not a complete, transactional or tamper-proof audit log.

| Field | Meaning |
|---|---|
| `user` | Bounded host-supplied tool runtime user identifier, or null. It may represent an API/host account, not the human editor. |
| `user_verified` | Always false: the plugin does not independently authenticate a natural person. |
| `via` | Unverified request-context hint; defaults to app. A direct caller can claim endpoint without changing its HMAC. |
| `via_verified` | Always false: the hint does not prove the transport or origin. |
| `writer` | Writer identifier whose HMAC was verified, or null. Shared/copied keys can impersonate the writer. |
| `writer_verified` | Whether the request passed writer HMAC verification; not independent proof of human identity. |

The editor adds the endpoint hint, but its tag is not a trusted out-of-band channel. Host runtime identity semantics have not been verified on the target host. No access-control decision should rely on `user`, `via`, or attribution availability.

## Storage and operation behavior

- Saves/publishes store `saved_by` under `route-table:<canonical-table>:by:<save_id>`; draft saves use `by:draft:<draft_id>`. Metadata is never inserted into the table document, so table content and digests are unchanged.
- The successful response contains attribution and `metadata_status`. `persisted` means the storage API returned a matching read-back, not a transaction, authoritative fresh read or durability guarantee. `unavailable` includes write/read errors, conflicting sidecars and uncertain write outcomes. Do not replay a successful business operation just to retry its metadata.
- Retried publication preserves and returns the original attribution instead of replacing it with the retrying actor. Sidecar conflicts are not permission to overwrite an author.
- Undo and draft discard return a separate `operation_record` with a unique operation ID, operation, actor and result summary; storage uses `route-table:<canonical-table>:operation:<operation_id>`. They do not rewrite the authors of existing versions. Undo's result identifies moved versions and reference fixes, but internal repair writes are not independently attributed versions.
- History enrichment reads both canonical and legacy sidecars by the unchanged save ID, so undo does not lose existing version attribution. Conflicting or unreadable aliases are marked unavailable rather than silently choosing an author. A failure for one history item does not hide other items' attribution.
- Only the pinned maintenance-app runtime context receives new historical identity fields. Other callers retain existing history data without attribution enrichment. This is an app-level boundary: it does not prove login or identify a person. Review host Web App/API access policies before enabling OPEN.
- Older versions or writes without successful metadata persistence have no attribution. Refused operations do not create attribution, but a storage-error response may already have changed business state. An absent record does not prove no write occurred.

## Privacy, retention and compatibility

This release adds persistent runtime identifiers and unverified origin hints. Maintenance-app callers, authorized storage operators and retained host outputs/backups may see them. See the [privacy notice](../../builtin/PRIVACY.md). No automatic record listing, retention expiry or cleanup is implemented; discarded draft and operation records remain and consume the existing 16 MiB allowance. Downgrading does not remove these records.

Version, draft and publication document formats remain unchanged. v0.5.28 ignores the new sidecars and can continue to read compatible table content. Its earlier access/governance behavior returns on downgrade. The table-name and role limitations for downgrade to v0.5.27 and earlier remain as documented for [v0.5.28](v0.5.28.md). No production migration, database restore or host configuration change is performed by this release.

## Verification scope

The v0.5.29 tests cover synthetic host context, signed/open saves and publication, undo/discard operation records, alias migration, spoofed origin hints, metadata failure isolation, historical identifier visibility, digest preservation and prior-version reads. SDK protocol tests do not establish actual host authentication semantics. Exact final-commit test counts, CI links and package identity are recorded in the GitHub release.

Manifest permissions remain endpoint, app and 16 MiB storage. The official CLI-produced package is unsigned and has not undergone Marketplace review. Follow the host's signature and installation policies; do not bypass them.
