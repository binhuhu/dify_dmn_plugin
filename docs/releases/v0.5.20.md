# v0.5.20

**Prerelease candidate. Production compatibility has not been accepted.** This version adds first-store migration from transitional table aliases to standard storage names on top of the published v0.5.19 (`3364027130f2df77c69d44685788d783ab322e5e`). The design, offline tests and operating limits are documented below. Publication is separate from installation or migration of live tables.

**Before a table's first store under its standard name, it is intended to retain v0.5.19 behavior**, including old-name saves. Verify this on isolated snapshots before any production use.

## Names

| standard name = storage name | old name (transitional alias) | table |
|---|---|---|
| `target.scene.entity` | `target.scene_entity` | decision table or set, owner 定位 TARGET |
| `triage.scene.acceptance` | `triage.acceptance` | decision table or set, owner 分诊 TRIAGE |
| `triage.supplement.requirements` | `supplement.requirements` | supplement requirements |
| `triage.dispatch.route` | `dispatch.route` | route table |
| `triage.dispatch.resource` | `dispatch.resource` | resource targets |

One mapping (`dmn_client/table_names.py`, standard → old); the other direction is derived from it. A standard name follows its old name's format and owner rule, so `triage.dispatch.route` is a route table name and a resource table may list it in `route_tables`. S below is a standard name, O its old name, n the version of O's head at the first store.

## The first store

The first store under S copies O's current head unchanged: same `schema`, same `content_sha256` (recomputed as readers compute it), `expected_version` = n. It is stored as **S version n**, not 1, with `supersedes: {table: O, version: n, content_sha256}` in the document and at the top of the save receipt; its `parent_save_id` is O version n's (the copy takes that version's place in one chain). Send it through `route_table_store` op `save` with the table parameter empty (or O): before the first store a table parameter naming S is refused as in v0.5.19. Anything else under S before the copy is refused `STORED_TABLE_MIGRATE_FIRST` and writes nothing. A standard name whose old name holds nothing saves normally as its version 1.

The state of S lives in its first record `route-table:<S>:first`, read from storage at every decision (no cache). Each record carries an epoch (+1 at every change) and the id of the operation that wrote it; writers compare (state, epoch, owner), never the state alone (I18). Once written, the record is never deleted: an undone first store leaves it as OLD.

| state | record | reads | writes |
|---|---|---|---|
| OLD | none (as v0.5.19 left the storage), or `state: OLD` (a first store that aborted, or one undone) | both names read O, as v0.5.19 | O as v0.5.19; S only the first store |
| COPYING | written before anything else of the first store, with the copy's save id, time and document digest | both names read O | O refused; S only the same first-store request again |
| NEW | written last | S's own chain (below) | S only (numbering on from n); O refused |
| UNDOING | written first by an undo (rollback only) | S's own chain until its head is deleted, then O | refused; the same undo again finishes it |

A first store writes: the COPYING record (conditional), the gate report (if any), the route index entry (route tables), S version n, the save record, S's head, the NEW record (conditional) — 5 writes (6 for the route table; one more with a gate report). It reads O's head again before S version n and before NEW, and the record before S version n and before S's head; after NEW it checks that S version n and S's head are still its own. A copy aborted because O's head moved takes its own S head and version back (only while they carry its save id), so no standard-name key is left under OLD.

## The invariants

**I1 version continuity.** The copy is S version n; the next save under S is n+1. A standard name with nothing behind it starts at 1. Tests: `test_i1_the_first_store_keeps_the_old_head_version_and_saves_number_on`, `test_i1_a_fresh_standard_name_starts_at_1`.

**I2 below n, the old history.** A version pin S@k with k < n reads O version k, before and after the copy (receipts byte-identical, `alias_of: O` as before); k = n reads the same content (S's copy after the first store; no `alias_of`, its own `saved_at`); k > n reads S's own versions. Tests: `test_i2_a_version_pin_below_n_on_the_standard_name_reads_the_same_before_and_after`, `test_i2_a_version_pin_at_n_reads_the_same_content_and_above_n_the_own_history`.

**I3 the old name's history frozen.** A version pin O@k reads O's own version k before and after the copy (receipts byte-identical); `history(O)` is frozen; O takes no write from COPYING on and its keys are never written. Test: `test_i3_the_old_names_history_is_frozen_and_read_the_same`.

**I4 content pins.** A pin by `content_sha256` on either name searches S's chain once S is read from its own storage (S's own versions, then O's below n), before that O's chain, as v0.5.19. One digest finds one content, under the same version number before and after. Test: `test_i4_a_content_pin_finds_the_same_content_under_both_names`.

**I5 one chain.** `history(S)` after the copy: S's own versions from its head down to n, then O's below n, without gaps or repeats; v n carries `supersedes`. `history(O)`: O's own, frozen. Test: `test_i5_the_standard_names_history_is_one_chain_and_the_old_names_frozen`.

**I6 receipts number on.** No receipt restarts at 1. After the copy an unpinned O read answers with S's table and version: `evaluate_stored_table` `source.table` = S, `source.version` and `source.saved_at` S's, `source.read_as: O` added; `route_table_store` op `table` the same; `evaluate_decision` `trace.model_source` (and `.resources`) the same; `invoke_solution` `table` / `table_version` the same plus `read_as`. `content_sha256`, `status`, `result` are unchanged, and the version is the one O had. Downstream receipt and sidebar schemas must accept the standard name. Test: `test_i6_receipts_after_the_copy_carry_the_continued_version`.

Tests: `test_pre_migration_receipts_are_0519s_byte_for_byte`, `test_i7_before_any_first_store_every_receipt_is_0519s`, `test_i7_a_table_before_its_first_store_reads_as_0519_while_another_is_copied`, and the pre-copy tests of `test_v0520_store_name.py`.

**I14 forward only, no cache.** The state is asked of storage at every read and write; a failed read never makes NEW look OLD. Tests: `test_i14_the_read_only_old_name_is_asked_of_storage_at_every_write`, `test_i14_new_does_not_fall_back_to_old_when_a_read_fails`.

**I15 references.** `resource_table` / `route_tables` naming either name point to the same table before and after. A save names the referenced table's storage name now (the old name until that table's copy, then the standard name); a copy keeps its references as they are (part of its content). ## The write discipline (I18–I27)

Plugin storage has no transaction, and four writers touch the five tables: an old-name save, a standard-name save, the first store and the undo. Every one of them now follows the same rules.

**I18 the record carries an epoch.** COPYING, NEW, UNDOING and OLD each write epoch + 1 and the writer's id: a first store, an undo and the next first store give epochs 1, 2, 3, 4, 5, 6. Writers compare (state, epoch, owner), so a state that went away and came back is not taken for the same one. A save that saw one NEW and lands in the next (a save racing an undo and a new first store, which (c) excludes) is not answered 200: it is told that its version was written while the state changed to 「另一轮的 NEW」 and must be read back; the new round's record and copy are untouched (I20). Tests: `test_i18_the_epoch_grows_at_every_state_change_and_the_owner_names_the_writer`, `test_i18_a_save_that_saw_one_new_does_not_commit_into_a_later_one`.

**I19 re-check before the commit point.** Every save of the five re-reads the record before its version check, under the old name before the copy and under the standard name after it; if it is not what the save started from, the save writes nothing and fails (`STORED_TABLE_COPY_RACE` for an old-name save, `STORED_TABLE_IN_PROGRESS` otherwise, both saying the save did not take effect). From that check to its head a save of the five then makes exactly v0.5.19's storage calls, so a race between two saves has v0.5.19's windows (bar (b), measured per class below). A state change after the re-read is caught after the head (I20), and for a copy also by the copy's own re-reads of O's head (I11): that detection is weaker than a re-read right before the head, and (c) is what excludes those races (bar (b) is measured per class; the standard name is the everyday save path after the copy).

A version key that exists is refused `ROUTE_TABLE_STALE` under every name, exactly as v0.5.19 (T1). The only orphan left is a crash's between its version key and its head; as on v0.5.19, the next save of that table is then `ROUTE_TABLE_STALE`. The way out stays open: op `check` lists it; under an old name it must be reconciled against recorded pins and preserved snapshots before any cleanup; deletion is not a pin-preserving recovery (I22: the copy refuses while it is there); under a standard name the undo removes it with the first store (the table can then be copied again). Unpinned reads never read an orphan; a version pin on an old-name orphan reads it, as on v0.5.19 (which is why the copy refuses it, I22); a version pin above a standard name's head is missing (404 / `STORED_TABLE_VERSION_MISSING`). The first store re-reads before S version n and before S's head; the undo before the old head and before deleting S's head. Tests: `test_r6_a_save_makes_0519s_calls_from_its_version_check_to_its_head`, `test_r6_an_ordinary_save_crashed_at_any_write` (each write of a save, both crash modes, both names, five tables), `test_t1_*`, `test_r2_*`.

**I20 re-check after the commit point.** After its head, a save reads the record again: changed, it answers `STORED_TABLE_COPY_RACE` 「…已写入，但同时…首存状态变了：这一版可能被另一个操作覆盖或撤销，读回核对」; that re-read failing is 503 `STORED_TABLE_UNAVAILABLE` saying the version was written. A standard-name save that finds the table undone in the meantime deletes the head (and version) it wrote again, each only while it carries its save id, read again just before the delete, so no standard-name key is left for v0.5.19 to refuse. The first store checks after NEW that what NEW points at is still its own (else back to OLD, `STORED_TABLE_IN_PROGRESS`); the undo moves versions saved under S after UNDOING instead of deleting them. One operation at a time and at every crash point, every 200 is readable later; with two writers at once, see 「What is guaranteed」 (b).

**I21 conditional record writes.** The record is written only if it is still (state, epoch, owner) as read, then read back; the loser gets `STORED_TABLE_IN_PROGRESS`. Without a transaction a write can still land over a record changed between the read and the write; the writers detect that afterwards and repair it: a first store that finds a standard-name head whose save id its record does not know over a twin copy (S version n carrying the same `supersedes`: another first store of the same old version, then possibly saves after it) puts NEW back — under a fresh owner, so the restored mark never repeats an earlier one — and fails `STORED_TABLE_COPY_IN_PROGRESS`; any other unknown head or version key is a leftover (a save cut by an undo, an aborted copy) that the copy overwrites and never restores (T2); an undo that finds the copy it planned to undo completed puts NEW back and fails; an undo that finds another undo finished ends the same way. Tests: `test_i19_i20_i21_two_writers_interleaved_at_every_write` — ten writer pairs (old save / copy, copy / old save, copy / copy, S save / undo, undo / S save, undo / undo, S save / S save, old save / old save, undo / copy retry, copy retry / undo), the second run in full at every write of the first, for three tables (30 tests): afterwards the table reads by both names or an undo brings it back, every 200 is readable, of two first stores at most one copy is stored.

**I22 "the old name moved" is judged by its head; an orphan blocks the copy.** A version key above O's head (a save that died before its head) is an orphan: it does not move the old name or lock the table. But a pin S@k reads it through the alias before the copy (v0.5.19's reading), and after the copy the next save under S would give (S, k) a second content, breaking I1 / I2 (Codex review of v0.5.20). So a first store that starts from OLD refuses `STORED_TABLE_ORPHAN_VERSION` with nothing written, naming every O version key above O's head (probed up to `MAX_HISTORY` above it) as a crash leftover to preserve and reconcile with recorded pins before considering cleanup; op `check` lists them as `old_orphans`. The same first store sent again while it is under way (COPYING) is not checked again and converges (I10). The undo removes O orphans it finds. Tests: `test_i22_an_orphan_old_version_does_not_move_the_old_name_and_blocks_the_copy` (five tables: refused with nothing written, `check` lists it, after removal the copy succeeds and (S, n+1) has one content), `test_i22_a_copy_under_way_converges_without_the_orphan_check`, `test_a1_*`.

**I23 undo checks everything first.** It reads the record directly (not through the state check that locks the table, so every state can be undone; a record that does not read is rebuilt from what storage holds — the copy is the standard-name version carrying `supersedes` — and replaced only if its bytes are unchanged; refused `STORED_TABLE_ALIAS_COLLISION` when S has a head that is not over a copy of O's version, i.e. `supersedes` missing or not matching O version n's content: the v0.5.13 collision is never moved into the old name, T3), checks the expected version, that every S version from n up is there, that O did not move when there is something to move back, and that no partner table it must re-save (I24) has a version key above its head other than this undo's own fix (a crashed save's leftover: refused `ROUTE_TABLE_STALE` naming the key, nothing written; see the rollback procedure), and only then writes UNDOING. After UNDOING it reads S's head again (a save landed: back to NEW, `ROUTE_TABLE_STALE`). A read that loses its document because the undo deleted S's head asks again and reads O: never neither name; a key deleted between a read's `exist` and its `get` reads as absent (any other storage failure still raises). An undo of an OLD record (an aborted or undone first store) also deletes exactly the keys op `check` lists (T5). Tests: `test_i23_a_refused_undo_writes_no_key`, `test_i23_undo_works_from_every_state`.

**I24 after the undo, v0.5.19 reads (and saves) every table.** Moved resource versions list route tables by their old names (not part of `content_sha256`); the undo of the route table saves resource tables that list `triage.dispatch.route` again, and the undo of the resource table saves route tables that name `triage.dispatch.resource` again (as new versions: `resource_table` is part of a route table's content). Proved with c83caf1's source. Tests: `test_i24_undo_rewrites_heads_listing_the_standard_route_name`, `test_i24_after_undoing_both_every_head_is_one_0519_reads_and_saves`, `test_a11_route_undo_then_0519_cannot_read_the_resource_table_saved_meanwhile`. The re-save's save id is derived from the undo (its owner and the table): an undo crashed between that version key and its head finds the key when sent again, writes its head if it is the intended fix field by field, else takes it back and saves again; any other version key above the head stays v0.5.19's `ROUTE_TABLE_STALE` (review round 4; `test_review_r4.py`, `test_r8_*`).

**I25 the copy equals the old version field by field.** Every field but `table`, `note` and the identity (`version`, `saved_at`, `save_id`, `parent_save_id`, `content_sha256`, `supersedes`, `schema_transition`) must equal O version n's: a changed scene name, `route_tables`, declaration or gate report is refused `STORED_TABLE_MIGRATE_FIRST` naming the field. A copy of a gated old head keeps its `gate_report_sha256` without resending the report (same content, same gate; the report stays at the old name's gate key). Tests: `test_i25_the_copy_equals_the_old_version_field_by_field`, `test_a8_first_store_accepts_a_copy_that_is_not_the_old_version`.

**I26 no swallowed exceptions.** The table-parameter check answers 503 on a storage failure (not 「只读别名」); a failed check for the receipt warnings (I15, I22) is said in the receipt (`WARNINGS_UNCHECKED`). Tests: `test_i26_a_failed_check_after_a_save_is_said_in_the_receipt`, `test_i26_a_failed_state_read_on_the_table_parameter_is_503_not_read_only`, `test_a9_after_new_a_failed_state_read_is_reported_as_alias_read_only`, `test_a10_pre_copy_old_name_save_lands_but_is_answered_unavailable`.

**I27 content pins search two windows.** S's own last versions, then O's last versions (`MAX_HISTORY` each). Tests: `test_i27_a_content_pin_finds_the_standard_names_version_first_then_the_old_names`, `test_a7_old_content_pin_lost_after_s_grows_past_the_window`.

## What is guaranteed

**Known prerelease limits override broad invariant claims below.** The initial copy blocks old-name orphan versions only within its bounded scan. Deleting an orphan and then copying and saving can reuse a previously readable `(standard name, version)` pin for different content. `old_orphans` scans only through `MAX_HISTORY` (50) above the old-name head; `standard_keys` scans through 50 above the higher head of either name. COPYING retries do not recheck old-name orphans. An undo can remove orphan versions. Never use an empty `check` result as proof that all storage is clean. Preserve storage snapshots and pin receipts, inspect and reconcile orphan content before cleanup, and hold all table writers during migration and undo. This release does not resolve these cases.

Plugin storage has `get`, `set`, `exist` and `delete`: no transaction, no compare-and-set. So the guarantee has three parts, and only (a) is a proof.

**(a) One operation at a time, crashed at any write: every invariant holds (proved).** I1–I27 for each writer run alone, and crashed at each of its writes both before and after the write lands: the first store (52 crash points, I10), the undo (102, I17), an ordinary save under the old name before the copy and under the standard name after it (each write, 20 tests), plus reads, pins, listings, references and the rollback read by c83caf1's source.

**(b) Two writers at once: no path worse than v0.5.19 in any class (measured, not proved).** Two saves of one table from the same version are the only race v0.5.19 has. 10,000 random interleavings per path (every storage call a scheduling point, 2,000 per table, the outcome classes of the reviewer's `review_compare_0520_r3.py`; v0.5.19 run on its own source with the same seeds):

| outcome of two saves from version n | v0.5.19 (`c83caf1`), old name | v0.5.20, old name before the copy | v0.5.20, standard name after it |
|---|---|---|---|
| none of the classes below | 8376 | 8705 | 9106 |
| both answered 200, one of them not served | 770 | 651 | 431 |
| neither answered 200, the head serves one of them | 808 | 614 | 434 |
| one answered 200 and not served, the other (told it failed) served | 46 | 30 | 29 |

Every class on both paths is at or below v0.5.19's. Again with 10,000 schedules per table (50,000 per path): v0.5.19 41929 / 3779 / 4041 / 251, old name 43489 / 3122 / 3194 / 195, standard name 45697 / 2099 / 2057 / 147. Per table every cell is at or below v0.5.19's but one, the last class under the old name for `triage.supplement.requirements` (59 against 53 of 10,000, within sampling noise; that path makes v0.5.19's calls from its version check to its head). No case of T1's kind: the version-key guard runs under every name, so in every remaining case both saves passed it before either wrote, which is v0.5.19's own race. No new kind of failure between saves: the reviewer's explorer (`plugin/tests/explore_r3.py`) finds only v0.5.19's two save/save classes there (a head that is not its own version key; an acknowledged version replaced).

**(c) Concurrent writes to one table are excluded by operation, not by the plugin.** Each table has one writer at a time (a required single-writer discipline), and its writers are held (G-WRITE) during its first store and during every undo. A save racing an undo or a first store gets weaker detection than with the re-read right before its head (`22a9fe1`): its re-read is before its version check, so a change after it is only caught after its head (I20). Measured with the explorer and with a save against an undo followed by a new first store (9 pairings × 5 tables × 200 schedules, and 2,000):
- in these schedules no save was answered 200 for a write that was then lost, and no state was left that neither reads nor undoes;
- 43 of 2,000 save-against-undo-and-copy schedules end with the save told it failed (「已写入…读回核对」) while its content is served;
- 1 of 1,000 save/save/undo schedules leaves a standard-name head under OLD (a save whose head landed after the undo deleted S's head and whose re-read ran while the undo was still UNDOING); op `check` lists it and `undo` deletes it (T5), and the rollback procedure requires `check` to be empty.

The write hold is what excludes these races. v0.5.19 has no counterpart to the undo or the first store.

## Operator order

1. **Validate v0.5.20 in an isolated environment first.** Keep readers and writers on the old names until a migration is separately approved.
2. **Readers switch to the standard names**, one at a time, with replay validation and an available rollback version. Until a table's copy these are alias reads of the old table, with the same version numbers.
3. **Per table, after approval: the copy, then record `supersedes` in the migration ledger.** One writer per table at all times, and the table's writers held (G-WRITE) for the copy: this is part (c) of the guarantee; the plugin detects and repairs or reports races between writers (I19–I21, part (b)) but cannot prevent them without a transaction. First run op `check` on the table and expect it empty: `standard_keys` `[]` and `old_orphans` `[]` (an old-name orphan is a crash leftover: preserve it and reconcile its content and recorded pins before any cleanup; deletion can break pin continuity, and the copy is refused while the orphan remains (`STORED_TABLE_ORPHAN_VERSION`, I22)). Read O's head (version n, `content_sha256`); send it unchanged under S with `expected_version` n (`route_table_store` op `save`, table parameter empty, body = O's head without `version`, `saved_at`, `content_sha256`, `save_id`, `parent_save_id`, with `table` = S and a note); read back S version n, `supersedes`, the same `content_sha256`. If the call is interrupted, send the same request again. From then on that table is written under S only, numbering on from n+1. A racing old-name save is not lost silently (I11).
4. **After one release cycle with 0 old-name reads** in the run records and no `OLD_NAME_REFERENCE` warning left, a later version drops the aliases.

## Rollback

**Reinstalling the old plugin alone is not a data rollback.** After a first store the rollback is: hold the five tables' writes → `undo` every copied table → `check` each of the five, empty → reinstall v0.5.19. Validate storage states made by v0.5.20 against v0.5.19 as released (`3364027` source) in a separate process before relying on this procedure.
- **Why reinstalling alone is not enough after a first store.** v0.5.19's v0.5.13 check sees the standard name's keys: every standard-name read is refused `STORED_TABLE_ALIAS_COLLISION` (40 of the 80 reads), and an old-name route save is refused too (its same-state check reads the standard name the route index now lists). Old-name reads are unchanged. So the first bullet of I17 holds only with the undo below; nothing is weakened, a step is added.
- **The procedure:** on v0.5.20, under a write hold on the five tables (part (c)), run `route_table_store` op `undo` for every table that had a first store (table S, version = S's head version); then run op `check` for each of the five: every `standard_keys` and `old_orphans` must be `[]` (`check` probes S's head and every version key up to `MAX_HISTORY` (50) above the highest head of either name, T4; a key left behind: run `undo` again with the version its refusal names, which deletes exactly what `check` lists, T5); then reinstall v0.5.19. Undo all of them: v0.5.19 refuses a standard name whose keys are still there.
- **No write under S since the copy:** the undo deletes S's keys and the route index entry the copy added; its first record stays as OLD (v0.5.19 never reads it). Storage is then the storage before the copy plus those records, and v0.5.19 reads exactly as before (proved: all 80 reads and the route save equal).
- **Writes under S since the copy (head m > n):** versions n+1…m move to O under the same numbers, content and save ids (a resource table's `route_tables` with old names), then S's keys go; heads that would keep a standard name v0.5.19 refuses are saved again (I24). v0.5.19 then reads every table without a refusal and saves the route table (proved); every (name, version) that existed keeps its content, the old-name pins of the moved versions now exist, and the route table has one more version, written by the undo, whose content names `dispatch.resource`.
- `undo` is interruptible (crashed at every write in the tests: the same request again finishes it) and needs `storage.delete` (Dify plugin storage has it).
- *An undo refused because of a partner's leftover* (「撤销没有动手…是一次存表在版本键和头版之间中断留下的残留」, `ROUTE_TABLE_STALE`): a save of the partner table crashed between its version key and its head and left `route-table:<partner>:v<h+1>` above head h. The table is then exactly as v0.5.19 leaves it after such a crash: unpinned reads do not read that key, but old-name version pins can read it, and the partner's next save is `ROUTE_TABLE_STALE` too. Preserve and reconcile the orphan content, recorded pins and storage snapshot before any cleanup. Deleting this key can break pin continuity and is not a safe general recovery procedure. Test: `test_r8_a_crashed_partner_save_refuses_the_undo_up_front_and_writes_nothing`.

## Open points

- *The route copy keeps `resource_table: dispatch.resource`* (a route table's `content_sha256` covers it). It resolves either way; the I15 warning names it; the route table's next edit renames it, changing its `content_sha256` once without changing routing.
- *The table parameter before the copy.* v0.5.19 refused a save whose table parameter is a standard name; that refusal is kept, so the copy is sent with the parameter empty.
- *`route_table_store` op `undo` is not in the op list of the invalid-op refusal*, whose text stays v0.5.19's; the tool description names it.
- *Plugin storage has no transaction.* Races between writers are detected and repaired or reported (I19–I21), not prevented; see 「What is guaranteed」 (b) and (c).
- *Bar (b) is measured per class.* The standard-name re-read sits before the version check like the old name's; the price is the weaker detection of a save racing an undo or a first store, stated in (c) (with the re-read right before the head: 11 instead of 43 of 2,000 such schedules ended with the save told it failed and served, but under a standard name the class "one 200 not served, the other served" was 100 against v0.5.19's 46 per 10,000).
- *Undo writes versions.* Moving S's versions back and the I24 re-saves are writes under the old names (O's copied and lower versions are not touched).
