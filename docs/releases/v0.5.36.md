# v0.5.36: saves no longer stay blocked by a version left by crossing saves

Based on public v0.5.35 (`e74e36b`). This release keeps the existing storage keys, table formats, evaluation behavior and 1 GiB storage allowance. No table migration is required.

## Why

Plugin storage has no conditional write. When several saves of one table cross within seconds, a version that was answered as saved can be left above the head: a slower save writes the head last, so the head no longer points to the version below the leftover. v0.5.35 preserves such a version, as it should, but every later save then computes the leftover's version number, finds it taken and is refused. Nothing in the plugin could get the table out of that state.

## Changes

- **A save numbers past a leftover of crossing saves.** For tables other than the five delivery-chain tables, when the version number a save computes is taken, the save moves past it if all of these hold:
  - The head read is consistent: its own version-number copy is that save, is missing (the save writes it back first), or holds a sibling save of the same version and parent while the head's save-ID copy exists.
  - The version in the way names a parent, and that parent is not the head read.
  - That version has been stored for at least one hour.
  - At most three such versions are passed in one save.

  The passed version stays at its own number. It can still be read by version number, in history, by content-digest search and through `op=saved`. The new version's parent is the head read. The save's answer lists `skipped_versions` (number, save ID, parent and save time) and adds a `STORED_TABLE_VERSIONS_SKIPPED` warning.
- **Never passed:**
  - A version whose parent is the head read, even if it was answered as saved. It may be another save on the same head, or the real head behind a stale read; passing it would silently drop its changes from the new head.
  - Versions of the five delivery-chain tables.
  - The undo's reference-fix save, whose retries find it by version number.

  Ordinary saves, where the number is free, make the same storage calls as v0.5.35.
- **Cleanup keeps versions off the head's chain.** Cleanup follows the head's parent chain, and keeps following it past version numbers whose chain member is gone, so a version kept once stays kept through later cleanups. An old version that the chain passes over (one a later save moved past, or a sibling that wrote a chain member's number) is kept whole, with its version-number key, save-ID copy and records, and listed under `kept_off_chain`. `keep` now counts the head and the versions on its chain. Tables saved before parents were recorded are cleaned up as before.
- **History marks off-chain versions.** Entries for versions off the head's chain carry `off_chain: true`, for tables other than the five.
- **Storage calls and memory.** History and saves make the same storage calls as v0.5.35, except one check for a chain member's save-ID copy where its version key is gone or holds another save (at most once per save ID per call). A cleanup plan on a table with more versions than `keep` also reads the versions it keeps below the head (`keep` − 1 of them) to follow the chain, and looks one more number above the head. Only each version's save ID, parent, save time and size are kept in memory, as before.
- **Old versions are removed from the oldest up.** Cleanup stops at the first version that is not an hour old and keeps everything above it for the next run, so clock differences never leave a gap in the chain. A version without a readable save time is kept and does not stop the others.
- **Cleanup sees every number a save may write.** `usage` and cleanup look four version numbers above the head (one more than the three a save may move past), so a version written after moving past leftovers is never out of sight.
- **Clearer answers:**
  - A refusal because of a leftover that is not yet one hour old says when the save will move past it.
  - A refusal because the number is still taken, a read-back race, or a failed write after moving past says which versions were passed (`storage_failure.skipped_versions` for a failed write). Other refusals (gate report, callability) do not.
  - A refusal because the save can never move past the version in its way (more than three in a row, or a version that is unreadable or lacks a parent or save time) says so and points to `op=usage` instead of suggesting a retry. A version saved on the head read keeps the usual advice to reload and save again: it may simply be the next head.
  - Both incomplete-write answers now say to save again with the same content: saving different content while a timed-out write may still land would let that write replace the version.
  - The undo's refusal for a version in its way gives the remedy that works for that table: for the five, or for an undo already under way, the key must be removed in plugin storage; otherwise, one normal save moves past the leftover when it is a leftover of crossing saves at least an hour old and the head read is consistent, and the answer points to `op=usage` and cleanup for anything else.
- **Checks:**
  - `op=saved` refuses to hand back a copy that is not that save of this table.
  - A `confirm` entry must match both the version and the save ID, and this is now covered by a test.

## Safety boundary

This release is still intended for single-operator, serial maintenance. It does not add storage transactions, compare-and-swap, or a cross-process lock.

Moving past a version relies on the head read being current. If an earlier crossing left a foreign version above the real head and a replica keeps serving an older head for more than an hour, the save can move past the real head: that version stays at its number, but the new head does not carry its changes. This needs two anomalies at once and a stale read longer than the upstream five-minute cache.

Two saves that move past the same leftover at the same moment compute the same new number, like any two simultaneous saves: one write can land over the other, and the overwritten save remains only in its save-ID copy.

The one-hour waits assume the host behaves like the open-source plugin daemon (a shared read cache kept five minutes, delayed writes within ten minutes). If replicas keep separate read caches for longer than an hour, cleaning up old versions with a small `keep` can let a replica that still sees an old head write into a freed version number and overwrite the real head; v0.5.34 and v0.5.35 have the same exposure (v0.5.34 after ten minutes). Confirm the deployment's replica and cache layout before relying on cleanup.

In signed mode, the "answered as saved" protection relies on the record written after a successful answer; if that record could not be written, a stale plan may show the version as removable. The other protections (parent check, one-hour wait, explicit `confirm`) still apply.

Known limits carried over:

- A head write that fails for one of the five delivery-chain tables leaves a version key above its head that no plugin operation removes; that table refuses saves until the key is removed in plugin storage.
- Once the route table's standard name has been first stored and its references moved, the first store cannot be undone through `op=undo` in some states; the only way back is removing keys in plugin storage, as described in the v0.5.20 rollback notes.

See [storage care](../plugin-storage-care.md) for operation details.

## Upgrade and verification

1. Back up the relevant tables and record the installed plugin identifier, storage allowance and current table versions.
2. Upgrade from the GitHub release using the host's supported upgrade path. This publication does not itself install the plugin or change any production tables.
3. Verify the installed version and **plugin identifier** (not the version number alone), then read back table versions and compare representative evaluation results.
4. No table needs processing. A table that refused saves because of a leftover of crossing saves accepts the next save once the leftover is an hour old, if the head read is consistent and at most three such versions are in a row. Other blocked states stay as in v0.5.35 (see the storage-care known limits).

## Rollback

The stored formats remain compatible with v0.5.35 and v0.5.34. A table where a save moved past a leftover reads and saves normally on v0.5.35. On v0.5.35, a leftover not yet moved past blocks saves again. v0.5.35's cleanup does not know `kept_off_chain`: with `keep` below a passed version it deletes that version like any old version, including its save-ID copy, so do not run cleanup with a small `keep` on such tables after rollback.
