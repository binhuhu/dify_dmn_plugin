# v0.5.24: signed draft and publish

This release is limited to one human operator performing serial maintenance.
Signatures, expiry checks and sequential replay protection remain in place.
Cross-process concurrent replay and concurrent writes can still succeed and overwrite
state; this release does not add a coordinator or promise atomicity. A single operator
reduces ordinary editing conflicts but does not eliminate malicious or accidental
concurrent replay. Target-host installation/upgrade, real business API integration and
production acceptance remain **NOT_RUN**. Publication is not deployment acceptance.
This release changes writer behavior and governance; it is
not a behavior-neutral privacy cleanup. CURRENT v3 solutions still require the existing
request contract, topics and intents. The later topic-list relaxation is not included.

## Scope and storage

The five delivery-chain tables are `target.scene.entity`, `triage.scene.acceptance`,
`triage.supplement.requirements`, `triage.dispatch.route`, `triage.dispatch.resource`,
and their existing legacy aliases. Their live documents retain the previous storage
keys, format and numbering. Drafts and publish records use separate keys; readers do
not read them. Reader compatibility is tested against the public v0.5.23 runtime.

Each table has one server-side draft shared by all writers and by its old and standard
names, not independent per-writer drafts. A draft records the
request body, prepared document, predicted version, content digest, base version and
save ID, writer, and timestamp. A publish record records the publisher, draft writer,
release reference, gate-report digest and reported before/after invariants.

## Writer protocol

- Direct `save` of the five tables is refused with `STORED_TABLE_PUBLISH_REQUIRED`.
- `draft_save`, `draft_discard`, `publish`, and `undo` require a signed request from the
  pinned maintenance application. The immutable application pin remains intentional
  executable configuration in `dmn_client/two_state.py`; it is not a credential and
  has not been replaced as part of privacy cleanup. Another maintenance app requires
  a separately reviewed application release.
- The maintenance node supplies the writer registry. Another app cannot supply its
  own registry to authorize these writes. `op=writers` reports pin/caller information
  and exposes registry identifiers only to the pinned caller; it never returns keys.
- Writers sign the operation, table, version, RFC 8785 body digest excluding `writer`,
  writer ID and UTC timestamp using their own HMAC-SHA256 key. Timestamps must fall
  within the allowed ten-minute window. Signing keys are not sent in requests.
- A `draft_save` must match `expected_draft` and the live base. A rollback draft uses
  `from_version` with the supported rollback request keys; arbitrary extra content
  keys are refused rather than silently ignored.
- A publish must name the current draft and unchanged live base, supply a nonempty
  `release_ref`, and provide a matching gate-report content digest. A FAIL report
  requires an approval reference. The plugin validates the reference shape; this
  does not by itself authenticate an external approval authority.
- Publish re-runs the existing live-save validation and callability gate. The
  documented callability invariants in the publish record are informational, not a
  replacement for that gate. References from these tables must stay within the five.

## Replay prevention and retries

Version and draft checks alone did not prevent a discarded draft from being restored
by a replayed, still-fresh signed request. Signed mutations now claim a persistent
request-digest marker before their first real storage mutation. The marker contains
request identity and status, not a signing key or raw signature. With durable, coherent
storage, a retained pending or completed claim consumes that request for sequential
requests and requests coordinated by the same process. The identical request is then
refused. This is not a cross-process replay guarantee: an independent-process test
reproduced a delayed request overwriting a completed receipt and recreating a discarded
draft. That race is still unresolved.

Validation failures before any mutation do not consume a claim. After a mutation is
attempted, the confirmed pending marker is retained even if the operation reports an
error; it does not authorize retrying the old signed request. If the operation reports
success but finalizing the marker fails, the response includes `operation_applied` and
`applied_result`. Other error responses do not establish that nothing was written.

The release's replay and recovery checks have been exercised against synthetic
storage backends only. The deployed daemon version and its cache, durability and error
semantics have not been accepted. In the public upstream daemon at
[commit 14d7148](https://github.com/langgenius/dify-plugin-daemon/blob/14d714820d475075e15bd8dae605d61298382213/internal/core/persistence/persistence.go#L57),
`Save` writes the backing store before quota/accounting checks and cache invalidation.
It can therefore save a value and then return an error while leaving an older cached
value. `Load` consults the cache first. This source does not establish which daemon
version is deployed or that a production fault has occurred. An owner/readback match
through ordinary `get`, or the absence of `published_anyway`, cannot prove that a
write did not occur or that the returned state is authoritative and current.

After a storage error or uncertain outcome, a fresh signature is appropriate only
after authoritative, current state has been established. If that cannot be established,
stop and await operator verification; do not automatically retry, overwrite or delete
based on an ordinary cached read. This release has no verified authoritative-read or
recovery mechanism for this host boundary.

These markers are independent of drafts/live history, so deleting a draft, undoing,
or restarting does not itself remove them. There is no automatic marker
cleanup with the present storage API; storage growth must be monitored operationally.
Requests completed before this mechanism was enabled have no backfilled claim. A
cutover must account for any previously issued signatures still within their validity
window; enabling this code does not retroactively consume them.

The in-process lock and readback checks are not cross-process CAS. **One human operator
must perform maintenance serially across the entire workspace, covering all mutations,
including draft saves/discards, publication and undo.** Wait for each outcome to be
resolved before starting the next operation; do not run parallel browser tabs, scripts
or automated writers. This is an operational restriction, not enforced mutual exclusion.
A deployment may still use multiple processes: this release does not make those
processes concurrency-safe, and concurrent replay can bypass the operator discipline.
Cross-process coordination is outside this limited release; neither serial operation
nor a single operator validates the storage and recovery semantics above.

## Editor and vocabulary

The shared editor key is retired. The editor stores the writer ID and key only in its
browser tab session storage and uses WebCrypto to sign requests. The endpoint forwards
requests to the configured maintenance application; without it the API fails closed
with `ROUTE_STORE_APP_REQUIRED`. It no longer has an independent storage write path.

The editor can read live/history/version/draft/vocabulary, save or discard drafts, and
publish with a gate report and release reference. Clients must update to this protocol.

`op=vocabulary` exposes the declared closed value sets, row shapes and table names used
by validators. Unknown top-level keys are refused for the five tables. Other tables
retain their direct-save behavior but return a warning naming dropped keys. The
vocabulary is code-defined; a mutable stored vocabulary is not part of this release.

## Installation and rollback

1. Assign one human operator and establish serial maintenance across the workspace,
   including all tools and automated writers. Account for outstanding signatures at
   cutover as described above; do not treat this discipline as cross-process protection.
2. Configure the approved maintenance app and writer registry through the authorized
   deployment procedure. Verify the platform supplies the correct caller application
   ID. A missing/incorrect caller ID must leave signed writes disabled.
3. Update every editor, script and workflow writer to sign and use draft/publish.
   Keep maintenance serial under the operating restriction above. The plugin cannot
   verify or enforce that restriction; a configured writer registry and matching caller
   identity can enable writes without it.
4. Independently validate deployment permissions, key handling and exports. A node
   editor may see signing keys; do not publish workflow exports containing them.
5. Rollback is reinstalling v0.5.23. Existing live table formats remain readable;
   drafts, publish records and replay markers are ignored by that version.
   **Editing returns to the shared-edit-key governance of v0.5.23**: restore the old
   endpoint setting as required, and direct saves become possible again. Downgrade
   does not preserve v0.5.24's signed-writer or replay protections.

A write interrupted between version and head can leave an orphan version requiring
operator recovery. Reference checks do not retroactively repair already stored tables.
The storage API does not offer transactional rollback or compare-and-swap; do not
advertise this release as providing either.

## Privacy and verification scope

Personal quotations, internal operational notes and redundant deployment identifiers
have been removed from this release. Production-readback test fixtures are replaced
by independently authored toy models. The routing fixture checks two artificial routes
and no-match behavior against a separately authored expected model. The decision model
checks FIRST ordering, quality/missing-input handling, numeric boundaries, boolean and
string branches, validation refusals, and stored-tool receipts. It does not claim to
validate a private production policy or replay a production incident.

The pre-migration receipt golden is independently reproducible with public v0.5.19;
rollback tests use pinned public tags rather than private local worktrees. Test results
and CI conclusions must be reported from the final clean release tree, not copied from
an earlier build. A new clean tree does not erase old public commits, tags,
release descriptions, source archives or previously distributed installation assets.
Any historical removal remains a separate decision.
