# v0.5.19

This release builds on v0.5.18 (`19dd547`). Existing valid legacy and TRANSITION fixtures retain their recorded save receipts and evaluation results. STANDARD save checks are expanded. Name/role checks apply to declarations at both stages; model source checks apply wherever `from_table` is present, including tables without declarations. Publication does not install the plugin or change stored tables.

**Rules (第 10 条).**
- A rule's `when_any` takes up to 128 condition combinations (was 32), each still 1–32 conditions; a table still fits in 512 KiB.

**Save checks for STANDARD decision tables (第 5、8、11、12、13、23 条).**
- PENDING and UNKNOWN templates carry `result.gap`. A gap is `{code, owner, kind, field_id?}` with `owner` OPERATOR / CUSTOMER / SYSTEM / AUTHOR and `kind` FACT / ENTITY / CONFIRM / RULE (AUTHOR and RULE are new: the input is complete but no rule covers it), or a list of them, one per association group, each may add `any_of`, `min_satisfied`, `blocking`, `assoc_id`. A gap is checked wherever it is written.
- `DISPOSAL_STATUS` templates write no `gap`: the status table gives `outcome` + `reason_code`, and the shared node sums the upstream gaps as they are.
- Each item of `result.actions` is exactly `{code, capability_id, executor, money}`: `executor` SYSTEM / AGENT, `money` null or `{amount_rule_id}`. The template's own `actions` stays `[]`.
- Every template but the no-match one writes the role's business keys (null when there is no value): acceptance `decision` + `reason_code`, feature `feature_id` + `value`, reality `reality_id`, disposal `disposal_id`, disposal status `outcome` + `reason_code`, scene entity all six keys. A missing key is reported before a repeated conclusion.
- A declared parameter may give `unit` (its stored unit, up to 32 characters).
- A text with a `{槽位}` (customer sentence or segments, agent, by channel) needs `texts.slots` listing it, whether or not the table declared slots before.
- A feature table never uses FAIL: a negative feature is PASS with its value.
- A FIRST table may give one conclusion in a second rule only as the ordered exception: its row writes `split_of` (the conclusion's first rule) and `split_reason`, and between it and the previous rule of that conclusion stands a rule of another conclusion that may hold together with it. Adjacent or non-overlapping rules are one rule (`when_any`); UNIQUE and COLLECT tables get no exception.
- A declaration on a `solution.*` table has the role of its name segment: `fact.feature` FACT_FEATURE, `feature.reality` FEATURE_REALITY, `disposal.strategy` DISPOSAL, `disposal.status` DISPOSAL_STATUS. This one is checked for TRANSITION declarations too.

**Realities that hold together (第 3 条).**
- A STANDARD reality table may declare `coexist`: groups of `reality_id` that may hold together, each id one of `outputs.reality_id.values`. It is part of the declaration, not of `content_sha256`.
- Save warnings (yellow, never a refusal) on a COLLECT reality table: `EXIT_REALITY_MAY_COEXIST` lists the exit rules (`kind = EXIT`) and reality rules that may hold together; `REALITIES_MAY_COEXIST_UNDECLARED` lists two reality rules that may hold together but no `coexist` group lists both. Up to 100 pairs each, then `pairs_truncated`. Detailed overlap comparisons share a 4096-check budget with cached finite domains. On exhaustion, unresolved pairs stay possible overlaps and warnings include `overlap_analysis_limited`; no warning is silently suppressed. This only bounds warning analysis, not the exact FIRST split validation.

**Table name (第 14 条).**
- `solution.disposal.status.shared` names one disposal status table several scenes share. Only for `disposal.status`, without `.<part>`.

**Stored evaluation checks the receipt's table.**
- A `table` parameter may carry `from_table` in the model: the one table whose receipt it takes. It is part of the model, so of `content_sha256`: one content digest always means one execution rule, also for a pin by content digest alone. Evaluation reads no declaration.
- At stored evaluation the chained receipt must come from `from_table` (read aliases count as their stored name); otherwise the call is FAILED with `INPUT_SOURCE_MISMATCH`. The table a receipt names is its `source.table`, or, for an upstream call that did not get that far, its `table`. A receipt that names no table (an upstream table that was not requested) is a missing parameter, as before. A parameter without `from_table` is not checked, as in v0.5.18.
- Saving: when a declaration gives the parameter's `source` as `table:<name>` and the model has `from_table`, the two name the same table; a STANDARD declaration with a `table:` source needs `from_table` in the model. `from_table` on a parameter that is not `table` is refused.
- `content_sha256` includes model `from_table`, but excludes declarations. Changing or dropping only a declaration cannot alter evaluation. Hash-only pins continue resolving to the newest retained version with that hash; changing `from_table` changes the hash. Version-plus-hash pins still select the immutable version and verify its content. No new digest format is introduced.
- Direct table and decision-set evaluators derive constraints from their models. A legacy auxiliary source map cannot override them. Failed receipts prefer a string `source.table`, falling back to the requested `table` only when no string source name is available. Successful chained receipts require a positive integer storage version, a nonempty model reference and a 1–64-character state. Source names cannot contain whitespace. Unknown and missing upstream data preserve three-valued semantics and are never silently converted into known values or a positive match.
- Solution invocation ignores declarations at runtime while preserving registered app, input, status and gate checks. Save-time declaration validation remains in effect. This hardens an existing path, rather than changing route authorization.

**Inline evaluation takes `when_any` (第 15、22 条).**
- `evaluate_decision` accepts rules with `when_any` (the plugin's DSL schema now takes `when` or `when_any`), joined by the stored tables' three-valued or, with the same limits. Its output is otherwise unchanged: no `rule_id` fill, no `decisions`, no `selected_combinations`. Before, a `when_any` rule was refused or raised `KeyError 'when'`.

Checks: `plugin/tests/test_v0519_review27.py` and release guards cover the new behavior and frozen legacy receipts. The runtime schema extension is documented in [runtime-schema-v0.5.19.md](../runtime-schema-v0.5.19.md); the fixed upstream snapshot is unchanged. Not included: viewer changes (第 24 条, the structure-viewer plugin), standard outputs for supplement, route and resource tables.

**Compatibility and downgrade boundary.** Models using `from_table` and rules exceeding 32 `when_any` combinations are not accepted by v0.5.18. The inline `when_any` extension also needs a v0.5.19-aware runtime schema. Keep an application backup and retain earlier compatible table versions before upgrading; installing an older plugin does not migrate newer table content. No database restore or live migration is performed by this release.
