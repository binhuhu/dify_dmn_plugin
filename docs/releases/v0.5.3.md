# v0.5.3（候选，未打包、未发布、未装机）

WO-29（分诊 TRIAGE 0f34962a，release D）要的插件侧改动（迁移设计 S5a）。基于 main `305bc91`（v0.5.2 tag 位）。

| 改了什么 | 为什么 |
|---|---|
| 插件存储多收三种表，与 `dispatch.route` 同一套保存 / 读取 / 历史 / CAS（`dmn_client/stored_tables.py`）：`decision-table/v1`（表名 `p2.<方案应用编号>`，一张 service-decision-table-v1 模型，字面量结果、无动作）、`supplement-requirements/v1`（表名 `supplement.*`，按场景 NONE / REQUIRED〔补充项带 prompt_key〕/ UNDECLARED〔带缺口码〕；没列的场景读作 UNDECLARED / SUPPLEMENT_UNDECLARED，不当 NONE）、`resource-targets/v1`（表名 `*.resource`，自助 / 人工 / 专组 / 安全目标，入口未定的标 TO_CONFIRM） | 10-28 裁定：P2 表定义归方案、在分诊内求值；R-3 补充要求表；R-4 资源路由目标表 |
| 新工具 `evaluate_stored_table`（第 8 个内置工具）：按运行时给的表名读一张存储表——受理表求值（命中策略、逐规则轨迹、字面量结果；`missing: UNKNOWN` 时未给的参数按 UNKNOWN 补，由表自己的规则决定）、补充要求表答一个场景、资源目标表答一个目标；结果信封总会返回（SUCCEEDED / NOT_REQUESTED / NOT_FOUND / BLOCKED / FAILED） | 受理表按路由到的方案动态选表，`evaluate_decision` 的定义包是固定配置 |
| 路由表 v2 文档可以有资源去向 `{"kind": "RESOURCE", "resource_id"}`，同时写 `resource_table`；保存时先要有资源目标表、编号要在表里、资源目标表的 `route_tables` 要列出这张路由表；资源目标表不能删掉路由表还在用的目标 | 一张路由表（单一来源）同时管方案路由和资源路由 |
| 存根格式 `routing-table/v3`（分诊 release D 用）：编译全部行，模板多五个字段（resource_id / kind / name / entry_json / status），旧的 TRANSFER→SAFETY 行读作 entry 为 TRANSFER SAFETY 的那个目标；模型来源另记资源目标表的版本。旧存根 `routing-table/v2` 编译时**略过** RESOURCE 行，现网 DISPATCH 读到的模型与 0.5.2 逐字相同 | 新行对旧读者不可见；没有 `resource_table` 的文档存储形态与内容摘要不变 |
| 路由表不能用 `p2.*` / `supplement.*` / `*.resource` 这些名字；同一张表不能换存另一种表格式（路由表 v1→v2 照旧允许） | 防止表名与格式错配 |

## 回滚

- 只回插件（存储里只有新表、路由表没有 RESOURCE 行）：旧版不读 `p2.*`、`supplement.*`、`*.resource`，无副作用。
- 路由表一旦存进 RESOURCE 行：先在编辑页把路由表存回上一版（不含 RESOURCE 行与 resource_table），再回插件；0.5.2 遇到 RESOURCE 行会报 `ROUTE_TABLE_TARGET`，所有读路由表的流程都会失败。
