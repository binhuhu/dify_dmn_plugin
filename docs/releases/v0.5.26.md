# v0.5.26: writer key fingerprint in op=writers

This release builds on v0.5.25 and keeps its scope and limits (single operator, serial
maintenance; see [v0.5.25](v0.5.25.md) and [v0.5.24](v0.5.24.md)). Target-host
installation/upgrade, real business API integration and production acceptance remain
**NOT_RUN**. Publication is not deployment acceptance.

## What changes

- `op=writers` now lists, for the pinned maintenance application only, a `key_fp` for each
  registered writer: the first 12 hex characters of `sha256("dmn-writer-fp/1\n" + key)`.
  It is a one-way tag, not a key; it cannot be used to sign. Other callers still see no
  registry and no tags.
- Writer keys must be random (for example `secrets.token_urlsafe(32)`), never a chosen
  passphrase: the tag is a fast, unsalted hash, so anyone who can run the maintenance
  application could test guesses against a human-chosen key offline.
- `scripts/sign-store-request.py --fingerprint` prints the `key_fp` of `DMN_WRITER_KEY`
  (and nothing else), so a signer can compare it with `op=writers` before signing.
- Signing, verification, request keys, storage keys and formats, reads, evaluation and every
  refusal are unchanged.

## Why

The host may cache the decrypted secret-input settings of a workflow tool node per node.
When the writer registry of the maintenance application is edited and the application is
republished, runs can keep receiving the previous registry for a while. A writer then signs
with the new key while the plugin verifies with the old one, and every signed request is
refused as `STORED_TABLE_WRITER_REJECTED`, which looks the same as a wrong key. With
`key_fp`, the difference is visible: if `op=writers` shows a different tag than
`--fingerprint`, the plugin is not holding the key being used.

Operational notes:

- After changing the `writers` setting, read `op=writers` and compare `key_fp` before the
  first signed write.
- If the tag is stale, either wait until the host's cache expires, or republish the
  maintenance application with the store node under a new node id (the cache is per node).
  Both are host-side; the plugin does not and cannot clear the host cache.

## Installation and rollback

- Install after v0.5.25; nothing else changes. Rollback to v0.5.25 only removes `key_fp`.

## Verification

- `test_v0526_writer_fingerprint.py`: tag shape and definition; tags shown only to the
  pinned application and never the key; a stale registry shows a different tag and rejects
  the new key; `sign-store-request.py --fingerprint` prints the same tag.
- Version pins moved to 0.5.26.
