## 一、改了什么

### 1. 场景与话题表外部键（0.5.45）

行上可多一格 `external_keys: {question_trees: [...], smart_qids: [...]}`，两样都只放号（字符串，问题树号 4–5 位、智能 qid 7–8 位），不重复；
工单标题三级不进表，按问题树号经桥表现推。不带这一格的行、不带这一格的表，存、读、摘要逐字节同 rc4。拒存文案逐字节守旧版。

### 2. 候选筛选格存前核

存场景关联实体表时，每个结论的 `candidate_filter` 按合同 `$defs/candidate_filter` 核形状与上限（上限从 `dmn_client/chain_limits.py` 读，
它是合同生成件的原样拷贝，不手改）；条件里的原值号必须在能力表头版、这个结论的对象种类那几行上，`states.in` 的值照那个原值的类型。
写坏了拒 `CANDIDATE_FILTER_INVALID`。时间窗只用时刻原值那一核从 0.5.47 起（等能力表第 8 版标出时刻，第 6 节）。

### 3. 资源去向表终形

带 `resource_id` 参数的旧形照旧核。不带的按终形核：参数只收 `route_target`（`SOLUTION_APP` / `NO_FLOW`）、`scene_status`、`scene_id`、
`issue_type`、`phase`、`channel`。知识去向的题不读资源去向表（2.0.97）。

### 4. 「要什么对象」三级两格

`issue_type_objects {问题类型: 对象}`、`topic_objects {话题: 对象}`，都写成 literal；值只收能力表头版的结果实体种类，或词表值 `KNOWLEDGE` / `NONE`；
`topic_objects` 的键必须是这个结论的规则所列场景的话题（读场景与话题表头版），至多 `TOPIC_OPTIONS_MAX` 个。不写这两格的表照旧。

### 5. 品类表结论键、时刻类型、场景号业务模式段

- `CONCLUSION_KEYS["BUSINESS_MODE"] = ("mode", "product_type")`：同一结论只写一条规则，出行一个模式的几个品类是几个结论。现网第 1、2 版照样过。
- 能力表原值类型末尾加 `datetime`（`YYYY-MM-DD HH:MM:SS`，北京时间，到秒）。旧六种原样、次序不变。
- `M_` 是出行的业务模式段：只有整串没有业务模式段的 `P_` / `D_` / `H_` 号读成 `M_`；`HY_` / `JR_` / `NY_` / `LL_` 原样、不和 `M_` 号等同（代码早就这样，这次加用例钉住）。

### 6. 路由表终形闸与 `retire_solutions`

- 路由表 v3 有头版的存表：资源去向、转接去向（以场景·类型·阶段 + 去向整体比）与表头 `resource_table`，头版有的可以留、可以删，不能新加，
  拒 `ROUTE_TABLE_TARGET_RETIRED`。排在 0.5.45 给的全部拒存之后（它们的码与次序不变）、调用方的闸之前。首存不比。
- 降方案：删掉一行原来能调的方案行，请求带 `retire_solutions: [{scene_id, issue_type, phase}, ...]`。每一项必须是头版里真有的方案行、
  这次真删了；不许通配、不许只写场景块、不许重复、格不多不少；首存（含标准名首存）不收。写错拒 `ROUTE_TABLE_RETIRE_INVALID`，路径指到那一项。
  没列的照旧 `ROUTE_TABLE_SOLUTION_LOST`。
- 这份清单（场景号照 `M_` 记）随存表结果回 `retired_solutions`、记在那一版上（插件自有字段，载回再存不当请求重核）、
  进那一版的 `op=ledger` 行。草稿 → 发布一路带着。回滚不带走它。
- 回滚窗（`RESTORE_WINDOW` = 3）内的回滚带回头版删掉的转接、资源行或绑定：只报不拦（`RESTORE_RELAXED` 加 `ROUTE_TABLE_TARGET_RETIRED`）。
