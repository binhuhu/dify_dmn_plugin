- 起因：按号取的写法每读一个号先问它已知，护栏也算条件，32 只够十几个业务条件；本地 1347 份表里 8 种情形正好 32 条、62 种在 28 条以上。
  留一个数、不交给 1 MiB：挡住机器转出来、人读不了的大情形。
- 实测：同体积的表一种情形 32 条和 128 条，存表与求值耗时无差（求值中位数 120–135 毫秒）。
- 放宽面：只放宽，原来收的表照收、摘要不变；原来因为 33–128 条被拒的表现在收。DMN XML 导入：一格 1024 种 × 几百列的那种表，

## 九、三级资源去向表的可空资源编号（协调定 370 ②、定 371）

- 合同里 `route.resource_id` 可以是 `null`（带 `resource_id_note`）；rc2 以前的资源去向表声明写不出可空，入参 `null` 进不到规则。
- DMN 2.0 §五 RESOURCE 的 K 规则只放开「可空」一项：`resource_id` 仍 string、仍必有、仍只收 KNOWN（空是「已知没有编号」）。可空的表另有：
  - 每条规则（`when_any` 的每种组合）都写一条资源编号条件，只许 `eq` / `in` 比具体的非空编号，或「为空」`is_null: true`；
    `ne`、`exists`、`is_null: false`、比大小、`in` 里带 `null`、写在质量上的都拒；一种组合里资源编号条件只许一条；
  - 不收 `when: []` 的通配行：拼错或没登记的非空编号照旧 `NO_MATCH`，错露出来；
  - 「为空」有且只有一处（单独一行，或某条规则 `when_any` 里的一种组合），**而且那一种组合只能写这一条条件**〔复核后加，见第十三节〕。
- 不可空的表（今天所有表）校验、求值、内容摘要同 0.5.43（5 个金样）；只有拒绝说法改了一处：「string，必有，不可空，只收 KNOWN」→
  「string，必有，只收 KNOWN；可空写 nullable: true」，码与位置不变。

### 新增：情形概述（2.0.88，合同线 f4cee5075）

一条规则有几种情形时，声明 `rows.<rule_id>.cases` 逐种情形写一句依据：`{why, case_sha256?}`。

- **存表核**：
  - 只收不止一种情形的规则：v1 的 `when`、v2 只有一种情形的规则写了 cases 就拒；
  - 条数等于情形数；
  - why 1–300 字；
  - `case_sha256` 是 64 位小写十六进制。
- **标黄**：`case_sha256` 和那种情形条件的摘要对不上时，报 `CASE_WHY_STALE`「情形改过，依据待重新确认」，不拒。
- **老表**：不写 cases 照收，不标黄。
- **不进内容摘要，求值不读**：带与不带 cases，决策本体和 `content_sha256` 逐字节同；改 why，摘要也不变。
- **DMN XML 导出**：
  - 一种情形一行 `<rule>`，description 写那种情形的依据，没写就写规则依据；
  - 一条规则合成一行导出时，写规则依据；
  - 带依据的 rule 标 `dj:why="declare"`，导入不回读（v1 标准形状原来会把 description 读成说明）。
  - 0.5.42 金样里十张真表的导出因此不同；去掉声明再导，与 0.5.41 金样逐字节同。
- `op=v2_vocabulary` 的声明一节加了 `row_keys`（含 cases）和 `case_keys`。
- 查看页 `plugin/viewer_static` 只画条件原 JSON，不画规则依据，所以不动。
