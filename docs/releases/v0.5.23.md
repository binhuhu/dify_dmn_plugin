# v0.5.23

Historical version record. Test counts and validation status below describe that version, not the current review branch or a current deployment.

**Prerelease candidate. Production compatibility has not been accepted.** On top of v0.5.22 this version adds a **callability gate on route-table saves**. It prevents a route update from replacing a callable solution with a non-callable registration without an explicit fallback.

**Not additive.** Saves that v0.5.22 stored can now be refused (below). Reads, evaluation and `invoke_solution` are unchanged. Every refusal v0.5.22 gives keeps its code, message, path and order: the gate runs after all of them, just before the caller's own gate. A save that is not a v3 route table is untouched.

## The gate

A v3 route-table save is compared with the v3 version it replaces. If it leaves the table **less callable**, the whole save is refused and nothing is written. Refused, in this order:

- **`ROUTE_TABLE_SOLUTION_NOT_CALLABLE`** at `routes[i].target.app_id` (the row as sent): a `SOLUTION_APP` row newly points at an app that is not `CURRENT`, or the app it points at is no longer `CURRENT`. The message names the row (scene shown as `M_…`), the app and its status, and says how to do it right: make the new app `CURRENT` in the same save, or park the row on a transfer or resource target.
- **`ROUTE_TABLE_SOLUTION_LOST`** at `routes`: a row whose solution was callable is gone and the key has no target at all. A transfer or resource target in its place is an explicit fallback and passes.
- **`ROUTE_TABLE_CURRENT_UNROUTED`** at `solutions.<app>.status`: a `CURRENT` app that some row named before is named by no row now. Step it down (`CANDIDATE` / `RETIRED`) in the same save. A `CURRENT` app no row named before (a new registration, or one promoted ahead of its rows) is left alone.

**Only worse is refused.** What the replaced version already had is left alone: a row already parked on a `GATED` / `SHADOW` / `CANDIDATE` app, a `CURRENT` app already without a row. So unrelated saves pass, and so does the save that repairs things. Rows are compared on the legacy spelling of the scene id, so a save that only respells `P_xx` as `M_P_xx` changes no row.

**Not compared:** the first v3 store (from v2 or nothing), and a first store under a standard name, which copies the old head unchanged and so cannot change callability.

`route_callability(doc)` and `callability_gate(prev, clean, sent)` are in `dmn_client/route_table.py`; the save path calls the gate after every earlier refusal and before the caller's gate. It reads only the head being replaced, does not add cross-table checks.

## Known limits

- **Callable means `CURRENT`.** The gate does not check that delivery can build the app's `request_contract` (for example, v4 / v4.2), that the app's published Start matches `inputs`, or that the app exists. Those require separate caller-contract and deployment checks.
- **No explicit "parked" marker.** A parked row is a row on a non-`CURRENT` app; there is no field saying why or where it falls back. A parked row's app can change status between non-`CURRENT` states, but repointing it to another non-callable app is refused.
- **One table at a time.** The gate compares this table with its own previous version. An app's status across route tables is still `_one_state`'s check.
- **A new key on a parked app is refused.** A row added on a key that had no row, pointing at an app that is not `CURRENT` (even one already parked elsewhere), is refused `ROUTE_TABLE_SOLUTION_NOT_CALLABLE`: a new parked row would carry no reason or fallback. Park a new key on a transfer or resource target instead.
- **An app in two route tables:** moving its last row in one table to a fallback gives `ROUTE_TABLE_CURRENT_UNROUTED`, and stepping it down there gives `ROUTE_TABLE_SOLUTION_STATUS_CONFLICT` (`_one_state`). Remove it from this table's registry instead.
- **Emergency path:** closing a gate again on a routed app (`CURRENT` → `GATED`), or rolling back to a version stored before a gate was opened, now needs a transfer or resource fallback for that app's rows in the same save.
- **Topics, intents and request contract are not checked.** Rewriting a routed `CURRENT` app's `topics` / `intents` passes the gate, even when a caller uses those lists to decide applicability; so does a `request_contract` delivery cannot build.
- **Ids with surrounding whitespace:** validation still accepts an app id or scene id with a trailing newline (`UUID_RE` / `SCENE_RE` use `match`, unchanged from v0.5.22). A solution row that names such an id is never callable to the gate, whichever way the twin points: the routing result reads the exact id while `invoke_solution` strips it, so the two would read different entries. Refusing those ids at validation (`fullmatch`) is left to the next version, since it would change v0.5.22's refusals. The same looseness lets a row on a padded scene key (`"P_02_04_01\n"`, and likely a padded issue type or phase) keep an app counted as named, so `ROUTE_TABLE_CURRENT_UNROUTED` does not fire while the real key has moved to an explicit fallback (the scene retains an explicit target).
- **Same race window as before:** the gate reads the stored head, then writes; plugin storage has no compare-and-set (the stale and version-key checks are unchanged).

## Evidence

- **Tests:** 2523 passed, 101 skipped, 0 failed (v0.5.22: 2503 / 101). The new tests are in `test_v0523_callability_gate.py` (20): a save pointing a route at a candidate app is refused (also respelled with `M_`, path naming the row as sent); a complete replacement in one save passes; a half replacement, a demotion, a removal, a parking that leaves the app `CURRENT`, and a repoint of a parked row to another non-callable app are refused; parking with a transfer fallback and the app stepped down, an unrelated save, the repair, the promotion from the broken state, and an `M_` respelling pass.
- **One earlier test adapted, intent kept:** `test_v0520_invariants.py::test_i17_a_coupon_status_change_after_undo_reads_as_before` gives the stepped-down app's rows a transfer fallback in the same save. (`test_scene_id_m06.py` is back to v0.5.22's text: with the gate after the gate-report check it passes unchanged.)

- External-fixture replays are not public reproducibility evidence and do not establish production acceptance.
- `ruff check` and `ruff format --check` are clean.

## Rollback

Reinstall v0.5.22. Nothing is stored differently: the gate only refuses saves, and every table v0.5.23 stores, v0.5.22 would also have stored.

## Regression fixes

The following regressions were corrected:

- the gate ran before v0.5.22's own refusals (note, stale version, gate report) and changed their codes; it now runs after all of them (`test_earlier_refusals_keep_their_order`; `test_scene_id_m06.py` is back to v0.5.22's text).
- `ROUTE_TABLE_CURRENT_UNROUTED` refused a `CURRENT` app no row ever named (a new registration, a promotion ahead of its rows); it now needs a row before (two tests).
- a crafted twin app id with a trailing newline passed the gate while `invoke_solution` (which strips ids) reached the `CANDIDATE` entry. Further testing found the mirror case (a `CANDIDATE` twin of the `CURRENT` app, read by the routing result). Now a row on an id with surrounding whitespace is never callable (two tests).
- known limits added (new key on a parked app, an app in two route tables, the emergency path, topics / intents / request contract, whitespace ids); the message tail no longer assumes a callable app existed.

## Exact-ID regression

A further regression exposed the same issue in the opposite direction: stripping whitespace let a `CANDIDATE` twin of the `CURRENT` app take its row, because the routing result reads the exact id. Corrected behavior: a row whose app id has surrounding whitespace is never callable (`ID_WHITESPACE`), and `named` / `was_named` / unrouted use the exact ids again (`test_a_candidate_twin_of_the_current_app_cannot_take_its_row`).

## Additional coverage

Both whitespace-ID directions are refused. The historical checks also covered false refusals and a 400-mutation crash-fuzz run; the remaining limitations are listed above.
