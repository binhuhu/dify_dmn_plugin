# v0.5.23

**Prerelease candidate. Production compatibility has not been accepted.** On top of v0.5.22 this version adds one thing: a **callability gate on route-table saves** (ruling D13 of the 11-06 routing review, Brian 11-06 19:0x "As recommended"; Brian chose a gate-only 0.5.23, so the items queued for 0.5.23 before — mandatory `gate_report` with the writer, the plugin registry table, the 0.5.22 M1 fix — move to the next version).

**Why.** On 11-06, version 8 of `dispatch.route` (18:08) registered a second coupon app as `CANDIDATE`, and version 9 (18:11) pointed the coupon complaint row at it, leaving the `CURRENT` coupon app with no row. The plugin accepted both saves; `invoke_solution` calls only `CURRENT`, so every coupon complaint became "no solution", with no refusal anywhere. Version 10 (20:25) pointed the row back.

**Not additive.** Saves that v0.5.22 stored can now be refused (below). Reads, evaluation and `invoke_solution` are unchanged. Every refusal v0.5.22 gives keeps its code, message, path and order: the gate runs after all of them, just before the caller's own gate (review round 1). A save that is not a v3 route table is untouched.

## The gate

A v3 route-table save is compared with the v3 version it replaces. If it leaves the table **less callable**, the whole save is refused and nothing is written. Refused, in this order:

- **`ROUTE_TABLE_SOLUTION_NOT_CALLABLE`** at `routes[i].target.app_id` (the row as sent): a `SOLUTION_APP` row newly points at an app that is not `CURRENT`, or the app it points at is no longer `CURRENT`. The message names the row (scene shown as `M_…`), the app and its status, and says how to do it right: make the new app `CURRENT` in the same save, or park the row on a transfer or resource target.
- **`ROUTE_TABLE_SOLUTION_LOST`** at `routes`: a row whose solution was callable is gone and the key has no target at all. A transfer or resource target in its place is an explicit fallback and passes.
- **`ROUTE_TABLE_CURRENT_UNROUTED`** at `solutions.<app>.status`: a `CURRENT` app that some row named before is named by no row now. Step it down (`CANDIDATE` / `RETIRED`) in the same save. A `CURRENT` app no row named before (a new registration, or one promoted ahead of its rows) is left alone.

**Only worse is refused.** What the replaced version already had is left alone: a row already parked on a `GATED` / `SHADOW` / `CANDIDATE` app, a `CURRENT` app already without a row. So unrelated saves pass, and so does the save that repairs things. Rows are compared on the legacy spelling of the scene id, so a save that only respells `P_xx` as `M_P_xx` changes no row.

**Not compared:** the first v3 store (from v2 or nothing), and a first store under a standard name, which copies the old head unchanged (I12) and so cannot change callability.

`route_callability(doc)` and `callability_gate(prev, clean, sent)` are in `dmn_client/route_table.py`; the save path calls the gate after every earlier refusal and before the caller's gate. It reads only the head being replaced, so I19 / I20 are unaffected.

## Known limits

- **Callable means `CURRENT`.** The gate does not check that delivery can build the app's `request_contract` (v4 / v4.2 today), that the app's published Start matches `inputs`, or that the app exists. Those stay with the pairing gate and the release line.
- **No explicit "parked" marker.** A parked row is a row on a non-`CURRENT` app; there is no field saying why or where it falls back. A parked row's app can change status between non-`CURRENT` states, but repointing it to another non-callable app is refused.
- **One table at a time.** The gate compares this table with its own previous version. An app's status across route tables is still `_one_state`'s check.
- **A new key on a parked app is refused.** A row added on a key that had no row, pointing at an app that is not `CURRENT` (even one already parked elsewhere), is refused `ROUTE_TABLE_SOLUTION_NOT_CALLABLE`: a new parked row would carry no reason or fallback. Park a new key on a transfer or resource target instead.
- **An app in two route tables:** moving its last row in one table to a fallback gives `ROUTE_TABLE_CURRENT_UNROUTED`, and stepping it down there gives `ROUTE_TABLE_SOLUTION_STATUS_CONFLICT` (`_one_state`). Remove it from this table's registry instead.
- **Emergency path:** closing a gate again on a routed app (`CURRENT` → `GATED`), or rolling back to a version stored before a gate was opened, now needs a transfer or resource fallback for that app's rows in the same save.
- **Topics, intents and request contract are not checked.** Rewriting a routed `CURRENT` app's `topics` / `intents` passes the gate, though admission judges whether a solution applies by them; so does a `request_contract` delivery cannot build.
- **Ids with surrounding whitespace:** validation still accepts an app id or scene id with a trailing newline (`UUID_RE` / `SCENE_RE` use `match`, unchanged from v0.5.22). A solution row that names such an id is never callable to the gate, whichever way the twin points: the routing result reads the exact id while `invoke_solution` strips it, so the two would read different entries (adversarial review rounds 1–2). Refusing those ids at validation (`fullmatch`) is left to the next version, since it would change v0.5.22's refusals. None of the 51 stored live route versions has such an id. The same looseness lets a row on a padded scene key (`"P_02_04_01\n"`, and likely a padded issue type or phase) keep an app counted as named, so `ROUTE_TABLE_CURRENT_UNROUTED` does not fire while the real key has moved to an explicit fallback (review round 3, 低; the scene is never left without a target).
- **Same race window as before:** the gate reads the stored head, then writes; plugin storage has no compare-and-set (the stale and version-key checks are unchanged).
