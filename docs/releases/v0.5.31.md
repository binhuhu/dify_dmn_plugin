# v0.5.31: one route row shared between solution apps by share

This is a **pre-release**, continuing v0.5.30's single-operator, serial-maintenance scope and OPEN/SIGNED risks. Target-host installation/upgrade, real business API integration and production acceptance remain **NOT_RUN**. Publication and CI are not deployment acceptance.

## What changed

A row of a v3 route table may name several solution apps with a share each:

```json
{"kind": "SOLUTION_SPLIT", "split": [
  {"app_id": "<app A>", "share": 50},
  {"app_id": "<app B>", "share": 50}
]}
```

- 2 to 4 apps, none repeated. Each must be registered in `solutions` and be `CURRENT`; otherwise the save is refused (`ROUTE_TABLE_UNREGISTERED_APP`, `ROUTE_TABLE_SOLUTION_NOT_CALLABLE`). `share` is an integer from 1 to 99 and the shares add up to 100 (`ROUTE_TABLE_TARGET`). A v2 route table refuses the kind.
- **A split is active only for a flow that binds `split_key`.** Every decision node that reads the route table must list `split_key` in its `input_bindings` (if some do and some do not, evaluation is refused with `ROUTE_TABLE_SPLIT_BINDING`, naming the nodes that do not); the flow passes the ticket id there as a string parameter. The plugin takes the first 8 hexadecimal digits of the SHA-256 of the key (UTF-8, surrounding whitespace removed) as a number modulo 100. The apps take consecutive ranges of that bucket in the order they are listed: with 50/50, buckets 0–49 go to the first app and 50–99 to the second. The same key always reaches the same app while the row is unchanged.
- The caller reads the result of the chosen app, exactly as a plain row to that app gives it: `route_kind` is `SOLUTION_APP`, with the same `app_id`, `inputs` and, in the v4 output, `solution` block. Nothing downstream needs to know about splitting.
- A flow that does not bind `split_key` gets the **first** app of every split row. So does a bound flow on a request that carries no usable key (record absent, value empty, or quality other than `KNOWN`). The trace says which case it was: `route_split` is `{"bound": false, …}`, or `{"bound": true, "key_given": false, "bucket": null}`, or `{"bound": true, "key_given": true, "bucket": n}`; `model_source.split` is `BOUND` or `NOT_BOUND`. A bound flow always carries both fields; an unbound flow carries them only when the table has a split row.
- The order of the two changes does not matter. A flow that binds `split_key` works on a table without split rows (before the first is added, after the last is removed, after a rollback): the key is accepted and has no effect. A table with split rows works for a flow that does not bind the key: first app.
- Stepping an app down while a split row still names it is refused at the store, as for a plain row; so is dropping a `CURRENT` app from every row without stepping it down. The two-state invariants count a split row once and check each of its apps.
- The route editor offers "按份额分流…" as a target on a v3 table, one line per app with its share, and reports the same refusals before saving.

## Compatibility

- For a flow that does not bind `split_key`, a table without split rows compiles to the same model as in v0.5.30. Existing stored tables are not rewritten. For a flow that binds it, the model declares one more optional parameter, `split_key`.
- A flow that does not bind `split_key` reads a model with the same three parameters as before, also when the table has split rows. Passing a `split_key` record from such a flow is refused like any undeclared parameter (`INPUT_TYPE_MISMATCH`).
- A split group compiles to one rule per app plus one for requests without a key, per 128 scenes; these count toward the existing limit of 128 rules for a stored route table.
- The bucket depends only on the key. Two split rows with the same shares send a given key to the same position in each; this release has no per-row salt.
- Changing shares or the order of apps moves some keys to another app from the next evaluation on. The plugin keeps no record of where a key went before.
- The shares are exact over the 100 buckets, not over any finite number of requests; the observed proportion varies with the keys that arrive.
- Downgrading: v0.5.30 and earlier do not know the kind. They refuse to save a table that contains a split row, and are expected to refuse one that is already stored when a flow reads it (not tested against v0.5.30). Replace split rows with plain rows before downgrading.

## Not in this release

- No measurement or comparison of the apps that share a row, and no automatic adjustment of shares.
- `scripts/accept-route-table-v3.py` reads a split row as an unbound flow does (its first app); it does not exercise bound evaluation. This change to the script was not run against a host.

## Verification scope

Tests cover the stored shape and each refusal, the rule limit, unchanged compilation of tables without split rows, a bound flow on a table without split rows, refusal of nodes that disagree on the binding, two split groups in one table, a split shared by more than 128 scenes, the first-app result for an unbound flow and for a bound flow without a usable key, the bucket function, the range edges, stability of a key, the proportion over a sample of keys, the other rows of a table that has a split row, the v4 solution block, and the callability and invariant gates. Each guard was checked by removing it and confirming a test fails; the one survivor (the quality check on the key) is unreachable because the snapshot check refuses a non-`KNOWN` record that carries a value. The original handoff checked the route editor change by syntax only. The reviewed publication adds automated DOM and real signed-endpoint browser regression for the split editor; exact results, test counts, and package identity are recorded with the release artifacts.

Manifest permissions remain endpoint, app and 16 MiB storage. The official CLI-produced package is unsigned and has not undergone Marketplace review. Follow the host's signature and installation policies; do not bypass them.
