## 一、对现网的影响

全部读法——定位、分诊、交付编排、方案、定位查询各图里的插件节点，81 采集器、81 存表入口、查看器读的那些——回答不变；同一存表请求存下的表文档、内容摘要、版次与存表号不变；不带用例的存表不写任何新键（存储逐字节同）。证据：全链路无影响对跑闸（见五）。

变的只有存表：

1. **7 张交付表（标准名）存表的回执**多出 `auto_gate` 键和本闸的黄项（码见二）。只这 7 张：方案层表、试验表、别的任务类型的表、旧名下的存表，回执逐字节不变。今天 7 张都还没有用例集，每次存都带一句「还没有随表用例：用例没跑，不拦」；四张表头版就有的「不在场景目录里的场景号」每次存都带一句黄字（个数见四），换号窗口清掉之前一直在。
2. **新引入问题的存表被拒**（0.5.41 收这些请求）：
   - 这张表存着用例集，这一版改了某条用例的答案（`TABLE_CASE_FAILED`，回执 `error.detail` 逐条给用例号、路径、期望、得到）。**只拒这次存表改出来的**：某条用例在现头版上本来就过不了、这一版答案和头版一样（别的表改过之后带来的「漂移」），只报黄 `TABLE_CASES_DRIFT` 并点名改过的那张表；
   - 随存带来的用例集本身写错或超限（`TABLE_CASES_INVALID`）；
   - 7 张交付表里新出现的场景号不在场景与话题表里（`SCENE_NOT_IN_CATALOG`；表第一次存、存目录本身、整包加的新场景不算）；
   - 受理条件表、场景成立表新用到的、声明了 `fact:` 来源的事实，这个场景的关联实体在能力表里给不出（`ACCEPTANCE_FACT_SUPPLIER_MISSING`）；
   - 场景关联实体表、补充要求表、能力表这一版让受理条件里在用的事实没了供给方（`ACCEPTANCE_FACT_SUPPLIER_REMOVED`）——这条对能力表也生效；今天没有一个受理参数声明来源，两条都不会触发；
   - 路由表这次改动过的方案，登记的入参与方案应用已发布版本的开始变量对不上（`ROUTE_TABLE_SOLUTION_INPUTS_LIVE_MISMATCH`）。
3. **存表请求多收一个键 `cases`**（这张表的整份用例集）。0.5.41 下：五张交付链表带它是拒（`STORED_TABLE_UNKNOWN_KEY`），其余表是丢键报黄（`UNKNOWN_KEYS_DROPPED`）；本版收下当用例集，写错就拒（`TABLE_CASES_INVALID`）。带 `cases` 的请求照样走严格 JSON：整份请求（用例集在内）有重复键、非有限数，和不带 `cases` 一样回 `INVALID_JSON`。`cases` 暂不进存表词表，`op=vocabulary` 回答不变——和标准 §十「仍拒未登记的顶层键」的关系见「七、标准要并进的」。
4. **三个新 op**：`cases`（读这张表现用的用例集）、`cases_check`（把一次存表干跑一遍、什么都不写，回哪几条过不了，附一份照新结果改好期望的整份用例集，照抄进 `cases` 就能存；也回 `proposed_dependent_cases`：这一版会让哪些别的表的用例过不了、它们的新结果）、`cases_save`（只换用例集，必须对现头版全过；场景与话题表照受控入口签名）。op 写错的拒绝文案仍只列 0.5.38 那些 op。
5. **一张表改了，读它的别的表的用例也跑**：用例集记着自己的读方读到过哪些表（`reads`）。存资源去向表这类被别的表读到的表时，把读到它的那几张表的用例集也跑一遍；在头版上过、这一版过不了的，点名报黄 `DEPENDENT_TABLE_CASES_FAILED`（不拒：那几张表的新用例集要等这一版成了头版才能 `cases_save`，拒了就两头卡死）。
6. **路由表存表会读平台**：只对这次改动过的方案（新增、登记改了、新有行指着的），经插件会话 `fetch_app` 读应用已发布版本的开始表单，每个 3 秒、合计 8 秒；读不到、超时、平台不支持一律报黄照存。没改方案的存表不读平台。改动过的方案一律再报一句黄 `ROUTE_TABLE_SOLUTION_CONTRACT_UNCHECKED`：方案真正收的请求合同本闸不核。AgentHub 是否实现了 `fetch_app` 这个反向调用，装机前测不了；最坏就是读平台这一项一直黄。
7. **调用方**：路由表维护应用（人手存表、查看器经它存、81 存表入口经它存）。81 入口现在不读回执里的 `warnings` 与 `auto_gate`、台账写死 PASS——**81 侧待派**。查看器带不了 `cases`：**查看器侧待派**。**这两单落地之前不给 7 张表首存用例集**；没有用例集的表，用例这一项只报黄，不拦任何编辑路径。

### 1.1 照实说：装上之后两次事故拦不拦得住

| 情形 | 第 9 版那种存法（行指到候选应用、在用方案没了路由行） | 第 16 版那种存法（有意换去向，登记的合同又不实） |
|---|---|---|
| 装上、7 张表还没有用例集（两单落地前一直是这样） | 照旧被 0.5.23 可调闸拒（不靠本闸） | **不拦**：存成，只报黄（还没有用例、方案现网没读到或合同没核） |
| 有用例集，存表人没改期望 | 0.5.23 可调闸先拒；可调闸之外，用例也拒 | 用例拒（券投诉第一阶段那条） |
| 有用例集，存表人有意改、在同一次存表里带上 `cases_check` 给的新期望（查看器「接受新结果」就是这一下） | 0.5.23 可调闸照拒 | **不拦**：开始变量对得上（`call_id`、`request_json`），真正的祸根（入口只收 v4/v4.3、话题诉求为空）在代码节点里，本闸只报黄 `ROUTE_TABLE_SOLUTION_CONTRACT_UNCHECKED`，要靠存后回归（评审 3-7）照 `contract_unchecked` 核 |
| 原样重发历史里的第 16 版内容 | — | 头版之前 2 版以内算回滚，只报黄；更早的（如现网第 29 版重发第 16 版）照常跑用例，过不了就拒 |

即：本闸拦的是「改了去向没改用例」「新号不在目录」「事实没供给方」「登记入参与现网开始变量不一致」；有意改且合同不实的那一类，本闸不拦。

## 二、拒存与黄项（码给实现与 81 用）

| 码 | 拒 / 黄 | 意思 |
|---|---|---|
| `TABLE_CASE_FAILED` | 拒 | 这一版改了用例的答案（`error.detail.failed` 前 20 条，`failed_count` 总数） |
| `TABLE_CASES_INVALID` | 拒 | 随存带来的用例集写错或超限（≤ 500 条、≤ 256 KiB；不许钉版本；期望里不许写来源段与表的版次、摘要、存表号） |
| `SCENE_NOT_IN_CATALOG` | 拒 | 新引入的场景号不在场景与话题表 |
| `ACCEPTANCE_FACT_SUPPLIER_MISSING` | 拒 | 声明了来源的新（场景, 事实）找不到供给 |
| `ACCEPTANCE_FACT_SUPPLIER_REMOVED` | 拒 | 供给方那几张表这一版让在用的（场景, 事实）没了供给 |
| `ROUTE_TABLE_SOLUTION_INPUTS_LIVE_MISMATCH` | 拒 | 改动过的方案登记入参与现网开始变量对不上 |
| `TABLE_CASES_MISSING` | 黄 | 7 张交付表之一还没有用例集 |
| `TABLE_CASES_DRIFT` | 黄 | 现用用例在头版上也过不了、这一版答案没变：别的表改过之后带来的（`sources` 点名） |
| `DEPENDENT_TABLE_CASES_FAILED` | 黄 | 这一版会让读到它的别的表的用例过不了（`table` 点名） |
| `TABLE_CASES_REDUCED` | 黄 | 这次带的用例集比现用的少了（删掉的用例号） |
| `TABLE_CASES_FAILED_ON_RESTORE` | 黄 | 回滚（内容等于头版之前 2 版以内的一版）时现用用例过不了，照存；带着用例集回滚的不算 |
| `TABLE_CASES_NOT_MOVED` | 黄 | 表存成，挪用例集时写失败；下一次存表照样用这次带的那份 |
| `SCENE_NOT_IN_CATALOG_KEPT` | 黄 | 头版本来就有的、不在目录里的号（带个数） |
| `SCENE_CATALOG_ABSENT` | 黄 | 场景与话题表没存过 |
| `SCENE_CATALOG_DROPS_IN_USE` | 黄 | 存目录时，别的表还在用的号这一版没了 |
| `ACCEPTANCE_FACT_SOURCE_UNDECLARED` | 黄 | 参数没写来源，供给核不了（不按参数名猜） |
| `ACCEPTANCE_FACT_SCENE_UNBOUND` | 黄 | 事实所在规则没限定场景 |
| `ACCEPTANCE_SUPPLIER_REGISTRY_ABSENT` | 黄 | 能力表没存过 |
| `ACCEPTANCE_FACT_SUPPLIER_MISSING_KEPT` | 黄 | 头版就有的缺供给 |
| `ROUTE_TABLE_SOLUTION_LIVE_UNREAD` | 黄 | 没读到方案应用的现网开始变量 |
| `ROUTE_TABLE_SOLUTION_CONTRACT_UNCHECKED` | 黄 | 改动过的方案，真正收的请求合同没核（留给存后回归） |

回执 `auto_gate` = `{cases: {suite_sha256, ran, passed, changed?}, red, yellow, contract_unchecked?}`；`changed` 是这次带来的用例集相对现用的增、删、改期望；`contract_unchecked` 是这次改动过、合同没核的方案（留给存后回归 3-7 照单核）。

## 三、已知限制

- 开放模式下谁都能改用例集：同一次存表把用例删掉再存坏表，本闸照存，只报黄 `TABLE_CASES_REDUCED`；要靠 81 每日读数列出「用例被删 / 期望被改」（81 侧待派）。
- 有意改且合同不实（第 16 版那一类）不拦，见 1.1。
- 用例是抽样：路由表 1024 行里取 82 条（每种结论、每个（问题类型、阶段）×结论、每个转安全的场景各至少一条），没取到的行单独改了照样存得进去。
- 用例集只占一个键（`route-table:<表>:c`），`op=usage` 不数它（每张 ≤ 256 KiB）；断在两次写之间留下的 `:cp:<存表号>` 只在断电时出现，`op=prune` 不清。
- 插件存储没有比较后写入：用例集与表是两次写，断在中间时下一次存表会挑对那份；并发存同一张表的老问题不变（仍按单人串行维护）。
- 用例集记的 `reads` 是写用例集那一刻读到的表；之后表的读法变了（比如路由行新指到一个以前没读过的表），要等下一次换用例集才更新。
- 回滚走远版（头版之前 3 版及更早）要带改好的用例集一起存（`cases_check` 给），草稿回滚 `from_version` 不能带 `cases`，要回远版就把那一版内容作普通草稿带 `cases` 存。
- 用时见四；路由表、资源去向表每次存表要多两秒上下，场景与话题表近一秒（读方每次都整份校验），AgentHub 上可能更慢。
- 闸在版本核之前算好、之后才拒（为了版本核到头版之间仍只有 0.5.19 的存储调用，并发撞车的时间窗不被拉长）：随后被版本核或可调闸拒的存表，闸白算一遍（含读平台）。
- 撤销首存时改引用的那次存表（`take_back=False`）不跑闸，没有单测覆盖。
- 同号不同义（换号窗口里那 43 个号）目录核查不出，照 R-108 逐件批。

## 七、标准要并进的（发版当天由标准维护人并进 DMN 结构与维护标准 2.0，本线不改标准）

- §十「存表两种模式」开放模式一条，「仍拒未登记的顶层键」后加：「存表请求另收 `cases`（这张表的整份随表用例集），它是请求键、不是表键，不进表内容与摘要，暂不进存表词表 `op=vocabulary`；写错按 `TABLE_CASES_INVALID` 拒。」（或改实现把 `cases` 登记进请求键、`op=vocabulary` 多一个键——二选一，本线建议前者，`op=vocabulary` 回答保持不变。）
- §十一「插件支持」加一段「存前自动闸」：三项核（随表用例、跨表核、路由表改动方案的现网开始变量）的口径——只拒这次存表改出来的、漂移与回滚（2 版以内）只报黄、读不到平台只报黄；三个新 op `cases` / `cases_check` / `cases_save`；拒存码与黄项码照本说明「二」。
