# v0.5.6

Historical version record. Test counts and validation status below describe that version, not the current review branch or a current deployment.

基于 v0.5.5 记录提交 `9e250bd`（包源 `36b81d4`）。

0.5.5 的 v2 路由表仅登记应用名称与开始变量；v3 将可调用状态和声明收进路由表，使方案登记有单一维护点。

## 改了什么

| 改了什么 | 为什么 |
|---|---|
| **路由表 v3**（`dmn-json.route-table/v3`，`dmn_client/route_table.py`）：与 v2 同一份文档，`solutions` 每项多登记字段——`status`（必填：`CURRENT` / `CANDIDATE` / `GATED` / `SHADOW` / `RETIRED`）、`gate_code`（`GATED` 必填；`SHADOW` 可写）、`request_contract`（如 `场景方案调用/v4`）、`topics[]`、`intents[]`、`invocation_scope`、`priority`、`package_id`、`target_handoff`。存时每项补齐全部键（没写的是 `null` / `[]`），话题 / 诉求保持登记顺序。`input_bindings` **不进插件表**（拒收，`ROUTE_TABLE_INVALID @solutions.<app>.input_bindings`）：交付编排怎么组请求是交付编排的事，按 `request_contract` 选适配 | 方案登记只在一处维护；新方案 / 翻闸 = 编辑页存一版 |
| **校验**：`CURRENT` 必有 `request_contract` 与非空 `topics` / `intents`（`ROUTE_TABLE_SOLUTION_INCOMPLETE`）；`GATED` 必有 `gate_code`（`ROUTE_TABLE_GATE_REQUIRED`），`CURRENT` / `CANDIDATE` / `RETIRED` 不写闸；**同一个应用在两张路由表里状态（status + gate_code）不能不同**（`ROUTE_TABLE_SOLUTION_STATUS_CONFLICT`；存储键 `route-table-index` 记 0.5.6 起存过的路由表，`dispatch.route` 总在比；v2 表按全部 CURRENT 算）；**v3 表不能存回 v1 / v2**（`STORED_TABLE_SCHEMA_CHANGED`：旧格式把每个方案都当 CURRENT，会放开被闸挡着的方案） | 不让「选哪张表」或「旧格式覆盖」决定一个被闸挡着的方案跑不跑 |
| **v2 照旧可读**：每个方案按 `CURRENT`、无闸、其余未声明读（`solution_entry`）；v2 文档的存储形态与 `content_sha256` 不变 | 已有 v2 表保持调用行为 |
| **`invoke_solution` 只放行 `CURRENT`**（`dmn_client/solution_invoke.py`）：被闸挡着的（`GATED`，或带闸的 `SHADOW`）REJECTED `SOLUTION_GATED`，其余非 CURRENT REJECTED `SOLUTION_NOT_CURRENT`；状态先于开始变量核；回执与工具变量多 `solution_status`、`gate_code`（加法，其余键与码不变） | GATED / CANDIDATE 拒，码带 gate_code |
| **路由求值回执加 `solution` 块**：新存根格式 `routing-table/v4` = `routing-table/v3` 的规则与字段 + 决策字段 `solution`——方案行 `{app_id, status, gate_code, request_contract, topics, intents, table_content_sha256}`，转接 / 资源 / 无方案行 `null`；`trace.model_source.format = "routing-table/v4"`。`routing-table/v2` / `v3` 的编译结果与 0.5.5 **逐字节相同**（表升 v3 也不变：登记字段不进这两种模型） | 回执合同按格式版本升名（见下「回执格式版本与调用方迁移」） |
| **编辑页**（`route_editor_static/editor.js`）：v3 表的方案登记每行能看能改 状态 / 闸 / 请求合同 / 话题 / 诉求；调用范围 / 优先级 / 方案包 / 交接只显示、原样带回；表里其余的键照 0.5.5 原样带回。v2 表有「升为 v3」（每个方案先当 CURRENT，写全才能存）；v3 表上新登记的应用先是 CANDIDATE；状态改成不带闸的状态时闸清空；存前先挡住 GATED 没写闸、CURRENT 没写全的项（标红）；改动列表按字段列（「状态 GATED → CURRENT」）；现存是 v3 时不载入 v2 旧版；下拉里非 CURRENT 的应用名后带状态。文字字段改完（change）重画，「检查改动并保存」跟上（以前改方案名称后按钮不亮） | 路由表编辑页；其他查看器不在本版本范围 |
| **存前闸接入点**（只留接口，不判闸）：存表请求体可带 `gate_report`（对象 ≤ 64 KiB，必须写 `content_sha256` = 这次要存的内容摘要，否则 `STORED_TABLE_GATE_REPORT_INVALID` / `_MISMATCH`），报告存 `route-table:<表>:g:<save_id>`，存下的文档多 `gate_report_sha256`；不带报告时存下的文档与 0.5.5 相同。代码钩子 `StorageTables.save(..., gate=fn)`：`fn(clean, gate_report)` 在全部检查之后、写入之前调，抛 `RouteTableError` 即拒存（0.5.6 没有调用方传它）。编辑页可粘贴闸报告随一次保存发出 | 可选报告接口；本版本不执行外部闸。 |

## 不变

存表 / 读表 / 历史 / 版本冲突检查、`evaluate_decision` / `evaluate_stored_table` 入参出参、版本号规则、v1 / v2 / 决策表 / 补充表 / 资源表的校验与 `content_sha256`、`routing-table/v2` / `v3` 的编译模型、全部原有错误码。插件全套原有测试全绿。
包内工具个数不变（8 个）；`invoke_solution` 多两个输出变量。

## 回执格式版本与调用方迁移

路由求值回执（`evaluate_decision` 对 PLUGIN_STORAGE 路由存根的结果信封）按存根格式定版：**`routing-table/v3` → 新名 `routing-table/v4`**（加 `outputs.decision.data.solution` 与 `trace.model_source.format`）。`routing-table/v2` / `v3` 原样保留、编译逐字节不变，所以旧格式的调用方在改钉 v4 之前不受影响。

| 调用方协议 | 旧格式读取方式 | 升级要求 | 未升级时 |
|---|---|---|---|
| 路由结果消费者 | 读取 `routing-table/v3` 的去向字段及模型来源 | 切换到 `routing-table/v4` 后读取新增 `solution` 块，并按登记状态和请求合同处理调用 | v3 模型保持不变 |
| 方案调用消费者 | 读取 `invoke_solution` 的状态、错误码、子流程结果和表摘要 | 处理新增 `gate_code`、`solution_status` 及拒码 `SOLUTION_GATED` / `SOLUTION_NOT_CURRENT`；请求适配仍由调用方负责 | v2 表中登记应用保持原调用语义 |

公开调用方应按上述格式调整读取合同；迁移不随插件安装自动执行。

## 已知限制

- 与 0.5.5 相同：插件存储只有 get/set/exist，expected_version + save_id 读回是乐观并发判冲突，不是原子 CAS。
- 跨表一态只看 `dispatch.route` 和 0.5.6 起存过的路由表（`route-table-index`）；0.5.6 之前存过、之后没再存的其它路由表不在比对里。索引在文档之前写，存失败时索引里多一个名字无害（读不到就跳过）。
- v3 支持 `SHADOW` 并允许它带闸；被闸挡住的候选应写为 `GATED`。
- 编辑页只编辑路由表 v2 / v3；策略表经 `route_table_store` 工具或编辑端点同一 API 存。查看器（flow-structure-viewer）的方案行编辑不在本版。
