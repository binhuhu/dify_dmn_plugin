# v0.5.15

Adds version pins, decision sets, separate content and declaration size limits, table-to-table chaining, FIRST row-order fingerprints, and list-form state declarations. Existing formats remain supported; compatibility is verified with synthetic regression tests.

- **Version pin.** `evaluate_stored_table` takes optional `version` (positive integer) and `content_sha256` (64 lowercase hex). With `version` it reads exactly that stored version; with both, that version must also have that digest; with `content_sha256` alone, the newest of the last 50 versions with that digest. A pin that is not there fails with `STORED_TABLE_VERSION_MISSING` and never falls back to the latest. The envelope's `source` echoes `pin`. Published solution flows pin their tables; the plugin cannot tell draft from published, so that rule is checked at publication.
- **Decision sets** (`dmn-json.decision-set/v1`, format `decision-set/v1`): one table, several models (`models: {key: {model_ref, model}}`), same name and owner rules as a decision table, its own schema family. Inputs `{models?, parameters, missing, undeclared}`; parameters are one pool, each model takes its own; `undeclared` counts against the models asked for. Every model carries its own call status in `result.models.<key>` (`SUCCEEDED` with its result, or `BLOCKED` / `FAILED` with an error and no state) and `result.failed_models` lists the rest; only table- or input-level problems (missing table, format, pin, malformed inputs, unknown model key, reading the same set) fail the whole call. Saving respells scene ids across all models; a declaration names each model.
- **Size.** The table content (everything but `declare`, canonical JSON) is limited to 512 KiB (`STORED_TABLE_TOO_LARGE`), the declaration separately to 256 KiB (`TABLE_DECLARATION_TOO_LARGE`), the request to 832 KiB (`BODY_TOO_LARGE`, 413). These are application validation limits, not a deployment capacity guarantee; backend quotas and transport limits must be verified separately. The declaration stays in the table's key. Nonfinite or invalid JSON inputs, including embedded upstream envelopes, return structured errors. Evaluation input byte/depth budgets are not newly imposed in this release; deployments must enforce appropriate request limits.
- **Table-to-table chaining.** A parameter of type `table` receives `{"from_table": <upstream results>, "model"?: <set model key>}`. Its conditions read the upstream table state (`[parameters, p, state]`), one result key (`[parameters, p, result, key]`) or `quality`; never `value`. The plugin fills `source_refs` (`stored-table:<table>@<version>#<model>`, `rule:<rule_id>`, at most 16) and echoes `chained_parameters`. An upstream call (or set model) that did not succeed leaves the parameter missing, handled by the table's own `missing` setting. A result key the upstream did not produce is unknown, never false.
- **Row-order fingerprint.** A FIRST table's declaration may carry `row_order_sha256` (the digest of its rule ids in order; required when `states` is a list). A save whose order no longer matches returns a table-level `ROW_ORDER_STALE` warning ("行顺序变了，优先级待重新确认") with the shadowing changes against the previous version (rule pairs whose precedence flipped and that may both hold); the save is never refused.
- **`states` as a list** of the states a table uses. STANDARD: row states only (`PASS` / `FAIL` / `PENDING` / `UNKNOWN` / `CONFLICT` / `NOT_APPLICABLE`); the no-match template is the table state `NO_MATCH` and no rule may point at it. The v0.5.14 object form (state -> meaning) is still accepted under the v0.5.14 rules.

Not in this release: solution-layer table names (`solution.<…>.<scene_id>[.<part>]`). Production installation and acceptance have not been completed.

Compatibility and rollback: existing table formats and object-form state declarations remain supported. New decision sets, list-form declarations, version pins and chaining require this release; older versions must not be assumed to understand newly saved data or calls. Back up application artifacts and stored data before any separately authorized installation. Rolling back code does not remove or migrate newer table versions. Stored history is not automatically pruned; the 50-version digest search is a read window, not a retention limit.
