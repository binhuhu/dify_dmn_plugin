9. **FIRST 表 `split_of` 的依据查到上限就放行**（第三份核验评审第 1 条，第四节）：同结论的后一条规则写 `split_of` 时，要求它和同结论上一条
   之间有一条别的结论、可能和它同时成立的规则。0.5.40 逐对、逐种情形查到底（两边各 128 种情形就是 16384 次比较，中间每多一条规则再加一份），证得了
   「都不可能同时成立」就拒；这一版同一张表（决策集各模型合起来）的情形比较最多 4096 次、比对的规则对最多 20 万对，用完还没证出的按「可能同时成立」放行，
   不因上限拒一张好表。**0.5.40 收的表照收，回执逐字节不变**（v1 不标黄；用例与随机对拍逐个比过）；变的只是「要比 4096 次以上才证得出
   不可能同时成立」的表：0.5.40 拒，这一版收。v2 的表回执标黄 `SPLIT_OF_ANALYSIS_LIMITED`，列出是哪几条。

**操作提醒：原地改存有风险。** 把一张现网在用的表原地改存成 v2，**默认读最新版的读方会立刻失败**（它们还按 v1 的格式、v1 的入参读），
而且改存后**不能再存回 v1**——「存表回滚」（再存一版旧内容）这条退路没了。建议：
- 改新写法**走新方案段 / 另起应用**：新表名从头存 v2，旧应用的表一个字不动，路由切过去之前两边并存，切回只改路由；
- 实在要原地改存，**先把读方的版本钉住**（`evaluate_stored_table` 写 `version` 或 `content_sha256`），整条链按顺序换完、读方改成 v2 的传法以后再放开。

## 二、方案层新写法 v2（第一段，`30d55f9`）

照需求单第 1–5、7–10、13、16、17 件与标准 2.0.54；v1 的检查、求值、摘要一处没动。

- **表名与角色**：方案层五个标准表名 `solution.<search.info | info.fact | fact.feature | feature.reality | reality.strategy>.<场景号>[.<方案段>]`
  对应 `SEARCH_INFO`、`INFO_FACT`、`FACT_FEATURE`、`FEATURE_REALITY`、`DISPOSAL`。`search.fact` 留作旧名（照收照读，`SEARCH_FACT` 照旧整表判）。
- **格式 v2**：表文档 `schema = dmn-json.decision-table/v2`，顶层键 `schema / table / owner / decision_ref / decision / note / declare`；
  决策 `profile = service-decision-table-v2`，键是 v1 八个键（`profile, version, hit_policy, parameters, rules, result_templates, on_no_match,
  empty_template_ref`），按号判的两种角色另有 `ids`（号 → `{type, values?}`），原值 → 事实另有 `passthrough`（直通的原值号）。每条规则
  `rule_id + output_template_ref + rows`，`rows` 是情形列表、每项一个「且」条件列表，只有一种情形也写成一项；v2 不收 `when` / `when_any`。
  v2 只在五个标准表名下：不收分片名、不收旧名；一律要声明（`stage = STANDARD`）。
- **输入按位置固定**（标准 2.0.54 顶层规则三的表）：参数正好是角色那一套——查询 → 原值、原值 → 事实是 `request, calc, info`；事实 → 特征是
  `request, calc, fact`；特征 → 现实是 `request, calc, fact, feature`；现实 → 处置策略是 `request, calc, fact, feature, reality`。多一个、少一个、
  写法不对都拒。参数只写类型：组 `{type: group}`，上游表 `{type: table, from_table: 同一方案那一张}`（第九节 (a)）。没被条件引用的输入只记录，
  不核、不拦。
- **按号取**：条件路径 `[parameters, <输入>, key, <号>, value | quality | state]`（组里的号只有 `value`、`quality`）；现实表是 FIRST / UNIQUE，
  整表读 `[parameters, reality, state | quality]` 或 `[parameters, reality, result, <键>]`。读哪些号由条件路径得出。按号取的参数不收 `hit`、
  `model`；按号取接不带号的回执 → `INPUT_INVALID`；接错表 → `INPUT_SOURCE_MISMATCH`。**新写法的条件一律不收 `exists`**（评审第 9 条：按号取的
  号总在，问它在不在没有意思；整表读的结果键缺了判未知，`exists` 也问不出「没有」）：要问拿没拿到用质量，要问值是不是 null 用 `is_null`；
  JSON 类型（`array` / `object`）的号只许问质量和 `is_null`。
- **按号判**（原值 → 事实、事实 → 特征）：每个定义了的号一条结论——一条规则给出 → 质量 KNOWN（写表人写的「判断不了」也是 KNOWN、state
  UNKNOWN）；同号异值 → CONFLICT（同号矛盾压过判不了）；给它的规则判不了 → UNKNOWN（`filled: INDETERMINATE`，缺口 `KEY_INDETERMINATE`）；
  定义了但一条没中 → UNKNOWN（`filled: NO_RULE`，缺口 `KEY_NO_RULE`，kind = RULE）。插件补的不带 `rule_id`、带 `filled`，和写表人写的分得开。
  直通的原值照原值的质量出同号事实（带 `passthrough: true`）。整表一条没中仍是 NO_MATCH；查询 → 原值、现实、处置照 v1 整表判。
- **下游只收按号的结论**：回执 `result.conclusions`（`dmn-json.conclusions/v1`：表名、版本、内容摘要、`decision_ref`、`keyed`，按号判的表是
  `keys`：每个号的质量 / state / 值 / 规则号；整表判的表是 `decision` / `decisions`）。表输入收整份回执、只收这一部分、或 `{from_table: 其一}`。
  回执记 `inputs`（给没给、读没读）、`reads`（读了哪些号、各号质量）。
- **查询 → 原值**：同 0.5.34 的查询计划，结果 `actions / capability_id / bindings / infos`，`bindings` 写 `request: / calc: / info:<号>`，同一种
  情形里先问已知，不做大小比较；钉新名能力表（只钉 infos 写法的那一版），存表时对着它的 `infos` 核能力号、入参、原值范围（几行取交集）、
  原值号登记过、一轮一轮能成立。
- **同号互斥**：同一个号的几条规则可能同时成立、给不同的值 → 存表标黄 `KEY_RULES_MAY_OVERLAP`，不拒。每条规则的取值域只算一次，用每条
  规则都限定的那条路径分候选对（互斥的规则一对都不比）；比对数与预算任一用完就停、标「分析受限」（`overlap_analysis_limited`）。
- **FIRST 表的 `split_of` 与行序**：沿用 v1 的检查（第一节第 9 类、第四节）。`split_of` 的依据查到上限没证出时放行，回执标黄
  `SPLIT_OF_ANALYSIS_LIMITED`（列出是哪几条规则）；行序变了的 `ROW_ORDER_STALE` 在分析用完上限时同 v1 带 `shadowing_analysis_limited`。
- **头版闸**：方案层表名没有头版只收 v2；头版 v1 的照收 v1，也可改存 v2；事实 → 特征的决策集头版可改存成 v2 的一个决策；改存后单向。v1 与
  v2 之间不继承声明。分片名、旧名不收 v2。
- **v2 不做 `M_` 等同**：v1 对 `scene_id` 的比较把不带 `M_` 的旧写法当同一场景，v2 的条件一律纯相等。

## 三、两头核（第 14 件）

只管新写法 v2；头版是旧写法 v1 的表名不核（它们按 `{from_table, model}` / `hit` 读）。号在哪里定义：原值号在同一方案查询 → 原值表钉住的
那一版能力表（`infos`）；事实号在原值 → 事实表（`ids` 的类型，直通的号照能力表）；特征号在事实 → 特征表（`ids`）；现实号在现实表声明
（`declare.outputs.reality_id.values`）。

- **读方存表**：v2 表的表输入（`fact` / `feature` / `reality`）的上游头版**都要是 v2**（评审第 7 条：v2 处置表不读 v1 现实表，v2 现实表不读
  v1 特征表）；上游没存过、或头版是 v1 → `STORED_TABLE_UPSTREAM_MISSING`，回执写明先存哪一张。按号取的号要在上游当前头版的定义里
  （`STORED_TABLE_ID_UNDEFINED`），条件里的固定值和号的类型对得上（`STORED_TABLE_ID_TYPE_MISMATCH`：`eq` / `ne` / `in` 的值照类型；大小比较只对
  数、字符串；null 都收；`is_null` 不看值；布尔不算数）。**原值 → 事实存表前，同一方案的查询 → 原值表要先存**（原值号只在能力表定义，读方
  对着查询表钉的那一版核）。处置表比的现实号要是字符串、在现实表声明的清单里。
- **上游存表**：和当前头版比，删掉的号、改了类型的号，同一方案排在后面、头版是 v2 的表（隔段读的也算，比如现实表直接读事实）还在读 →
  `STORED_TABLE_ID_IN_USE`，列出读方表名与号；现实表删掉处置表在比的现实号同理；查询 → 原值表换钉能力表时，原值 → 事实读的原值号、各表
  读的直通事实一样核。**只拒变坏**：读方读的号上一版就没定义的，不算这次存表的事。
- **读不出不放行**（评审第 2 条）：两头核读同一方案各段头版时，只有「键不存在」当没有；别的存储失败照原样抛，存表回 503，不会因为读不出读方
  就让上游删号存进去。
- **钉住的能力表那一版找不到**（没存过，或滚出按摘要可找的最近 50 版）：查询 → 原值表自己存表时钉的是这样的一版 → 拒
  `SEARCH_CAPABILITY_TABLE_MISSING`；那张查询表正在换钉时，上一版的钉找不到不挡。**读方不拒**（第三份核验评审第 3 条）：能力表是各方案
  共用的，别的方案改它 51 次以上，一个方案钉的那一版就滚出去了，它的原值 → 事实、事实 → 特征原样重存不该因此被拒。这时照收：读的原值号
  在不在、和条件里固定值的类型对不对这次不核，直通事实的类型当不知道、不比；存表回执警告 `INFO_IDS_UNCHECKED`，写明是哪张查询 → 原值表
  钉的哪一版、为什么找不到、怎么办（重存查询表改钉现有的一版，之后再存就照常核上）。不读原值、不读直通事实的表不受影响、不警告。
- 算出的量（`calc:`）的号插件不带目录、不核，归存前闸（标准 §六「参数用标准化参数」第 5 条）；请求字段不核。

  按号判的同号异值去重都改成按可哈希的键一遍走完（评审第 4 条，480 个号 × 256 个取值的表校验由约 3 秒降到 0.2 秒）；v2 求值按内容摘要记住

    收的全部一样，只有 14 张「要比 4096 次以上才证得出不相交」的从拒变收。
- 超线拒存的文案：「表 `<表名>` 的内容（不含声明，按规范 JSON 算）是 N 字节（约 x KiB），超过存表线 1048576 字节（1024 KiB，所有表一套）」。
- **体积碰线的存储层分块（只评估，没做）**：一张表的版次分成几个键存（每块 ≤ 1 MiB，键 `route-table:<表名>:v<n>:part<k>`），版次键与头版键
  只存块清单（每块 sha256、总长），读时按清单拼回、逐块核摘要；内容摘要照旧按拼回的整份文档算，**分块不改摘要、不改任何读法的回答**；写法
  照「先历史、后头版」的次序先写块再写清单，清理与用量把块算进去。代价是读一张大表多几次存储读。现在最大的真表是费用 v2 现实表 740 KiB，
  1 MiB 线够用；写手建议等有真表过 800 KiB 再做。

## 五、旧写法停收开关（第 16 件）

- 插件存储里的登记值 `solution.v1_writes`（存储键 `dmn-setting:solution.v1_writes`）：`ACCEPT` 照收（默认，键不存在就是它）/ `REFUSE` 停收。
- 读：`route_table_store op=setting`，不带内容（或 `{name}`），任何应用可读，回 `dmn-json.plugin-settings/v1`：值、默认值、可取的值、存过没有、
  读不读得出（`readable`）、谁何时为什么翻的。
- 翻：`op=setting`，内容 `{name, value, note}`，`note` 写一句为什么翻（谁定的）。**只收钉定的「路由表维护」应用 3c016f44 的调用**（别的应用
  403 `STORED_TABLE_WRITERS_APP_REJECTED`）；签名模式下要写手签名，AGENT 不能翻；开放模式下能在 AgentHub 里运行维护应用的人都能翻——翻要
  Brian 一句，这条靠流程管。记下谁、何时、一句说明、上一个值（最近 50 次）。翻开关不发版。写法不对（名字、取值、说明的类型或内容不对）→ 400
  `STORED_TABLE_SETTING_UNKNOWN` / `STORED_TABLE_SETTING_INVALID`。
- 停收后：方案层表名（`solution.*`，含旧名与带分片的名字）再存 v1 → `STORED_TABLE_V1_STOPPED`；已存的 v1 版照读、照求值；v2 照收。交付链等
  别的表不受影响。
- **登记值读不出**（写坏了，或以后的版本写了这一版不认的值；评审第 1 条）：存表闸不当默认值，存 v1 回 503 `STORED_TABLE_UNAVAILABLE`；`op=setting`
  照常读（`readable: false`、`value: null`）、照常写（覆盖掉读不出的值，历史里记一笔「旧值读不出」）。
- 81 统计还剩几个 v1 头版不归插件；翻之前先把分片名、旧名下的表迁到 v2 的新表名（见第一节第 6 类）。

## 六、新写法的词表：`route_table_store op=v2_vocabulary`（第 6、12 件；评审第 11 条补齐）

`dmn-json.v2-vocabulary/v1`，不读表参数、不带内容，带 `content_sha256`。每一项都是校验用的那个对象本身（不是抄的）：
- 格式：表文档 schema、求值格式、profile、结论部分的 schema、顶层键、决策键（各角色要写的键）、规则键、号的定义键与类型、模板键、
  可以没有规则的角色（`INFO_FACT`）；
- 表名：五段与角色、表名规则、链路顺序、只收 v1 的旧名、只收 v2 的新名、**头版闸与改存规则**（没头版只收 v2、头版 v1 可单向改存、决策集
  头版的事实 → 特征可单向改存、改存后不再收 v1、分片名和旧名不收 v2、停收后不收 v1）、**v2 的表输入只读 v2 的上游**、各角色的命中策略、
  按号判的角色与号的键；
- 输入：各角色的固定输入、组与按号读的表与整表读的表、参数写法、声明里的来源；
- 路径：按号取的写法、组与表能读的部分、整表读的写法、**能用的比较（不含 `exists`）**、质量与 state 能用的比较、JSON 类型只许的比较（`is_null`）、
  `bindings` 来源写法；
- 号：字符规则（1–128 个字符，排除 Unicode 类别 C*、Z*）、直通、能力表 `infos` 与 `info_id`、**新名下 facts / infos 两种行形、infos 单向、v2 查询表
  只钉 infos**；
- 声明：键、按号判的表多 `ids`、查询表多 `capability_table`、**`declare.ids` 每项 `{name, names}`（号的中文名在这里）**；
- 结论部分：键、按号的每项键、`filled` 三种、补出的缺口码；
- 码：新拒存码、**`STORED_TABLE_SETTING_INVALID` / `STORED_TABLE_SETTING_UNKNOWN`**、登记值读不出时存表闸的 `STORED_TABLE_UNAVAILABLE`、警告；
- 登记值；安全线（**含「没中模板不计」**）。

`op=vocabulary`（0.5.38 的）与 `op=capability_vocabulary`（0.5.40 的）不动。

## 七、DMN XML 导出新写法 v2（第 15 件）

`convert_dmn_xml` 导出 v2 表文档（只给决策不收：表名定角色与固定输入），导回带 `<dj:decision>` 的 XML；v1 的导入导出一字不动。
- 按号取写成 DMN 的过滤再取第一项，例 `fact[fact_id = "X"][1].value`。号的键名：`request` 写 `field`、`calc` 写 `calc_id`、`info` 写 `info_id`、
  `fact` 写 `fact_id`、`feature` 写 `feature_id`。质量、state 照 v1 质量列的做法各自成列（`….quality`、`….state`）；现实表整表读照 v1 写
  `reality.state`、`reality.quality`、`reality.result.<键>`。
- 每列精确路径在 `dj:path`；导回以它为准，表达式或路径被改过、不是这张表的路径 → 拒。扩展元素各格的类型不对 → `DMN_XML_INVALID`。
- 真读到的输入各写一个 `<inputData>`，决策写 `<informationRequirement>` 指向它（只用从条件推出来、真读到的输入）。
- 一列里值的类型不同（按号判的表 `value` 列，各号类型不同）typeRef 写 `Any`。
- 一条规则的每种情形一行，同一条规则的几行输出一样。**UNIQUE 表里有规则拆成几行时导成 ANY**（几行可能同时成立，按 DMN 的 UNIQUE 算违例），
  扩展元素记着原来是 UNIQUE，导回还是 UNIQUE。COLLECT 表里拆成几行的规则提示一句：标准 DMN 会出几份同样的结果，插件求值一条规则只出一份。
- XML 说不出的（表名、`decision_ref`、版本、`ids`、`passthrough`、模板名、一种情形里条件的先后）记在扩展元素；单元格是导回的准。导出时就
  导回一遍核对，导回逐字一样；不一样的（比如只有一个值的 `in`，单元格写出来就是等于）回执里写明。
- 导回走 1 MiB 的导入线：费用 v2 现实表（740 KiB）、贴线的 v2 表导出的 XML 都超过 1 MiB（967 KiB 的表约 6.9 MB），经工具导回会被拒（导出自己核对的
  那一遍不受这条线限制）。
- 新写法不收 `exists`，表里不会有 `exists` 条件。
- **顺带核的 v1 现有行为**：v1 导出 UNIQUE 表时，一条规则的几种情形不是各列写法的交叉就拆成几行，照旧写 UNIQUE——几行可能同时成立，按
  DMN 的 UNIQUE 是违例。v1 这一版不改（全链路不变），见第十二节；写手建议下一版 v1 也照 v2 导成 ANY。

## 八、能力表 `facts` / `infos`（第 5 件；Brian 批 (c)；评审第 6 条）

- 新名 `support.target.capability.catalog`（存名 `target.capability.catalog`）下两种行形都收，一张表不混：`facts`（每项 `fact_id`，0.5.40 的写法）
  或 `infos`（每项 `info_id / name / field / type / unit / object` + `alternate_of`）。**头版是 infos 以后只收 infos（单向）**；没有头版、头版是
  facts，两种都收。旧名 `platform.capability.catalog` 只读，照旧 facts / `fact_id`。
- **v2 的查询 → 原值表只钉 infos 写法的那一版**（钉 facts 的 → `SEARCH_TABLE_INVALID`）。所以次序是：现网先照上线单存 facts（第 ④、⑧ 步），
  哪个方案要改存 v2，先把能力表改存成 infos（一次存一版，内容只把 `facts` 改 `infos`、`fact_id` 改 `info_id`），再存那个方案的查询 → 原值表。
  改存成 infos 以后回退 0.5.40 读不了这张表（第十节）。
- `info_id` 的字符照新写法号的规则（1–128 个字符、不含空白和控制字符，可以有中文和点）——它就是条件里按号取的原值号；费用直通的原值里有
  `会话.点名.R01` 这类号。`fact_id` 照旧 ASCII、≤ 96 个字符。
- v1 的查询 → 事实表（`SEARCH_CAPABILITY`）钉写 `infos` 的能力表照读成它的 `facts`。

## 十、回退

装了这一版、存过下面几种东西之后，回退到 0.5.40 会读不到或存不进：
- **v2 的表**：0.5.40 不认 `dmn-json.decision-table/v2`，读、求值都失败；改存过 v2 的表名在 0.5.40 下也存不回 v1（头版格式不同）。所以
  **第一次存 v2 的表，要排在「确认不再回退 0.5.40」之后**。装上而还没存过 v2 时，回退不受这一条影响。
- **新名能力表改存成 infos**：0.5.40 在新名下只认 facts，读不到。同样排在确认不回退之后。照上线单存的 facts 版次回退后照读。
- **过旧线的表**：规则 > 512、结果模板 > 128、一条规则 > 128 种情形、一个 `in` > 128 个值的表，0.5.40 求值时会按旧线拒（求值前要再核一遍表）；
  内容 512 KiB–1 MiB 的表 0.5.40 读得到、求值得了，但再存会被拒。
- **停收开关**：键留着，0.5.40 不读它，翻成 `REFUSE` 的效果回退后就没了（照 0.5.40 的规矩管）。
- 用 `op=v2_vocabulary`、`op=setting`、`convert_dmn_xml` 的 v2 导出导回、节点内求值 v2 的图，回退前要先撤。

现网装前没有一个图用到这些；装上以后谁接了，回退前要先撤。v1 的表回退后照读照存，内容与摘要不变。
