# v0.5.22

Historical version record. Test counts and validation status below describe that version, not the current review branch or a current deployment.

**Prerelease candidate. Production compatibility has not been accepted.** On top of v0.5.21 this version lets the resource routing table hold a **three-tier, human-and-AI decision table** instead of the resource-targets list.

**Additive only.** Existing tables keep their exact behaviour. That includes list-format resource tables, their saves and reads. Every refusal that v0.5.21 gives keeps its code, message and path, except a decision table under a triage resource name with another owner, which now says the owner must be TRIAGE.

## Resource routing as a decision table

- **Names:**
  - A triage resource name may hold a `dmn-json.decision-table/v1` owned by the TRIAGE workflow (分诊): a three-segment `triage.<object>.resource` (for example, `triage.dispatch.resource`), or its old name `dispatch.resource`.
  - A decision table there with another owner is refused with `STORED_TABLE_NAME` at `owner.app_id`, saying the resource routing is TRIAGE's.
  - Every other name ending in `.resource` keeps v0.5.21's rule: `target.x.resource`, `p2.x.resource`, a two-segment `x.resource`, a `supplement.*` or solution-layer name. A decision table there is refused as in v0.5.21 (`STORED_TABLE_NAME`, same text).
  - The single-segment `target.resource` / `triage.resource` keep their v0.5.20 behaviour.
- **Declaration:**
  - Required. Role `RESOURCE` and stage `STANDARD`.
  - On a resource-targets name `RESOURCE` is the only role; elsewhere it is not a role (the role-list refusal of other tables is unchanged).
  - The model must use hit policy `FIRST` and have a parameter `resource_id` (string, required, not nullable, allowed quality `KNOWN` only). `states` is written as a list. These two refusals name the model's field (`model.hit_policy`, `model.parameters.resource_id`).
  - A resource name holds a decision table, never a decision set: the set is refused with v0.5.21's name refusal (`STORED_TABLE_NAME`, same text). A solution-layer table whose last segment is `resource` keeps its own rule.
  - Only this declaration may name an object output's fields (`fields: {field: display name}`, display only, never read at evaluation). Every other table refuses `fields` exactly as v0.5.21 did (`TABLE_DECLARATION_INVALID`, path `declare.outputs.<key>`, same text): acceptance tables, target lists, route, supplement, p2 and solution-layer tables, and the models of a decision set.
- **Result** (each rule template):

  ```
  { tier1: { pool, executor, split? },
    tier2: { skill_group, priority, executor },
    tier3: { pick, agent_app_id? },
    gap?, actions }
  ```

  - `executor` is `HUMAN` or `AI`.
  - `pick` is `QUEUE`, `LAST_AGENT` or `AGENT_APP`. `AGENT_APP` requires `agent_app_id` (an app UUID); the other picks must not have one.
  - `split`, if present, is a list of `{pool, weight}`: pools unique, weights positive integers summing to 100. The platform's distributor applies it; the table does no random choice.
  - No key naming a person (`agent_id`, `staff_id`, `agentId` and similar) may appear anywhere in a result. Tier 3 says how to pick, not whom.
  - **Codes** (`tier1.pool`, each `split` pool, `tier2.skill_group`, a string `tier2.priority`) are written as the platform writes them: 1–64 characters, no spaces, no other whitespace, no invisible or control characters. `tier2.priority` is a code, an integer or null; a number goes as an integer, never as a string (`"1"`, `"１"`). Within one table a code has one spelling: two spellings that differ only in case are refused (the later one, in rule order). So a spelling never makes a second conclusion.
  - Rule states are `PASS` (codes complete; `tier2.skill_group` must be set; no `gap`) or `UNKNOWN` (codes missing: at least one of the four codes is null; `gap` exactly `{code: RESOURCE_TO_CONFIRM, owner: SYSTEM, kind: CONFIRM}`). A PASS and an UNKNOWN rule never carry the same four codes. So the state follows from the codes, the gap from the state, and neither can tell two rules' conclusions apart.
  - An unregistered resource id hits the empty template: `NO_MATCH`, not assigned. Its result is `{actions}` only, with no tiers and no gap.
  - No `texts`: this table does not talk to passengers.
- **Conclusion keys:** `tier1.pool` + `tier2.skill_group` + `tier2.priority` + `tier3.pick`. Dotted business keys are paths into the result. As for every STANDARD table, one rule per conclusion: targets whose codes are still missing give the same conclusion and are written as one rule with `when_any`.
- **Reading:** read it as a decision table (`evaluate_stored_table`, format `decision-table/v1`), with `resource_id` required and the other parameters optional. Reading it with the list format `resource-targets/v1` gives `STORED_TABLE_FORMAT_MISMATCH`.

## Switching a stored list to a decision table

- **One way:** under a resource name, a stored resource-targets list may be replaced by a decision-format version. Going back from a decision table to a list is refused (`STORED_TABLE_SCHEMA_CHANGED`), also when the save leaves `declare` out: it does not inherit the decision table's declaration.
- **Route guard:**
  - A stored route table that names the resource table as its `resource_table` compiles against the list: its targets, their entries and the transfer map.
  - While such a route table exists, a decision-format save is refused with `RESOURCE_TABLE_ROUTE_COMPILED`, and nothing is written.
  - So the switch needs the route table to stop naming the list first.
  - **The switch therefore needs a later change to route compiling**, in which route rows that point at a resource return only the resource id and the caller reads the resource table itself. That change is not in this release; until it ships, live routing keeps reading the list.
- **First store:** the first store under the standard name still copies the old head unchanged, so a list stays a list. A decision version follows as an ordinary save.

## Known limits

- **Cross-table race window (accepted, not fixed here):** the route guard reads the stored route tables, then writes. Plugin storage has no compare-and-set, so a route save and a decision-format resource save that interleave exactly can both succeed, after which route evaluation fails (`ROUTE_TABLE_FORMAT_MISMATCH`). This is the same class of window as the existing resource ↔ route checks (v0.5.21 has it too). The plugin does not guard against cross-table concurrency; safe deployment requires externally serialized saves. This review does not verify that any deployment supplies such serialization. A test pins the window (`test_known_limit_a_route_save_inside_the_guard_window_is_not_caught`).
- **The guard sees the indexed route tables:** a route table stored under another name before the route index existed, and missing from it, is not read by the guard.
- **Tiers are not checked against each other:** for example `pick: AGENT_APP` with `tier2.executor: HUMAN`, or a `tier1.pool` missing from its `split`.
- **Corrupt stored values (unchanged from v0.5.20):** if a stored head is valid JSON but not an object (an array, a string or a number), `evaluate_stored_table` raises instead of answering `FAILED` for formats other than scene-topic.

- **Route compiling** still reads only the list format. A route table cannot name a decision-format resource table (route saves are refused, `ROUTE_TABLE_RESOURCE_TABLE_MISSING`, saying the table is in decision format).
- **A null priority is read two ways:** in a PASS rule it means no priority; in an UNKNOWN rule it may be the code still missing. The PASS / UNKNOWN pair check keeps the two apart; whether PASS should need a priority is the standard's to say.
- **Orphan check window:** the first-store orphan check (`check` / `old_orphans`) probes only the 50 versions above the old name's head (`MAX_HISTORY`).
- **Version reuse:** after a rollback cleans up orphan versions, a version number can be used again by a later save.
- **Pre-existing double names:** the single-segment `target.resource` / `triage.resource`, and `supplement.<x>.resource`, fit two formats until first stored; then the stored format wins.
- **After rolling back to v0.5.21 (new in this version):** see Rollback.
- **After rolling back to v0.5.20:** the v0.5.21 limits apply too. A stored `target.scene.topic` and three-segment-name tables cannot be read.

## Historical validation

- The original release recorded 2503 tests passed, 101 skipped, and no failures; `test_v0522_resource_decision.py` provided 127 cases. These are historical results, not the 0.5.24 CI counts.
- Public tests cover declaration-field scope, PASS/UNKNOWN consistency, owner/name validation, refusal messages and paths, resource-format switching, and the known non-atomic guard window.
- Review-driven regressions cover whitespace/case normalization of codes, required `resource_id` quality, duplicate conclusions, and compatibility with the earlier resource-list format.
- For the 0.5.24 review branch, the resource-table compatibility test archives the pinned public v0.5.20 tag. The D14 live-storage reader test separately archives the pinned public v0.5.23 tag. These tests do not establish an independently reproduced v0.5.21 comparison. The v0.5.21 rollback behavior below remains the historical version record.
- The original release recorded clean `ruff check` and `ruff format --check`. External deployment replays are not public reproducibility evidence and do not establish production acceptance.

## Rollback

Reinstall v0.5.21. Historical stored-data behavior recorded for that version:

- **Nothing stored in decision format:** no effect. While the live route table names `dispatch.resource` as its `resource_table`, the guard refuses the decision format there, so with saves made one at a time the live tables roll back with no change.
- **A `.resource` table already stored in decision format locks you out of rolling back to v0.5.21 for that name.** v0.5.21 reads the document (`op=table`, `history`), but evaluating it fails (`STORED_TABLE_NAME` as a decision table, `STORED_TABLE_FORMAT_MISMATCH` as a list), saving it again is refused (`STORED_TABLE_NAME`), and saving a list there is refused too (`STORED_TABLE_SCHEMA_CHANGED`, or `STORED_TABLE_ALIAS_READ_ONLY` / `TABLE_DECLARATION_INVALID` depending on the request). Undoing a first store does not turn it back into a list. Only reinstalling v0.5.22 makes the name usable again; route tables and other tables are not affected (a route table cannot name it: `ROUTE_TABLE_RESOURCE_TABLE_MISSING`).
- So do not store a decision-format resource table while rolling back to v0.5.21 is still an option. Once a caller reads that table in decision format, the rollback target is no longer v0.5.21.
