# v0.5.38 (candidate, not published): every table name carries its task type; decision tables for the other task types

Built on v0.5.37 (`af1dcaf`), the version installed on the target host (read back 2026-11-16: `dmn_json` V0.5.37, from GitHub).
No storage key or table format of an existing table changes; no table migration. A table stored by v0.5.37 validates and
saves as before, **except where an existing name falls under the prefixes this version keeps for the task types' tables**:
`<task type>.<workflow>.` for the six task types and four workflows below, `support.<workflow>.`, and `handle.` (delivery's handle
workflow, below). Check the target host for these five before installing, and stop if any exists:

1. a **route table** whose name begins with such a prefix - its save, and any validation of it, is now refused;
2. a **resource target list** (`resource-targets/v1`) whose name begins with such a prefix - refused the same way; and a
   delivery route table that names such a list as its `resource_table` can no longer be re-saved until the reference is
   removed;
3. a resource target list anywhere (including delivery's `dispatch.resource`) whose `route_tables` **lists** a route table
   under such a prefix - the list itself becomes invalid, and with it the route tables that use it.

4. **any table whose stored name itself begins `support.target.`, `support.triage.`, `support.solution.` or
   `support.handle.`** - from this
   version that spelling means the table without `support.`, so a table literally stored under it can no longer be
   reached by its name;
5. **a table whose parameter's `from_table`, or any declared source `table:<name>` (a parameter's or a text slot's),
   begins `support.target.`, `support.triage.`, `support.solution.` or `support.handle.`** - v0.5.37 took that as the
   name of another table; this version refuses it at validation, so a re-save is refused. With `from_table` evaluation
   fails too, and it was only ever usable with a table of case 4; a declared source is not read at evaluation, so a
   table that has only that still evaluates.

None is expected: no delivery table is named so. For cases 1-3 and 5 `op=table` still returns the stored document and the refusal is at validation (save,
cross-check, evaluation); in case 4 the table can no longer be reached by that name at all. In cases 1 and 2 the route table also no longer compiles.

Read on the target host on 2026-11-16 (not a listing: the plugin has no operation that lists every stored table). Sources: the
ledger of stores, the scheduled snapshot of the six delivery tables, and the inputs of the maintenance app's 4485 runs
(draft runs kept since 11-10, published runs since 10-23). No table name and no reference under any of these prefixes
appears in any of them. Not covered: stores before 11-10 that the ledger does not record, writes that did not go through
the maintenance app, and references late in a save request longer than the run record keeps.

## 1. Names: task type first, four segments

One standard structure serves every top-level task type (delivery, monitoring, quality, annotation, iteration, evaluation,
rollout). Names put the task type first, as ruled on 2026-10-30 (process, then workflow), joined with the five names of
2026-11-02 (`<workflow>.<object>.<judgment>`):

    <task type>.<workflow>.<object>.<judgment>

- task type: `monitoring` / `quality` / `annotation` / `iteration` / `evaluation` / `rollout` (delivery's own task type is
  `support`; the English names are the product owner's);
- workflow: `trigger` / `triage` / `solution` / `handle` - the same four every task type has. The first step of every
  task type is its trigger (why a task of this type is opened, and on what); `target` (定位) is delivery's own name for
  its trigger workflow and stays with delivery's stored names;
- object, judgment: lower-case letter first, then lower-case letters, digits, `_`, at most 32 characters each; the whole
  name at most 64.

**Delivery's tables, spelled in full.** Delivery's task type is `support`. Its tables stay stored under the names they
have (`target.` / `triage.` / `solution.`, and the transitional old names): those are the same names with the task type
left out. From this version each may also be written in full, `support.<name>` - for example
`support.triage.dispatch.route`, `support.target.scene.topic`, `support.solution.fact.feature.<scene>.<segment>` - and the
two spellings are one table: same storage, same versions and compare-and-set, same owner and format rules, same writer
and two-state rules, same old-name migration state. The full spelling is turned into the stored name wherever a name comes
in - the `table` parameter of the store, of `evaluate_stored_table` and of `invoke_solution`; a document's own `table`
(a save body, a draft); a DECISION-node stub's `source.table` - and the storage layer builds every key from the stored
name, so a table can never get a second set of keys under its full spelling. Nothing is re-saved and no storage key
changes.

Limits of this version:
- answers and stored documents name the table by its stored name, not the full spelling;
- a writer's signature is made over the table as it is sent: a request sent as `support.<name>` is signed over
  `support.<name>`, one sent as `<name>` over `<name>`. A signed request cannot be replayed under the other spelling;
- a name inside a document that refers to another table - a route table's `resource_table`, a list's `route_tables`, a
  model parameter's `from_table`, a declared source `table:<name>` (of a parameter of any type, in any kind of table, or
  of a text slot) - must be the stored name. The full spelling is refused there by validation, in its
  own sentence, in every migration state (the fourth review found it was accepted after the first stores and stored
  as written; undo then missed the reference and v0.5.37 could no longer compile the route table);
- an old name is not spelled in full (`support.dispatch.route`, `support.target.scene_entity` are not names).

**Delivery's handle workflow.** Every task type has the same four workflows; the other six could store a table of their
handle workflow (`<task type>.handle.<object>.<judgment>`) and delivery could not (found 2026-11-16 by storing names
through this candidate; the product owner: add it). Delivery's handle tables are named `handle.<object>.<judgment>` -
the same name with the task type left out, as `target.` and `triage.` are - and
`support.handle.<object>.<judgment>` is the full spelling of the same table, under every rule of the full spelling
above. Object and judgment as in every standard name. There is no single-name form (`handle.<name>`), and a name
ending in `.resource` is not one: only triage routes to resources. Decision tables and decision sets only. The owner is
the app that reads the table, unchecked, as for the other task types: delivery's handle workflow has no registered app
yet (`target.` and `triage.` stay bound to theirs). Like every table outside the five chain tables it is outside the
two-state set and takes no writer's signature. Every name that begins `handle.` is kept for these tables.

A name ending in `.resource` is only the routing below.

The owner (`owner.app_id`) is the workflow app that reads the table. The plugin does not check which app that is: the
other task types' workflows are not registered yet (the 10-30 ruling has the owner follow the (task type, workflow)
registry). No route table and no resource target list may take a name that begins `<task type>.<workflow>.`,
`support.<workflow>.` or `handle.`.

Known limits, the same as a solution table without a solution segment: a later version may be saved with another
`owner.app_id`; these tables are outside the two-state (draft / publish) set and take no writer's signature. The
"never a person" check applies to the routing only, not to other tables of a task type.

## 2. Who a task goes to: the same three-tier routing as delivery

`<task type>.triage.<object>.resource` holds the three-tier, human-and-AI resource routing (`role: RESOURCE`, v0.5.22,
with v0.5.37's self-service executor): tier 1 pool, tier 2 skill group and priority, tier 3 how the executor is picked.
Never a person. Only the decision format is taken under such a name (not the old target list), and the `RESOURCE`
declaration is required, exactly as for `triage.dispatch.resource`. Delivery's routing still belongs to TRIAGE.

## 3. Vocabulary export

`op=vocabulary` adds `tables.task_types`, `tables.task_workflows`, `tables.full_names` (delivery's seven chain tables:
full spelling → stored name) and `tables.prefixes.handle`. The schema stays `dmn-json.vocabulary/v1`; the
export's `content_sha256` changes.

## 4. Refusal text

`STORED_TABLE_NAME`'s rule text names six kinds instead of four (the task types' four-segment names and delivery's
`handle.<object>.<judgment>`) and lists the task types and workflows. Code and path are unchanged. A target list or a
route table under a task type prefix is refused with its own sentence, and one under `handle.` with another of its own;
the sentences earlier versions return for every other name are unchanged byte for byte.

## 5. Tool description

The `table` parameter of `evaluate_stored_table` lists the names this version adds: the other task types'
`<task type>.<workflow>.<object>.<judgment>` (with their routing name), delivery's `handle.<object>.<judgment>`, and the
full spelling `support.<name>` of a delivery name. Description text only; the tool's parameters are unchanged.
