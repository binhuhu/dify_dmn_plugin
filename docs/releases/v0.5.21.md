# v0.5.21

**Prerelease candidate. Production compatibility has not been accepted.** On top of v0.5.20 (`4b0e7d3`) this version adds two things:

1. a new stored-table format, `dmn-json.scene-topic/v1`: the scene and topic catalog of the TARGET workflow (定位), with the intent → issue type map stored beside it;
2. standard three-segment decision table names, `target.<object>.<judgment>` / `triage.<object>.<judgment>`, accepted by grammar, so a new decision table no longer needs a plugin release.

**Additive only.** No read, save, refusal, listing, first store, undo or check of any existing table changes. Names that were accepted before stay accepted, with the same behaviour. The only refusal text that changes is the decision-table name rule, which now describes the wider rule.

## The scene-topic format

| | |
|---|---|
| schema / format | `dmn-json.scene-topic/v1` / `scene-topic/v1` |
| name | `target.scene.topic` only. The schema and the name are bound one to one (`STORED_TABLE_NAME` otherwise). Owner: the TARGET workflow. There is no old name, so the first save is an ordinary version 1, with no copy and no migration state. |
| document | `schema`, `table`, `intent_types`, `rows`, `note`, `declare`. Other top-level keys are dropped by the save, as for every stored format. |
| content_sha256 | `digest({intent_types, rows})` of the clean document. The note and the declaration are not part of it. |
| limits | body ≤ 512 KiB and declaration ≤ 256 KiB (unchanged); ≤ 1024 rows, ≤ 64 topics per row, ≤ 32 intents |

**`intent_types`** = `{types, intents}`.
- `types` has exactly the three issue types the TRIAGE workflow routes by: `COMPLAINT`, `CONSULT`, `FEEDBACK`. A fourth type is a plugin change, not a table edit.
- Each type is `{label, panel, marker, weight, associate_entity}`: label ≤ 16 characters, panel ≤ 2, marker 1–8 capital letters, weight an integer 1–9, `associate_entity` a boolean. Panel and marker are unique across the three types.
- `intents` maps each intent code to exactly one type, and every type has at least one intent.

**`rows`**: one row per scene, ascending by `scene_id`, which must be a canonical `M_` scene id.
- **Row fields:**
  - `scene_id`;
  - `name` (≤ 64);
  - `domain {l1, l2, business_mode (null or text), role}`;
  - `definition` (≤ 600);
  - `definition_sha256` (64 lowercase hex);
  - `status`: ACTIVE, SAFETY_TRANSFER, RETIRED or DRAFT;
  - `topics`;
  - `note` (≤ 500);
  - optionally `language_semantics {version, sha256}`.
- **`topics`:**
  - Topic codes are lowercase snake case, unique across the whole table, ascending within a row.
  - Each topic's `allowed_intents` is non-empty and strictly ascending, and every intent is in `intent_types.intents`.
  - Optional `intent_semantics`: a list of `{intent, meaning, required_expression_evidence, specificity}`, at most one per allowed intent, ascending.
- **Matching and errors:** every value is checked with a full match. Every refusal is `SCENE_TOPIC_TABLE_INVALID` with the exact path.

**Declaration**: role `SCENE_TOPIC`, stage `TRANSITION` only (like supplement, resource and route), parameters `{scene_id}`. The declared `states` must cover every row `status`, and the `outputs` must cover every row field.

### Reads (`evaluate_stored_table`, format `scene-topic/v1`)

| inputs | PASS | NO_MATCH |
|---|---|---|
| `{scene_id}` (either spelling) | `{query: SCENE, scene_id (canonical), state, row}` | `row: null` |
| `{topic}` | `{query: TOPIC, topic, state, scene_id, status, allowed_intents, issue_types}` | `scene_id: null` |
| `{topic, intent}` | `{query: TOPIC_INTENT, …, scene_id, status, issue_type, associate_entity, gap_code: null}` | `gap_code: TOPIC_INTENT_UNREGISTERED` |
| `{intent}` | `{query: INTENT, intent, state, issue_type, label, panel, marker, weight, associate_entity, gap_code: null}` | `gap_code: INTENT_TYPE_UNKNOWN` |

- `status` is the scene's row status. A topic of a RETIRED or DRAFT scene still answers, and the reader decides what to do with it.
- A scene id must be one of the two ASCII spellings exactly. Any other input shape or value → `INPUT_INVALID`.
- This format reads only `target.scene.topic` (`STORED_TABLE_NAME` otherwise).
- A stored head that is not a JSON object reads as `ROUTE_TABLE_CORRUPT`.
- Both guards apply to this format only.
- Version and content pins work as for every stored table. `route_table_store` `op=table / version / history` return the whole document.

## Standard decision table names

- **Accepted by grammar:**
  - `target.<object>.<judgment>` and `triage.<object>.<judgment>`, each segment `[a-z][a-z0-9_]{0,31}` (full match);
  - **the whole name at most 64 characters**, as for every stored table name.
  - They are decision tables or decision sets. The prefix fixes the owner: `target.` → TARGET (定位), `triage.` → TRIAGE (分诊).
- **Before:** v0.5.20 accepted only single-segment `target.<name>` / `triage.<name>` plus the mapped standard names, so every new standard-named table needed a release.
- **Bound names keep their format:**
  - the five delivery-chain tables, through v0.5.20's mapping;
  - `target.scene.topic`, which is scene-topic only;
  - a three-segment name whose last segment is `resource`, which is a resource-targets table only.
  - A new three-segment name fits exactly one format.
- **Unchanged:**
  - Old single-segment names work exactly as before.
  - No first-store or alias state applies to the new names: `check` and `undo` refuse them, as for any table outside the five.
- **Who decides which names exist:** this is decided outside the plugin. The plugin checks grammar and owner only.
- **Still needs a release:** a genuinely new row shape (like scene-topic).

## Known limits (unchanged from v0.5.20 unless noted)

- **Orphan check window:** the first-store orphan check (`check` / `old_orphans`) probes only the 50 versions above the old name's head (`MAX_HISTORY`). An orphan further up is not seen.
- **Version reuse:** after a rollback cleans up orphan versions, a version number can be used again by a later save.
- **Pre-existing double names:** the single-segment `target.resource` and `triage.resource` fit both a decision table and a resource table, and `supplement.<x>.resource` fits both a supplement table and a resource table. Until one of them is first stored, either format may take it; after that the stored format wins (`STORED_TABLE_SCHEMA_CHANGED`, nothing written).
- **After rolling back to v0.5.20 (new in this version):**
  - a stored `target.scene.topic` cannot be read (`STORED_TABLE_FORMAT_UNKNOWN`);
  - a decision table or set stored under a new three-segment name can be neither read nor saved (`STORED_TABLE_NAME`).
  - Do not point a live reader at either before rolling back is no longer an option.

## Operator order

1. Install. Read back the identity.
2. Store the first version of `target.scene.topic`.
3. Switch the TARGET and TRIAGE workflows to read it, each in its own release, each behind a replay gate.

Nothing reads the new table or any new-name table before that, so installing and storing change no live behaviour.

## Rollback

Reinstall v0.5.20. Tables stored by this version stay in storage:

- A stored `target.scene.topic`: v0.5.20 cannot read it (`STORED_TABLE_FORMAT_UNKNOWN`).
- A decision table or set stored under a new three-segment name (`target.<object>.<judgment>` / `triage.<object>.<judgment>`): v0.5.20 can neither read nor save it (`STORED_TABLE_NAME`).

Do not point a live reader at either while rolling back is still an option.
