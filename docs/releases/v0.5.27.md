# v0.5.27: plain writer registry (pre-release)

This release builds on v0.5.26 and keeps the single-operator, serial-maintenance scope and
known concurrency limits of [v0.5.24](v0.5.24.md), [v0.5.25](v0.5.25.md) and
[v0.5.26](v0.5.26.md). Target-host installation/upgrade, real business API integration
and production acceptance remain **NOT_RUN**. Publication is not deployment acceptance.

## Changes

- `route_table_store`'s `writers` setting is now `type: string` (a plain form setting)
  instead of `secret-input`. Its format, parsing and signature checks are unchanged.
- `scripts/sign-store-request.py --fingerprint` now computes the same short fingerprint
  without importing plugin dependencies, so it can run on a bare Python interpreter.
  Signing still needs the plugin dependencies. A regression test pins both definitions.
- The bundled privacy notice and setup descriptions now disclose maintenance storage,
  plain-key exposure and the limits of rotation and rollback.
- Signing, verification, runtime `key_fp`, storage keys/formats, reads and refusals are
  unchanged. Version pins move to 0.5.27.

## Cache motivation and limits

This setting change is intended to avoid a host's secret-input decryption cache when
it serves the newly published plain setting. It does not clear the host's cache.
Previously cached registries, other workers and older workflow snapshots may still use
old keys. The exact host version, cache lifetime, upgrade value conversion and
republishing behavior have **not** been verified for the target installation.
There is no guarantee of immediate key rotation or revocation, and no promised cache TTL.

Before the first signed write after a change, compare `op=writers` `key_fp` with
`scripts/sign-store-request.py --fingerprint`. Verify on the actual host that the new key
succeeds and the removed key is rejected. A fingerprint match alone does not prove that
all workers or in-flight runs have been updated. If a key is leaked, an authorized
administrator should contain the affected maintenance entry point and invalidate the
exposed key using the host's supported controls. Do not merely wait for a cache timeout
while the affected entry point remains usable.

## Plain-key trade-off

The entire registry, including every writer HMAC key, is visible to people who can view
or edit the maintenance configuration, and to recipients of its DSL export. Host
snapshots, debugging records, logs and backups may also retain that configuration.
Anyone holding these keys and able to invoke the permitted maintenance application can
sign as any registered writer. The application pin does not prevent that impersonation.
Use this release only when all such people are authorized to possess all writer keys.
If this exposure is unacceptable, do not adopt the plain registry; an older version's
secret-input cache is not itself a safe solution for urgent revocation.

Keys must remain independent random high-entropy values (for example
`secrets.token_urlsafe(32)`), never chosen passwords. Do not share live registries in
issues, repositories or public examples. See the [bundled privacy notice](../../builtin/PRIVACY.md).

## Installation and rollback

Assess 0.5.26 to 0.5.27 in an isolated target-host workflow first. Do not assume the host
preserves or converts the stored setting correctly; inspect the effective registry and
test signed operations. This release does not change the plugin storage format and does
not require restoring a database.

Rollback to 0.5.26 restores a secret-input declaration, subject to the host's migration
and caching behavior. It does not retract keys already copied into exports, logs or
backups. Verify the effective registry after rollback. If exposure exceeded the intended
audience, rotate all affected keys after restoring a trusted configuration and address
historical copies under the host's retention policy. Downgrading to 0.5.23 additionally
restores the older shared-password/direct-save protocol, losing newer governance.

## Verification boundaries

- `test_v0527_writers_plain.py` checks the plain form declaration and absence of
  secret-input parameters; it does not test host caching, migration or revocation.
- `test_v0526_writer_fingerprint.py` checks fingerprint equivalence and operation without
  the plugin's signing dependency.
- Full regression, lint, package checks and exact-commit CI results belong in the
  published release record. A test claim in an uploaded commit is not independent evidence.
- Required target-host checks include cold/hot-cache upgrade, republish, rotation,
  removal of a writer, multiple workers, older workflow snapshots, DSL export/import and
  rollback, including new-key acceptance and old-key rejection. These remain **NOT_RUN**.
