# v0.5.34（预发布）：方案层新架构与插件存储维护

本版基于已发布 0.5.33 的运行时代码，即 0.5.32（`b7137a9`），并把 0.5.33 应急安装包的 1 GiB 存储配额补入源码（见 [v0.5.33](v0.5.33.md)）。第一到三项是方案层新架构，第四项是插件存储维护。范围仍限定为单人、按工作空间串行维护；目标宿主安装、升级、真实业务接口和生产验收仍是 **NOT_RUN**。公开发布不执行部署、表迁移或清理。最终源码提交、独立验证结果、CI 与安装包摘要以 Release 页面为准。

本版支持客服「解决方案」层四表架构，以券方案（场景 M_P_02_04_01）为样例。四张表、一个场景各一张、不分片：查询 → 事实、事实 → 特征、特征 → 现实、现实 → 处置策略。本版给插件补三件新架构的改动，外加一件存储的照看：

1. 同一张决策集里的模型按先后互读（事实 → 特征表里，一个特征读同表先算出的特征）。
2. 能力表（新格式，提议）。
3. 新结构的查询 → 事实表（提议）。
4. 插件存储的照看：存储报错说清是什么、存到一半留下了什么；看一张表占了什么；清理旧版次和半截版次。

下面凡标「提议」的名字（格式名、表名、角色名、键名、错误码），都**待 Brian 定**。

## 一、同表模型按先后互读

### 怎么写

在模型的一个 table 参数上同时写两样：

- `from_table`：本表的表名；
- `in_set: true`：提议的新键。

参数名就是本表里另一个模型的键。

```json
"parameters": {
  "deduct_compare": {"type": "table", "record_required": true, "nullable": false,
               "allowed_quality": ["KNOWN", "UNKNOWN"],
               "from_table": "solution.fact.feature.M_P_02_04_01", "in_set": true}
}
```

（`deduct_compare` 是本表里另一个模型的键，比如「抵扣比对」这个特征。）

条件照「表间衔接」的写法读它：`[parameters, <名>, state]`、`[parameters, <名>, result, <键>]` 或 `quality`。

### 求值

- 插件按先后求值：被读的模型先求，它的结果按「本表回执」的形状接给读它的模型。这个回执的来源是本表本次读到的那一版，`source_refs` 写成 `stored-table:<本表>@<版本>#<模型>`。
- 读它的模型的 `chained_parameters` 记下读了哪个模型、哪一版、哪几条规则、什么状态。
- 只点名读它的模型时，被读的模型也一起求、一起回报，回执里的 `models` 按求值先后排。
- 被读的模型没求成（BLOCKED / FAILED）时，读它的模型这个参数算缺，按表自己的 `missing` 处理。这和上一张表没求成是同一条规矩。
- 调用方不传这个参数；传了就整次 `INPUT_INVALID`（「不要传」），`undeclared = IGNORE` 时也拒。

### 存表拒（`DECISION_SET_INVALID`）

- 读表里没有的模型；
- 读自己；
- 绕成环；
- 读的模型是 COLLECT：它可能出好几份，读的一方只能拿到第一份，所以不收；
- `in_set` 参数的 `from_table` 不是本表；
- 一个名字在一个模型里标了 `in_set`，另一个模型却把同名参数当调用方给的量，或当别的表的回执。

另外：`in_set` 只能写 `true`，只写在带 `from_table` 的 table 参数上，决策表（非决策集）不收（`DECISION_TABLE_INVALID`）。声明里这个参数的来源写 `table:<本表>`，沿用 0.5.19 的核对。

### 兼容

没标 `in_set` 的参数照 0.5.32 的意思，`from_table` 写本表的也一样：本表回执被拒（`DECISION_SET_SELF_READ`），不传就算缺。0.5.32 的参数键集合拒收不认识的键，所以已存的模型里不可能有 `in_set`。已存表的读法、求值结果、模型顺序、报错都不变。

为什么要一个标记：最初的写法只看「`from_table` 是本表、参数名是兄弟模型的键」。独立复审指出，这会让已存的这类表换一种意思，甚至整张读不了。加了标记之后，复审第二轮无高、中。

### 测试与复审

- `plugin/tests/test_set_internal_reads.py`，26 个。
- 变异测试 16 个，全部变红：成环、读不存在的模型、读自己、调用方传同表参数、求值先后（三种改法）、同名冲突、来源版本、存表时不核先后、旧表不看标记、标记写法、标记读本表、读 COLLECT、决策表带标记、声明来源核对。

## 二、能力表（新格式，提议）

能力表跨场景、由平台维护：一行一个能力，按能力号查一行，做法同「场景与话题」表。代码在 `plugin/dmn_client/capability_catalog.py`。

2026-11-11 补充：能力分查询和动作两种，**动作能力暂时不能调用**。

### 提议的名字（待 Brian 定）

| | 名字 |
|---|---|
| 格式 | `dmn-json.capability-catalog/v1`（求值格式 `capability-catalog/v1`） |
| 表名 | 只有一个：`platform.capability.catalog`。不另占名字：0.5.32 能存的表照样能存；同一个名字下存表不许换格式，所以能力表和别的表不会混在一起 |
| 错误码 | `CAPABILITY_TABLE_INVALID` |

### 一行写什么

| 键 | 意思 | 取值 |
|---|---|---|
| `capability_id` | 能力号 | 唯一，按升序排 |
| `name` | 显示名 | |
| `domain` | 一级域 | 大写码，如 `MARKETING` |
| `entity` | 实体 | 小写码，如 `coupon` |
| `face` | 查询还是动作 | `QUERY` / `ACTION` |
| `kind` | 能力类型 | 查询能力取 `LIST` / `DETAIL` / `SEARCH` / `READ`（列表 / 详情 / 检索 / 识读）；动作能力写 `null`（动作怎么分类还没定） |
| `inputs` | 入参 | `{入参名: {required: true/false}}` |
| `facts` | 得到的事实 | 每条 `{fact_id, name, field, type, unit, object}`，可加 `alternate_of`。依次是：事实号、显示名、取返回的哪个字段、类型、单位、属于哪个对象；`alternate_of` 写这条事实的主来源能力。查询能力至少一条；动作能力写 `[]` |
| `fan_out` | 一对多 | `{input, max}`：对这个入参的每一个各查一次，上限 1–100；不是一对多就写 `null` |
| `call_ref` | 怎么调的引用 | 只收 `registry:<服务>/<操作>`：服务是小写字母开头，可含小写字母、数字、`_`、`-`；操作是字母、数字、`_`、`-`，最多带一个 `.`。地址、端口、协议、账号、查询串、IP、主机名都写不进这个格式。操作部分另有三条拒法：某一段是 token、pwd、ak、sk、jwt、signature 一类整段词；含 secret、passw、apikey、api_key、bearer、credential 字样；有一段 12 位以上、大小写和数字混着（像密钥）。都是凭写法猜的，登记时仍要人看 |
| `note` | 说明 | 可选 |

### 存表检查

- 能力号唯一、升序。
- 同一个事实号只能有一个主来源。另一个能力也给这条事实时，要标 `alternate_of = 主来源能力号`（备选来源），而且类型、单位、对象要和主来源一致。
- 同一个能力里事实号不重复。
- `fan_out.input` 要是本行的入参。
- 各个码都在闭集里。

### 读法（`evaluate_stored_table`，format `capability-catalog/v1`）

- `{"capability_id": …}`：返回那一行。状态是 `PASS` 或 `NO_MATCH`，并带 `callable`：查询为 true，动作为 false。
- `{"domain"?, "entity"?, "kind"?, "face"?}`，写一到四个：返回同时满足这些条件的行，按能力号排序，每行带 `callable`。

### 测试

- `plugin/tests/test_capability_catalog.py`。
- 样例 `plugin/tests/capability_fixtures.py`：券方案用到的六个查询能力（订单详情、账单结果、预估信息、券包、券详情、券批次），外加一个动作能力（补发券）。入参和一对多取自现网券查询应用的入参声明与取数登记；地址、凭据不进表。事实号、域码是样例写法，也待定。
- 变异测试：复审两轮修完后，第二件重跑 27 个，全部变红。

## 三、新结构的查询 → 事实表（提议）

查询 → 事实这一步像接口：输入是「已知什么」，输出是事实。代码在 `plugin/dmn_client/search_plan.py`。

### 一行写什么

一行一个能力调用。条件问哪些量已知；结果写三样：

- `capability_id`：调哪个能力；
- `bindings`：入参从哪来，`{入参名: 已知量}`；
- `facts`：要哪些事实；不写 = 这个能力得到的全部。

已知量有两种：请求里给的对象号，和已经得到的事实。

求值是表的 COLLECT：给当前已知量，返回这一轮成立的全部行，插件只做一轮。一轮一轮反复求、真正去调接口，是流程里「查询执行」节点的事，插件里的 `query_executor.py` 没动。

### 两种形状怎么并存（提议）

还是 `dmn-json.decision-table/v1`、COLLECT，表名照旧 `solution.search.fact.<场景号>[.<方案段>]`。区分靠声明里的角色：新形状写 `role = SEARCH_CAPABILITY`（提议），旧形状照旧是 `SEARCH_FACT`。

为什么选角色、不另起格式名：

- **旧表一字不变。** 两种形状求值完全一样（就是普通 COLLECT），所以旧表的求值结果一字不变；流程里的 `format` 也不用换。
- **两种形状互相排斥。** 两个角色的业务键不重叠：`SEARCH_FACT` 要 `fact_id`，`SEARCH_CAPABILITY` 要 `capability_id + bindings`。哪种写错了，对方的检查都会拒。
- **新检查跳不过。** `solution.search.fact.` 名下的表，结果里只要同时有 `capability_id` 和 `bindings`（就是一次能力调用），就必须带这个角色的 STANDARD 声明，否则拒存；决策集则提示只能存成决策表。旁边写不写 `fact_id` 都一样：复审第二轮指出，若按「没有 `fact_id`」来认，加一个 `fact_id` 就能把所有检查绕开。只写 `fact_id`、只顺带写了是哪个能力给的旧形状，照 0.5.32 存。
- **旧格式名下没法换形状。** 存表时不许换 schema（`STORED_TABLE_SCHEMA_CHANGED`）。若另起格式名，已有的查询 → 事实表名下就换不了形状。
- **代价。** 回执本身不标形状。执行查询的节点按结果里有没有 `capability_id` 认，或者在流程里固定读哪张表。

声明里不写 `role` 的查询 → 事实表，照旧按 `SEARCH_FACT` 认。

### 声明（STANDARD）

在 0.5.19 起的标准写法（`parameters`、`outputs`、`states`、`rows`）之外，多两个键（提议）：

- `capability_table: {table: platform.capability.catalog, content_sha256}`：钉住核对用的那一版能力表；
- `request_inputs`：请求里可能给的量。

### 存表检查

只看这张表本身就能核的：

- 命中策略是 COLLECT；是决策表，不是决策集；stage 是 STANDARD。
- 参数不读别的表，而且都写 `record_required = false`、`allowed_quality` 含 KNOWN 和 UNKNOWN。
- 声明里参数的来源：请求里给的写 `request:<名>`，得到的事实写 `fact:<名>`。
- 每条成立的行 state 写 PASS；`result` 只有 `actions: []`、`capability_id`、`bindings`，外加可选的 `facts`。
- 绑定的来源要是表的参数。每组条件里，绑定来源都要问过「已知」，即 `[parameters, 名, quality] eq KNOWN`。
- 读某个量的值的条件，同一组里要先问过它已知。大小比较（lt / lte / gt / gte）只用在不可空的数值或字符串参数上，和同类的值比：取到 null 或别的类型时，大小比较判不了，整张表会卡住。
- 问「已知吗」的条件只用 eq / ne / in / exists；对 quality 做大小比较，判不了，整张表会卡住。
- 一行没中的模板 state 写 NO_MATCH，`result` 只写 `actions: []`，不点名能力。
- 模型本身的毛病，报错路径写 `model.…`；声明的毛病写 `declare.…`。

拿钉住的那一版能力表核对的（存表时插件按内容摘要找这一版，`SEARCH_TABLE_INVALID`）：

- 能力号在能力表里，而且是查询能力。**动作能力暂不能调**，拒。
- 入参名和登记的一致，必填的都绑了。
- 要的事实是这个能力给得出的。
- 不在 `request_inputs` 里的量，都是某个能力登记过的事实，而且参数类型和登记的类型一致（number 可以收 integer）。
- **可达性**：从请求里可能给的量出发，一轮一轮推哪些行能成立、成立后得到什么。永远成立不了的行拒存，报出是哪一条、缺什么。
- 钉的那一版能力表不在插件里时，报 `SEARCH_CAPABILITY_TABLE_MISSING`。

### 三值规矩

量没取到时，问「已知吗」的条件是 UNKNOWN，整张表会卡住。避免的办法是调用方传 `missing = "UNKNOWN"`：插件把没传的参数按 quality UNKNOWN 填上，这类条件就是 FALSE。所以「查询执行」节点读这张表要传 `missing: "UNKNOWN"`；不传时，缺一个量就 `BLOCKED / INDETERMINATE_MATCH`，这条有测试钉住。

读值的条件旁边若已有同一个量的「已知」条件，这组条件在量没取到时就是 FALSE，不会是 UNKNOWN（AND 里 FALSE 优先）。存表要求这样写，大小比较另有上面那条限制，所以一轮求值不会因为某个量还没取到、或取到了 null，而卡住。前提是调用方给的值合参数类型；类型不合是调用错，整次 `INPUT_TYPE_MISMATCH`。

## 四、插件存储的照看

### 为什么

2026-11-11 15:40 起现网存表全部回 503「插件存储读写失败，稍后再试」，读正常，37 分钟后装 0.5.33 放宽配额才恢复。当时：

- 回包只有一句话，看不出是空间满还是存储服务故障；平台原话被插件吞掉了。
- 一张方案层的表存到一半（版本号那份写了、头版没写），这个表名之后再也存不进去，插件没有办法收拾。
- 插件没有办法看一张表占了多少，也没有办法删旧版次。

### 改了什么

| 哪里 | 改动 |
|---|---|
| 存储报错 | 平台因空间不够拒写回 507 `STORED_TABLE_STORAGE_FULL`；其他存储故障仍回 503，文案照旧，只有存表留了半截或结果不明时换成说该做什么。两种都带 `storage_failure`：哪次调用失败、是不是空间满。平台原话只进插件日志。签名模式下签名使用记录因空间被拒，也回 507 |
| 存到一半 | 五张交付链表以外的表：头版之前失败的，收回已写的几份（`outcome: NOT_SAVED`）；头版写失败的不收回，回包说可能已写进去（`UNKNOWN`），并带这次的存表号供核对；收不干净的说留了半截（`HALF_WRITTEN`）。闸报告的写入也纳入回收。撤销首存时替别的路由表重存的那一版不回收 |
| `op=usage` | 新增，只读。一张表各版次、各附属记录的键数与字节，头版之上的半截版次 |
| `op=prune` | 新增。先出计划（任何应用可调，不删），再带计划摘要执行（只认「路由表维护」应用；签名模式要写手签名，但不写签名使用记录，空间满时也能清；重发因计划已变被拒）。删最新 `keep` 版之前的旧版次；`half_written: true` 时一并删存了超过 10 分钟的半截版次；版本号那份删前再核存表号。五张交付链表和能力表拒清理（能力表的版次被查询 → 事实表钉着）。执行留操作记录 |
| 版本 | 0.5.33 → 0.5.34；清单配额保持 1 GiB |

不变的：已存数据的键名、份数、格式；任何表的格式；求值；调用方案。

变了的回答：空间满原来回 503 `ROUTE_TABLE_UNAVAILABLE`（签名模式下是 503 `STORED_TABLE_REPLAY_UNAVAILABLE`），现在回 507 `STORED_TABLE_STORAGE_FULL`。只认 503 才重试的调用方要认 507；仓内的页面、脚本、端点都没有依赖旧码。其他存储故障仍回 503 原错误码，多一个 `storage_failure` 键；文案照旧，只有存表留了半截或结果不明时换成说该做什么。

详见 [插件存储的照看](../plugin-storage-care.md)。

### 升级与回退

- 升级插件不自动改写、迁移已存表，也不自动切换表的 schema 或声明角色。采用新形状是单独的表和流程变更，不是换安装包就完成迁移。
- **只继续使用旧形状表时**，回退装 0.5.33 后旧表仍可校验、求值和追加保存，原有历史字节不变。0.5.33 的运行时代码是已发布 0.5.32（`b7137a985b73e9794f68efdb7d1729959167c7a8`）。
- **已采用新形状时不能只换回旧包**：带 `in_set` 的决策集和 `dmn-json.capability-catalog/v1` 能力表，旧版虽能取出原始文档，却不能通过旧校验或按其新语义求值。
- `SEARCH_CAPABILITY` 仍用旧 decision-table schema，旧版的通用 COLLECT 求值可以返回同样的行，但旧声明校验拒绝新角色及声明键，不能据此认定保存或能力调用链受支持。执行查询节点也不会因回退自动改成旧结果消费方式。
- 回退前盘点流程使用的表、头版和固定版本引用，确认仍是旧版支持的形状；已经采用新形状的流程须先另行验证旧形状表及其消费流程，并保留新旧包和经核验的备份。本版不提供新形状到旧形状的自动转换，不承诺同名表可跨 schema 覆盖保存。
- 旧版不支持 `usage` / `prune`；实测旧 `run_entry` 返回 404 `NOT_FOUND`。已经执行 `prune` 删除的旧版次不会因回退重新出现，固定引用也不会恢复；恢复备份属于另一项操作，不能用换包代替。
