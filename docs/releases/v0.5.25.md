# v0.5.25: scene-based routing without topic lists; M_ spelling guard

This release builds on v0.5.24 and keeps all of its scope and limits: one human
operator performing serial maintenance, signed draft and publish for the five
delivery-chain tables, and the known cross-process concurrent replay/write risk
(see [v0.5.24](v0.5.24.md)). Target-host installation/upgrade, real business API
integration and production acceptance remain **NOT_RUN**. Publication is not
deployment acceptance.

It changes two things:

1. A `CURRENT` application in a v3 route table no longer requires `topics` / `intents`.
2. A save may not silently respell a table stored in the `M_` scene-id spelling back to
   the legacy spelling; a real rollback must say so with `scene_spelling_rollback: true`.

## CURRENT applications: only the request contract is required

Routing is by scene. Topics and intents are labels carried inside a scene and do not
narrow routing.

- `_solution_v3`: for `status == CURRENT` only `request_contract` is required
  (`ROUTE_TABLE_SOLUTION_INCOMPLETE @solutions.<app>.request_contract`). `topics` /
  `intents` may be absent, `null` or `[]`; they are stored as `[]`.
- Lists that are written are validated exactly as before (code format, no duplicates,
  limits) and stored in the order written.
- The callability gate message (`ROUTE_TABLE_SOLUTION_NOT_CALLABLE`) now asks for the
  request contract only.
- The route editor no longer blocks a `CURRENT` application with empty lists and says
  that the lists are optional.
- Reads, evaluation, `invoke_solution`, the routing result and every other refusal are
  unchanged. Every table stored before 0.5.25 carries lists, so it validates to the same
  document and the same `content_sha256`.

**Downstream order.** A workflow that still decides applicability with
`topic in topics and intent in intents` treats an application with empty lists as
"not applicable" for every issue. Remove or relax such checks downstream (and in any
generator or release gate that writes or enforces them) before an editor clears the
lists of an application that is in use. Installing 0.5.25 alone does not clear any list.

## M_ spelling-regression guard

A document whose scene ids are all in one spelling is stored in that spelling (since
0.5.9). Without a guard, once a table is stored in `M_`, any later save from a tool
that still writes the legacy spelling would turn the whole table back to legacy.

- Such a save is refused with `400 SCENE_SPELLING_REGRESSION` at
  `scene_spelling_rollback`; nothing is written.
- A real rollback sends `scene_spelling_rollback: true` (only the JSON literal `true`).
- `M_` over `M_`, a mixed-spelling save (stored in the table's spelling, as before) and
  legacy over legacy are unaffected.
- The decision is made from the stored table and the sent document themselves, not from
  `respell`'s receipt. If the stored table's spelling cannot be read and the sent
  document is legacy, the save is refused with `503 ROUTE_TABLE_UNAVAILABLE` unless
  the flag is set. If the table is `M_` and the sent document's spelling cannot be
  read, the save always fails closed with `503 ROUTE_TABLE_UNAVAILABLE`, even when
  `scene_spelling_rollback: true` is set.
- The guard sits on the save path every table uses (`route_store.run_op`), so on the
  five delivery-chain tables it runs both in `draft_save` (dry-run save) and in
  `publish`.
- `scene_spelling_rollback` is a registered request key (`vocabulary.REQUEST_KEYS`), so
  it is not reported as an unknown key. A `draft_save` that carries it keeps it in the
  draft body, and publishing that draft performs the rollback. A version rollback
  (`draft_save` with `from_version`) accepts and forwards it too.
- `scripts/scene-spelling-gate.py`: the rollback step sends the flag; on a head that has
  the guard, it first checks on a throwaway copy that the same save without the flag is
  refused. The gate accepts `dmn-json.supplement-requirements/v2` and records a table
  that is already stored in `M_` as `already_canonical`.

Apart from the `503` edge below, nothing that is accepted by 0.5.24 is refused by 0.5.25
unless it would turn an `M_` table back to legacy without the flag.

Known limits:

- The route editor page has no control for `scene_spelling_rollback`. Loading an older
  legacy version in the editor and saving it over an `M_` table is refused; a deliberate
  rollback goes through a signed API request (for example `scripts/sign-store-request.py`)
  that carries the flag.
- `undo` (the 0.5.20 undo of a standard name's first store) does not run the guard. It
  moves stored versions between names without respelling them.
- The guard compares spellings. A version with no scene ids at all has no spelling, so a
  legacy save over it is accepted; an `M_` table can therefore reach legacy content
  without the flag through an intermediate save that removes every scene id. That
  intermediate save is a visible, content-destroying change, not a silent respell.
- If the stored table's spelling cannot be read and the sent document is legacy, the save
  is refused with `503` (no such table is known to exist; this is the one theoretical case
  where 0.5.25 refuses something 0.5.24 accepted).

## Installation and rollback

- Install from GitHub release `v0.5.25` after v0.5.24; the writer protocol, maintenance
  application pin and endpoint settings are unchanged.
- No storage key or format changed. Rollback to v0.5.24 is safe **only while no stored
  route table has a `CURRENT` application with empty `topics` / `intents`**. v0.5.24
  re-validates a stored route table when it reads it (`invoke_solution`, materializing a
  `PLUGIN_STORAGE` route model for `evaluate_decision`, the resource-table cross-check),
  so such a table would be refused as
  `ROUTE_TABLE_SOLUTION_INCOMPLETE` for every read and invocation, not just the next
  save. Before rolling back, write the lists again (or move those applications out of
  `CURRENT`) and publish on 0.5.25, then read back.
- After rollback the spelling guard is gone: a legacy save over an `M_` table respells
  it back without the flag, as on v0.5.24.
