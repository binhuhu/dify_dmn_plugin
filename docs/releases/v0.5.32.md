# v0.5.32：路由方案表按比例分流量（试验方案），取代 0.5.31 的按份额分流

这是一个**预发布**版本，接在已发布的 0.5.31（`65c21e8`）之后。本说明延续 0.5.31 的范围和风险：单人、按工作空间串行维护；目标宿主安装、升级、真实业务接口和生产验收仍是 **NOT_RUN**。发布、离线测试和 CI 通过不代表现网已满足升级条件。

## 改了什么

路由方案表的方案行，除了原去向，可以再挂一个「试验方案 + 比例」。同一个场景的进线按比例落到两个方案上，每次路由结果记下落到了哪一边。详见 [在插件里配置场景、方案和路由 · 试验方案](../route-table-editing.md)。

| 哪里 | 改动 |
|---|---|
| 表格式 | v3 路由表的方案行可选多一段 `trial {app_id, share, note?}`。表的格式名不变（仍是 `dmn-json.route-table/v3`），不挂试验的行不多任何键 |
| 存表校验 | 拒存：转接或资源去向的行挂试验；试验方案和原去向相同；试验方案没登记或不是 `CURRENT`；原去向本身不是 `CURRENT`；比例不是 0–100 的整数；一行多于一个试验；v2 表挂试验。新错误码 `ROUTE_TABLE_TRIAL`、`ROUTE_TABLE_TRIAL_SHARE`；没登记、不是 `CURRENT` 沿用 `ROUTE_TABLE_UNREGISTERED_APP`、`ROUTE_TABLE_SOLUTION_NOT_CALLABLE` |
| 路由求值 | 新存根格式 `routing-table/v5` = `routing-table/v4` + 可选入参 `split_key`（分流键）+ 决策字段 `trial`（落到哪一边、当时比例、这一行有没有挂试验、是否参与了分流、算出的数）。算法确定：同一分流键在同一行上每次结果相同，可事后重算。0% 保留试验但不放量，100% 把带有效分流键的进线全送试验；没带分流键一律走原去向并写明未参与分流 |
| 存表闸 | 试验方案算「有行指着」，0% 时仍然如此、仍须 CURRENT。停掉某个方案唯一的试验而它仍是 `CURRENT`，按没有行指向拒，同一次存表把它转候选、退役或删登记即可 |
| 调用方案 | 不变。试验方案是 `CURRENT`，照旧能调 |
| 插件自带的编辑页 | v3 表的方案行可「加试验方案」：选应用、填比例，显示两边各占多少，可改可去掉；保存前先挡住插件会拒的写法。此前的页面存表时试验原样带回，但不显示、也去不掉 |

## 取代 0.5.31 的按份额分流

0.5.31 发布过另一种分流写法：去向种类 `SOLUTION_SPLIT`，一行分给 2–4 个方案应用、份额合计 100、只看分流键、路由结果里不记落到哪一边。本版将其替换为按行配置的两路试验，比例允许 0–100%，使用「分流键 + 行」计算，并在结果中记录落边和比例。0.5.31 里同版并入的方案层表名方案段不受影响，原样保留。

| | 0.5.31 | 0.5.32 |
|---|---|---|
| 写在哪 | 去向换成 `SOLUTION_SPLIT` | 原去向不变，行上挂 `trial` |
| 几路 | 2–4 | 两路 |
| 比例 | 每个 1–99，合计 100 | 试验方案 0–100 |
| 怎么算 | 只看分流键 | 分流键 + 场景、类型、阶段 |
| 结果里 | 和普通方案行一样，轨迹里记桶号 | 多一个 `trial` 字段 |
| 怎么生效 | 节点多绑 `split_key`，格式名不变 | 新格式名 `routing-table/v5`，节点绑 `split_key` |

**从 0.5.31 升级前要做的：**

- 核对实际宿主上所有将被读取的路由表，把每一行 `SOLUTION_SPLIT` 改成一个方案应用去向并存表。带着这种行升级，读这张表的路由求值全部失败、调用方案也拒调，说明里会写怎么改（`ROUTE_TABLE_TARGET`，`routes[i].target.kind`）。本次发布未直接核验生产宿主；不能由离线快照推断当前配置。保留的历史版本、草稿或恢复流程也不能继续引入旧分流行。
- 在 `routing-table/v2`–`v4` 节点上按 0.5.31 的做法绑了 `split_key` 的流程，改成 `routing-table/v5`，或去掉这个绑定，否则 `PARAMETER_BINDING_MISMATCH`。
- 同一个分流键升级前后可能落到不同的方案（算法不同）。

拿掉的代码：`route_table.py`、`decision_executor.py`、`two_state.py`、编辑页、`scripts/accept-route-table-v3.py` 里 0.5.31 为分流加的部分，以及它的测试（`test_v0531_route_split.py`、两处页面测试）；这些文件回到只含方案段改动时的样子，再加上本版的试验方案。

## 格式名怎么升的

按仓内惯例：**路由结果多了字段，升求值存根的格式名**（`routing-table/v3` → `v4` 加 `solution` 块时就是这样），所以新增 `routing-table/v5`。**表文档的格式名不升**：`trial` 是方案行上的可选键，既没有试验、也没有旧 `SOLUTION_SPLIT` 的普通表保持原行为；要是升表格式名，加试验、删试验都得来回改格式名，还会撞上「v3 表不能存回旧格式」那道检查。

## 兼容

- **既没有 `trial`、也没有 `SOLUTION_SPLIT` 的普通表**：校验结果、内容摘要、存下的文档、`routing-table/v2` / `v3` / `v4` 编译出的规则和模型来源，与 0.5.29（`df817f3`）逐字节相同（测试里钉了在 `df817f3` 上算出的摘要；0.5.30、0.5.31 对没有分流行的表也没有改这些）。
- **未按 0.5.31 方式绑定 `split_key` 的 `routing-table/v2` / `v3` / `v4` 流程**：不受影响。表里就算挂了试验，这些格式也不分流，每一行走原去向，模型来源多一个 `trials_ignored`（被略过的试验行数）。
- **`routing-table/v5` 的流程**：节点要绑四个入参（多 `split_key`）。分流键可以不传值，但绑定要有。
- **0.5.31 的 `SOLUTION_SPLIT` 行和它的绑定方式**：不兼容，见上一节。
- 两条拒存说明的措辞变了（码和路径不变）：行的键不对时的「每条路由 = …」、`ROUTE_TABLE_CURRENT_UNROUTED`。
- 回执里 `routing-table/v5` 的结果比 `v4` 多一个 `trial` 字段；下游要读它的流程按新格式名申报。

## 上线顺序

1. 先完成上面的实际宿主升级检查，并保存可恢复的应用配置和表快照，再升级插件。只有确认没有旧 `SOLUTION_SPLIT` 行、没有旧格式的 `split_key` 绑定、没有预先挂试验的表时，才可预期普通路由保持原行为。本次发布不替代这些检查，也不执行生产部署。
2. 分诊查路由时换成 `routing-table/v5` 并传分流键（流程发布，要重绑）。
3. 查看器放开「加试验方案」的入口。

顺序反了的后果：先挂试验、分诊还没换格式——试验不生效（全走原去向），不会出错；先放开入口、插件还没上——旧插件读不了带试验的表，路由求值和调用方案都失败。

## 降级

**装回旧版插件（含 0.5.31）之前，先把所有当前路由表里的试验段去掉并存表；读路由的流程先换回 `routing-table/v4` 并去掉分流键。** 停掉某个方案唯一的试验时，同一次保存须把该方案转候选、退役或取消本表登记，并遵守跨表状态一致规则。旧版读到带试验的行会整张表校验失败，读这张表的路由求值全部失败，调用方案也拒调。历史版本和草稿保留，但在旧插件上不得恢复或发布仍含 `trial` 的内容，也不能使用 v5 存根。本流程不要求删除历史数据或覆盖数据库。清理后必须用旧版本读方核验实际将使用的头版与流程，再降级插件。

## 已知限制

- 编辑页的自动化回归使用合成数据和真实签名端点，不能替代目标宿主验收；最终浏览器结果见 Release。页面不预览某个分流键落到哪一边，也不能改试验说明。
- 试验方案的请求合同必须是交付编排认得的。保存时沿用现有规则：`CURRENT` 必须写请求合同，不新增合同白名单硬闸。不变量报告会检查原去向和试验方案两侧；任一侧合同不受支持时报告 `CONTRACT_NOT_BUILT`，整行不计为可调用。该报告不是实际业务接口验收。
- 只做两路。不做：两个方案同时跑、按用户属性分流、三路以上、质量对比报表、查看器界面、分诊与交付编排的流程改动。

## 审查修复

- 试验行两侧应用编号按完整 UUID 匹配，拒绝末尾换行等不精确编号，避免保存后的路由编号与调用层归一化后的编号不一致；普通旧行的规则不扩大修改。
- 不变量报告覆盖两侧请求合同，一行仍只计一次，避免只检查原去向却漏报试验方案。
- 补充固定公开 v0.5.31 的跨版本回归及真实签名端点的试验编辑浏览器覆盖。最终验证结果见 Release。

## 验证范围

- 新增四组测试（表格式、分流求值、存表闸、调用方案），全部用合成数据和内存存储；编辑页覆盖试验比例 0/100 边界及非法输入。
- 候选提供方记录了旧 1–50 范围的变异验证，以及改为 0–100 后的 10 处补充变异验证；这些记录不是本次独立复验结果。
- 上述候选变异验证为提供方记录；最终发布提交会重新执行适用的 Python、Node、页面、格式、清单权限和打包核对。精确提交、测试数、跳过原因、CI 链接、安装包摘要及身份统一记录在 Release，不把候选计数当作最终结果。
- 目标宿主安装与升级、真实分诊流程换格式后的联调、真实业务接口与生产验收均为 **NOT_RUN**。

## 发布边界

保留停试验时的 CURRENT_UNROUTED 闸，紧急停试验也须按上述顺序处理。原去向挂起的行不能挂试验。包未签名，遵循宿主签名和安装策略。既有 OPEN/SIGNED、无跨进程 CAS/事务、结果不明及尽力归属记录限制不变。README 的个人学习、本地评估及商业使用政策不变。
