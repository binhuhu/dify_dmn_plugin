# v0.5.28: open mode; the solution layer's four table names

This release builds on v0.5.27 (see [v0.5.27](v0.5.27.md) and earlier notes for scope and limits).
Target-host installation/upgrade, real business API integration and production acceptance remain
**NOT_RUN**. Publication is not deployment acceptance.

## 1. Open mode (the default)

The maintenance node's `writers` setting chooses the mode. Open mode is the default.

- **Empty, missing, only `#` comment lines, or the single word `OPEN`** (any case): **open mode**.
  Requests that run the maintenance application need no signature. The five delivery-chain tables
  are saved directly again (`op=save`, as before v0.5.24), with the checks a draft gets: no
  unregistered top-level key (`STORED_TABLE_UNKNOWN_KEY`) and no reference to a table outside the five
  (`STORED_TABLE_REFERENCE_OUTSIDE_FIVE`). Drafts and publishes still work and need no writer. Writes
  to the five still count only from the pinned maintenance application.
- In open mode a request that **carries a writer** is refused (`403 STORED_TABLE_OPEN_MODE_WRITER`):
  that is every editor-endpoint call (the endpoint still requires `X-Route-Writer`, unchanged) and
  every signing script. The editor endpoint is not guarded by the host's login, so open mode does not
  take it.
- **Writer lines**: **signed mode**, exactly as v0.5.24–v0.5.27.
- **`OPEN` mixed with writer lines, or any malformed line**: a mistake, not a default. Writes to the five are
  refused: direct saves still require the publish path, and signed draft/publish operations report
  `STORED_TABLE_WRITERS_INVALID`. A value that is neither text nor missing is not open mode either.
- `op=writers` reports `mode`: `OPEN` (including empty or missing) or `SIGNED`.

Every other check is unchanged in both modes: callability gate, formats, version numbers and history,
scene-spelling guard, rollback by version.

Costs of open by default (written out on purpose):

- The protection "a lost or mistyped setting never opens the tables" is gone. An empty or missing
  setting, including deleting every writer line from a signed registry by mistake, means open mode.
- In open mode whoever can run the maintenance application can change the five tables, and the
  plugin does not record who did; only the host's run records do.
- Before relying on open mode, check the maintenance application's web app and API access in the
  host: if either is enabled and reachable without login, the five tables are effectively open to
  whoever can reach it.
- Single operator, serial maintenance: version numbers detect some stale requests but do not keep
  concurrent writes apart. Both writers can succeed and one can overwrite the other.
- A direct save does not go through the publish window (gate report, release reference).

Known limits of open mode (review rounds 2 and 3):

- Open is the default: a registry emptied by mistake opens the five to unsigned writes.
- Open-mode writes are **not serialized** by version checks (`expected_version`, `expected_draft`).
  They do not take the signed path's in-process lock, so the same process can race as well as separate
  workers. Version checks are not atomic compare-and-set. Keep the single-operator, serial scope.
- OPEN has no HMAC verification, signature freshness check or signed-request replay receipt. Stale
  version/draft checks catch some repeated requests, but are not a general replay guarantee. Even
  with one serial operator, a previously accepted unsigned `draft_save` can recreate a discarded
  draft while the live version is unchanged. SIGNED mode rejects the consumed signed request.
- A storage error does not prove that nothing changed. After an uncertain result, stop automatic
  retry, overwrite and deletion until an authorized operator verifies authoritative fresh state.
- Drafts, publishes and saves carry no writer or publisher identity in open mode.
- A direct save skips the publish window (`gate_report`, `release_ref`, approval for a FAIL gate).
  Use drafts and publish when a gate report should be recorded.
- `op=writers` reports the mode of the calling node's own setting.
- A console draft run uses the maintenance application's draft graph; the endpoint uses its published
  graph. Keep the draft equal to the published version so both run in the same mode.

## 2. Solution-layer table names

The solution layer's four tables, end to end per scene:

| Table | Role (implied by the name) |
|---|---|
| `solution.search.fact.<scene>` | `SEARCH_FACT` (new) |
| `solution.fact.feature.<scene>` | `FACT_FEATURE` |
| `solution.feature.reality.<scene>` | `FEATURE_REALITY` |
| `solution.reality.strategy.<scene>` | `DISPOSAL` (`disposal.strategy`'s new name) |

- `<scene>` is the canonical `M_` scene id; `.<part>` is still allowed for shards.
- `solution.disposal.strategy.*` and `solution.disposal.status.*` stay storable and readable as
  legacy names, so tables already stored under them keep working. Other `solution.*` names are refused.
- A solution-layer declaration may leave `role` out: the table name implies it. A written `role` must
  still match the name.
- `SEARCH_FACT` gets the generic decision-set checks only; its conclusion key is `fact_id` (one rule
  per fact code). Its columns are not fixed by the standard yet.

## Installation and rollback

- Install after v0.5.27. Open mode needs no setting: clear the maintenance node's `writers` setting
  (or write `OPEN`) and republish the maintenance application. With writer lines kept, the node stays
  in signed mode. A registry cached by the host under v0.5.26 or earlier may still be served until that
  cache entry expires.
- Rollback to v0.5.27: open mode and the two new names are gone; an empty registry then refuses writes
  to the five, and `OPEN` is a malformed registry. The new `solution.search.fact.*` and
  `solution.reality.strategy.*` names and `SEARCH_FACT` role are rejected by 0.5.27. Stored bytes
  remaining in storage do not make those tables readable or executable after downgrade. Before
  downgrading, inventory needed tables, declarations and references, migrate them through an
  authorized compatible representation, then verify reads and evaluations on the target version.
  Do not silently rename tables, overwrite stored data or assume a complete rollback is automatic.

  be omitted (or null) and must match when written; open mode for empty, missing, comment-only or
  `OPEN`; deleting every writer line turns signed mode into open mode (regression for the known limit); every write op on the five (old and standard names) from another app is refused with no
  storage change; requests carrying a writer are refused in open mode; open-mode direct saves get the
  unknown-key and outside-five checks; drafts need no writer; signed mode unchanged; `OPEN` mixed with
