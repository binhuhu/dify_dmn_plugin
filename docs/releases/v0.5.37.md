# v0.5.37 (candidate, not published): self-service executor, writers that only draft, scene bundle, light catalog

Rebased for review on public v0.5.36 (`5aa8abae83b1691934ba1caa47a04fd879556e66`). Target-host installation identity has not been verified. No storage key or table format of an existing table changes; no table migration is required. In open mode (the default; the target-host setting has not been verified) every pre-existing operation answers as v0.5.36 does, except the two additions noted under "Open-mode differences".

## 1. User self-service as a resource executor

The three-tier resource routing (`role: RESOURCE`) takes a third executor.

- `tier1.executor` / `tier2.executor`: `HUMAN` / `AI` / `SELF_SERVICE`. A rule is self-service on both tiers or on neither.
- `tier3.pick` adds `SELF_ENTRY`, with the app behind the self-service entry in `entry_app_id` (an AgentHub app id). `SELF_ENTRY` is the only pick of a `SELF_SERVICE` rule, and no other executor takes it.
- `tier1.pool`'s `SELF` still means own staff; the executor is spelled `SELF_SERVICE` so the two never read alike.

A table without self-service is checked exactly as before.

## 2. Writers

- A fifth writer kind, `AGENT`: a registered writer that only drafts. It may `draft_save`, `bundle_save` and discard a draft. `publish`, `undo`, carrying out a `prune`, `bundle_publish`, `bundle_rollback` and a direct `save` of a scene table answer 403 `STORED_TABLE_AGENT_DRAFT_ONLY`. Its signed save of any other table outside the five is taken as any writer's (those tables have no draft to stop at).
- In signed mode a `save` of `target.scene.topic` or `triage.issue.acceptance` (the two tables a scene needs that are not among the five) needs a writer's signature and counts only from the pinned maintenance app. In open mode they are saved as before.
- Every successful `save` and `publish` answers with `ledger_row` (its `writer` is always `{id, kind}` or null; `kind` is null for a direct save, whose record keeps the id only): table, schema, version, save id, parent, content digest, save time, gate report digest, writer, `writer_verified`, draft writer, release line, and the unverified host user and `via`.
- `op=ledger` (read, only from the pinned maintenance app): one such row per stored version the history lists, newest first. A version stored with no record of who says so (`writer: null`, `recorded: false`).

The default stays open mode: an empty writers setting behaves as v0.5.36 does. Switching is still one edit of the maintenance app's writers setting and republishing that app; nothing in this candidate switches it.

Behaviour that changes on the switch, compared with v0.5.36 in signed mode: unsigned direct saves of the two scene tables above are refused (401 `STORED_TABLE_WRITER_REQUIRED`). Whoever saves them must sign, as for the five.

## 3. Scene bundle

One request carries one scene's rows in six tables: `target.scene.topic`, `target.scene.entity`, `triage.supplement.requirements`, `triage.scene.acceptance`, `triage.issue.acceptance`, `triage.dispatch.route`. See `plugin/dmn_client/scene_bundle.py` for the request, and `plugin/tools/scene_bundle.yaml` for the tool.

- `check` composes the six documents on the stored heads, runs the bundle gate and every table's whole save on a dry-run overlay. Nothing is written.
- `save` does the same and stores one draft key for the scene. The six tables are untouched.
- `publish` composes again on the heads the draft was made on (any head moved: 409), dry-runs again, then saves the tables one by one, the scene-topic row last. A failure after some tables were written saves their previous content back as a new version (`ROLLED_BACK`); if that fails too the record says `PARTIAL` and names each table. After a complete publish the new scene is probed once against the stored tables and the result is written into the publish record.
- `rollback` saves the previous content back to each table a publish wrote whose head is still that save.

A part only touches its own scene: a decision rule must test `scene_id = <this scene>` in every condition combination.

The operations are also `bundle_check`, `bundle`, `bundle_save`, `bundle_discard`, `bundle_publish`, `bundle_rollback` of `route_table_store` (the `table` parameter carries the scene id), so the maintenance app needs no new node.

A bundle does not remove rows. An `UPDATE` that leaves out a part (null) while the scene has rows in that table is refused by the gate (`B8-rows-left`): send the existing rows to keep them, or save that table on its own to remove them.

`like` copies another scene's rule: it refuses a scene that has several rules in the table, and on a rule of several condition combinations it adds this scene's combinations with the other conditions kept.

Only a scene's last publish can be rolled back (`SCENE_BUNDLE_NOT_LAST` 409 otherwise). Rolling it back does not make an earlier publish eligible: this is a single-last-publication undo, not a traversable rollback history. An `UPDATE` may replace the content of a template only this scene's rules use.

What a publish wrote is told by the heads: the publish record holds each table's save id before the first write, and `status`, the publish's own undo and `rollback` judge every table by whether its head carries that id. A head whose content is already the content before the publish counts as back.

## 4. Light catalog (`op=catalog`)

A read-only operation of `route_table_store`, for any app. It is computed from the stored heads at read time; nothing is stored.

- Request: no `table` or `version`; `body_json` optional, `{"parts": [...]}` with `intent_types` (the default) and/or `scenes`.
- Answer: `schema` (`dmn-json.catalog/v1`), `sources`, `parts`, `part_sha256`, `catalog_version`, `complete`.
- **What each digest covers:**
  - `sources[i].content_sha256` is that table's own content digest, the same value `op=table` answers in `doc.content_sha256`. For the scene-topic table it covers `{intent_types, rows}`. Equal to the head's digest means the whole table is the same.
  - `part_sha256.<part>` covers only that part as returned (`intent_types`: the issue types and the intent map; `scenes`: the returned list, without topics). It stays the same across table versions that do not change the part.
  - `catalog_version` is a digest of the sources, `[table, version, content_sha256]` for each source table. Two reads with the same value read the same versions of the same tables. It is not a digest of the parts.
- A source table never stored: 200, `version: 0`, `content_sha256: null`, the parts `null`, `complete: false`. A source that cannot be read or is not the table it should be: an error (`CATALOG_SOURCE_INVALID` 409, or a storage failure), never half an answer. A bad request: `CATALOG_PARTS_INVALID` 400.
- The default tier is the intent types only (about 1 KB on the current table). `scenes` is the scene id (M_ spelling), name, domain and status of each row.

The operation name, the schema name, the part names and the keys are proposals.

## 5. One trial name for a scene-topic table

`trial.scene.topic` may hold a scene-topic table, next to `target.scene.topic`. No workflow reads it, the scene bundle never writes it, and `op=catalog` reads the standard name. It exists so a trial scene can be stored without touching the table in use. It is outside the signed scene-table set: the AGENT draft-only restriction does not cover direct saves to this trial table. Proposal.

## Open-mode differences from v0.5.36

- Every successful `save` and `publish` answer carries an additional `ledger_row`.
- New operations (`ledger`, `catalog`, `bundle*`) and the new tool `scene_bundle`; a resource-routing table may use the new executor and pick; a scene-topic table may be saved under the trial name.

The supplied candidate reports a 143-call differential run and a fix for a non-string `table` value returning 503 rather than 400. That report has not been independently reproduced for this rebased revision; additional differences remain possible until the regression suite runs.

## Signed-mode differences from v0.5.36

Unsigned direct saves of `target.scene.topic` and `triage.issue.acceptance` are refused (401 `STORED_TABLE_WRITER_REQUIRED`); a writer of kind `AGENT` exists and only drafts. Whoever saves those two tables in signed mode must sign, as for the five.

## Safety boundary

- A bundle is not a transaction. Between the first and the last table's write a reader can see some tables with the scene's rows and others without. A crash between writes leaves a `PUBLISHING` record; `status` shows which heads are this publish's, and `rollback` takes them back.
- A failed table can be left with a version key above its head (the engine's existing behaviour for the five delivery-chain tables when the head write fails). The bundle then answers `PARTIAL` with `failure.stranded` naming the table and version; the key is preserved. The bounded v0.5.36 skip policy may allow a later save after the age threshold and within its skip limit; this is not automatic cleanup and does not provide atomic coordination.
- No cross-process lock, as before. A save of one of the six by someone else during a publish is detected (stale head, read-back), not prevented.
- **Signed mode is a setting of each node.** A `scene_bundle` node (or a second `route_table_store` node) whose own writers setting is empty runs in open mode even when another node of the same app carries a registry. To keep "an agent only drafts" enforced, the maintenance app should reach the bundle through the one `route_table_store` node (`bundle_*` operations) and not add a `scene_bundle` node, or repeat the registry on it.
- A scene left with rows in some tables but no row in the scene-topic table (a publish taken back only in part, or someone's later save keeping a table from being restored) cannot be repaired by a bundle: `CREATE` and `UPDATE` are both refused. Save the affected table on its own.
- A way back answered as failed may have been stored: the entry says `restored: false` for that attempt, and the next `rollback` recognises the table as already back.
- The probe reads the stored tables. It does not run the locate or triage workflows.
- In open mode the plugin cannot tell an agent from a person. "An agent only drafts" is enforced in signed mode only.
- The route editor endpoint does not forward bundle or catalog operations.
- Known limit: two resource-routing rules that differ only in `entry_app_id` (or, as before, only in `agent_app_id`) are refused as one conclusion.

## Upgrade and rollback

Upgrade from v0.5.36 needs no table processing. Verify the installed version and the plugin identifier, then read back table versions.

Rollback to v0.5.36 is conditional, not universally lossless. Against public v0.5.36 (`5aa8abae83b1691934ba1caa47a04fd879556e66`), read-back of a `SELF_SERVICE` resource table and `trial.scene.topic` succeeds, but re-saving them is rejected (400 `TABLE_DECLARATION_INVALID` and `STORED_TABLE_NAME`, respectively). Importantly, the old evaluator still succeeds for the self-service rule and returns `SELF_ENTRY` / `entry_app_id`; it does not reliably reject unsupported semantics. Before downgrade, restore a normal resource-table version without self-service rules and verify downstream behaviour; do not rely on the trial table. The tested ordinary resource version can be saved and evaluated by v0.5.36. Bundle drafts and publish records are extra keys v0.5.36 ignores. These are isolated synthetic-storage probes, not target-host validation.
