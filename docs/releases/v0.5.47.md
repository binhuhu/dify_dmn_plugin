## 一、改了什么

### 1. 场景号守门（`2f17c42`）

前面是字母数字的不算（`XHY_P_` 不拒）。排在文档本身的全部拒存之后。这是文法修好之前的窄守门：重铸那一窗把文法修好后撤掉（撤的条件另由协调定）。

### 2. 安全转接场景不许有方案行（`5865f94`）

- 路由表存表：读场景与话题表头版的 `SAFETY_TRANSFER` 场景，这次存的方案行（`SOLUTION_APP`）落在上面就拒，路径指到那一行（旧写法场景号认成同一场景）。
- 场景与话题表（现网那张，试验表不核）存表：改成 `SAFETY_TRANSFER` 的场景在任一在用路由表里还有方案行就拒，路径指到那一行的 `status`；先删方案行
  （带 `retire_solutions`）再改状态。
- 只核方案行：旧形转接、资源行归 0.5.46 的终形闸（只留只删）。现网 42 个安全场景 378 行旧形行、方案行 0 行（11-25 02:48 只读核），这一核对现网无影响。
  候选 D 存后把「带方案行就拒」收紧成「有行就拒」（协调定，进第二次切发布单，不在这一版）。

### 3. 插件拒码登记（`181c82d`；出图闸部分 `b5b33f0`）

### 4. 一次求值多个输入 `evaluate_stored_table_batch`（`37ae4cc`、`4b0288f`）

参数和 `evaluate_stored_table` 一样：`table`、`format`、`version`、`content_sha256` 原样照抄（说明逐字相同），只把 `inputs_json`
换成 `inputs_list_json`：一个列表（或列表的 JSON 字符串），每一项就是单个工具的 `inputs_json` 对这种格式收的那一份（空项当 `{}`）。

- **逐字相同**：`item_result_jsons` 第 i 项，与单个工具对同一存储版本、用同样的 `table` / `format` / `version` / `content_sha256`
  和第 i 项输入给的 `result_json` 逐字相同。两个工具跑的是同一个函数（`stored_tables.evaluate_stored_many`；单个工具就是只有一项的列表），
  不是第二份求值实现。
- **一次一读、同一版**：这一次只读一次表，所有项用同一版；钉了版本或摘要就都用钉的那一版。表本身的拒（钉的版本不在、表不在、格式对不上）
  每一项都会遇到，所以每一项的回执都带单个工具会回的那个码，列表的 `status` 仍是 `SUCCEEDED`。
- **单项失败不连坐**：一项的输入写坏、没中、判不了，只这一项的回执带它自己的 `status`，别的项照常。
- **次序与重复**：按给的次序求、按次序回；重复的项照样再求一次，不去重、不合并。
- **`status` 只说这张列表**：`SUCCEEDED`（每一项都有了自己的回执）、`NOT_REQUESTED`（列表空或没填）、`FAILED`（列表本身被拒：
  不是列表、不是合法 JSON、超线）。`results` / `result_json` 是这张列表的答案（`dmn-json.stored-table-batch-result/v1`：
  `status`、`table`、`format`、`count`、每项的 `statuses`、`error`），各项回执只在 `item_result_jsons` 里，不重复带一遍。

输出：`results`（对象）、`status`、`result_json`（字符串）、`item_result_jsons`（字符串列表）。

安全线（DMN 2.0.107 §八；三个数只写在 `plugin/dmn_client/stored_batch.py` 一处）：

| 线 | 值 | 超了 |
| :-- | :-- | :-- |
| 一次几项 | 至多 256 项（比场景与话题表的场景数多，读方不用拆） | `FAILED` `STORED_TABLE_BATCH_TOO_MANY` |
| 列表本身 | 至多 1 MiB（UTF-8） | `FAILED` `STORED_TABLE_BATCH_TOO_LARGE` |
| 各项回执合计 | 至多 4 MiB（UTF-8，在一条插件消息 5 MiB 以内） | `FAILED` `STORED_TABLE_BATCH_TOO_LARGE` |

11-26 修的三处（11-25 对 `37ae4cc` 的评审找出，三条用例在 `37ae4cc` 上红、在 `4b0288f` 上绿）：

1. 列表文字嵌套过深（远在 1 MiB 以内）时 JSON 读法抛 `RecursionError`，旧码只收 `ValueError`，整个工具崩；现在回 `FAILED` `INPUT_INVALID`，同单个工具。
2. 某一项带写不成 UTF-8 的字（孤立代理）时，按列表给整张拒 `INPUT_INVALID`、按 JSON 文字给却逐项求：两种给法答案不同。现在量字节不拒
   （孤立代理按它要占的 3 字节计），那一项的回执就是单个工具对它的回执，两种给法逐字相同。
3. 4 MiB 回执线原来先把全部项求完、复制、写成文字再核；现在每求完一项就写下回执、累计，跨线即停（码、路径、`status` 不变，`message` 写「求值到第 n 项」）。

读方怎么用：读方要一次查多个号（例如一轮里几个场景号各查一行）时用这个工具，不在流程图里整表读出来再用代码取行（那是第二份求值实现），
也不用平台的迭代节点一项一项调单个工具。下游按 `item_result_jsons` 第 i 项读，和原来读单个工具的 `result_json` 一样解析。
现网还没有图调它：定位候选图把四个迭代换成一次批量调用，要等这一版装上、81 读回把 `item_result_jsons` 按项拆开（设计稿 §六），都还没排。
