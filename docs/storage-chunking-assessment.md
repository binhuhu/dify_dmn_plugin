## 一、现在怎么存

- 一张表一个存储值：头版 `route-table:<表名>`，各版 `route-table:<表名>:v<n>`（最近 50 版可按摘要找回），首存记录 `…:first`，
  0.5.42 的随表用例 `…:c`。值是表文档的 UTF-8 JSON。
- Dify 插件存储经插件消息来回，一个值走一条消息，十六进制编码（体积翻倍）；一条消息默认 ≤ 5 MiB（`PLUGIN_STDIO_MAX_BUFFER_SIZE`）。
  0.5.41 把所有表的内容线定在 1 MiB（规范 JSON、不含声明），声明 256 KiB：满线的表编码后约 2.6 MiB，在 5 MiB 内（`route_store.py` 注释）。
- 现在最大的真表：费用 v2 现实表（n37 甲）757,473 字节，线的 72%。第二大是 v1 费用第一片 88,843 字节。交付链按场景写的表实数还没核
  （81 侧给数）。

## 二、分块怎么做（若做）

1. **键**：一版拆成几块 `route-table:<表名>:v<n>:part<k>`（每块 ≤ 1 MiB 原文）；版次键与头版键只存块清单
   `{schema: dmn-json.stored-chunks/v1, version, content_sha256, save_id, parts: [{bytes, sha256}], total_bytes}`。
2. **写**：照现在「先历史、后头版」的次序，先写块、再写版次键清单、最后写头版清单；断在中间只留下没人指着的块（清理照孤儿版次的做法收）。
3. **读**：读到清单就按清单逐块读、逐块核 sha256 与总长，拼回整份再解析；任何一块对不上 → `ROUTE_TABLE_CORRUPT`（不放行半份表）。
4. **摘要与回答**：内容摘要照旧按拼回的整份文档算——**分块不改摘要、不改任何读法的回答**；按摘要找版次只读清单（清单带 `content_sha256`），
   比现在逐版读整份还快。
5. **清理与用量**：`op=usage` 把块算进各版占用；`op=prune` 删版次时连块一起删；撤销首存删键时同。
6. **只给过线的表用**：原文 ≤ 1 MiB 的表照旧一个值（今天所有表），所以装上分块的那一版对现有表的读写逐字节不变。

## 三、代价与风险

| 项 | 说法 |
|---|---|
| 读多几次存储调用 | 一张 k 块的表每读一次多 k 次反向调用。求值每次读头版：AgentHub 上一次反向调用的耗时没量过，3 块可能就吃掉 300 毫秒目标的一大截 |
| 不只是存储一处卡线 | **存表与读表的回答本身也在一条消息里**：`op=table`、`op=save` 的结果带整份文档，工具还一份三发（json、`result_json`、`result`）。表过 2 MiB 左右，回答那一条就过 5 MiB——分块解决不了，要同时把这两个 op 的回答改成不带全文（或分页），这会改现网回答 |
| 求值变慢 | 每次读都整份校验：今天 1 MiB 的表校验约 0.2 秒（0.5.41 实测）；线放到 2–4 MiB，求值必过 300 毫秒，要先做「按内容摘要记住校验过的表」 |
| 回退 | 分块存过的表，回退到不认清单的版本（0.5.42 及以前）时：清单的 `schema` 不是任何表格式，旧代码回 `STORED_TABLE_FORMAT_MISMATCH` / 格式不认识——**拒得干净、不会读错**，但那张表在回退期间读不了。只给过线的表分块，这个风险只落在那几张大表上 |
| 不是事务 | Dify 存储没有比较后写入；块与清单是几次写，并发存同一张表的老问题不变（仍按单人串行维护） |
| 测试面 | 要补：块的读写、断在每一步、块被改一字节、清理与用量、按摘要找版次、回退旧版的拒绝；全链路无影响对跑闸要证明 ≤ 1 MiB 的表逐字节不变 |

## 四、建议

- **现在不做**。1 MiB 线是 0.5.41 刚定的（Brian「我们就把最大的限制变成一兆吧」），最大的真表在线的 72%；分块本身不难，难的是它牵出
  回答体积与求值耗时两件事，三件要一起做、一起评审，才真能放过 1 MiB。
- **触发条件**（建议写进标准 §八 体积）：任一张真表的内容过 800 KiB（线的 80%），或方案组要存一张预计过 1 MiB 的表——到那时再立项，
  三件一起做：存储分块、`op=table` / `op=save` 回答不带全文、按摘要记住校验结果。
- 在那之前，过线的表照现在的拒存文案拒（`STORED_TABLE_TOO_LARGE`，写明字节数与线），由方案组拆细（比如 n37 拆细、改算出的量）。

## 五、要 Brian 定的

1. 1 MiB 是不是继续当硬线（建议是）；
2. 触发条件取 800 KiB 还是别的数；
3. 真到要放线时，接不接受 `op=table` / `op=save` 回答改形状（不带全文）这一处现网回答的改动。

## 六、第二轮评审的更正（0.5.42，对本稿）

- **「回退拒得干净、不会读错」不实**（必须改）：在 0.5.41 上把费用 v2 现实表的头版与版次键换成块清单，求值回 `STORED_TABLE_FORMAT_MISMATCH`（干净），
  但 `op=table` 把清单当表文档交出去；上游事实 → 特征表删掉现实表在读的号照存（对照组回 `STORED_TABLE_ID_IN_USE`），两头核放行；下游重存回误导的
  `STORED_TABLE_UPSTREAM_MISSING`；这张表自己重存回 `STORED_TABLE_SCHEMA_CHANGED` 卡死。受影响的不止那几张大表。真要做时：存过分块的表就不能回退
  0.5.41（第一次存过线的表排在确认不回退之后），或先发一版只认清单的（读时拒 503、两头核把它算作读方、允许在它上面重存），再发一版写清单的。
- **「表过 2 MiB 左右回答那一条就过 5 MiB」偏紧**：用 SDK 的消息类实测，json 那一条是文档的 0.90 倍，`result_json` 那一条 1.21 倍，回答约在文档
  4.1 MiB 时才过线；存储写入（十六进制翻倍）在约 2.4 MiB 先碰线。2.4–4 MiB 之间单做分块就够用。AgentHub 实际的线没核。
- **第一节的数**：11-18 快照（`tests/fixtures/save_gate/tables`）已有交付链实数——场景与话题表内容 179,724 字节，路由表 154,982 字节；757,473 字节那张
  是 0.5.41 的夹具，现网没存过。现网最大的真表要以 81 读回为准。
