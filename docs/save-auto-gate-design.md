## 〇、一句话

在插件存表路径上、现有全部拒存之后，加一段「存前自动闸」：先拿这张表随存的用例对新版逐条跑（走读方同一条求值路径），再核它引用的场景号和事实有没有登记，路由表再读被指方案应用现网的开始变量核登记。**只拒变坏**：头版本来就有的缺口只报黄；这次存表新引入的问题才拒，拒时逐条说清哪条用例、期望什么、这一版得到什么、怎么改。表的存法、内容摘要、全部读法与 0.5.40 逐字节相同。

## 三、设计

### 3.1 放在哪、什么顺序

```
_save:  校验 → 现有跨表核 → 版本核 → 0.5.23 可调闸 → 【存前自动闸】 → 调用方的 gate → 写
                                                   │
                                                   ├─ ① 随表用例（本地、确定）
                                                   ├─ ② 跨表核：场景号在目录里；受理事实有供给方（本地读别的表头版）
                                                   └─ ③ 路由表：被指方案应用的现网开始变量（读平台，最后做）
```

- 排在所有现有拒存之后：现有每一种拒存的码、文案、路径、先后不变（0.5.23 的回归口径）。
- 三项从便宜到贵：前一项拒了就不再往下读平台。
- 一样跑在：直接存（开放与签名两种模式）、存草稿（`draft_save`，不落盘副本上跑同样的拒法）、发布（再跑一遍）、建场景整包的每一张（`scene_bundle` 经 `gate` 钩子）。
- 不跑：标准名首存（原样拷头版，不可能变坏，同 0.5.23）；撤销首存时改引用的那一次存（`take_back=False`）。
- 拒：一次存表只回一个错（现有错误信封 `{code, message, path}`），文案列出前 5 条，全部明细另放在本次的闸记录里（3.6）。过：照存，黄项进回执的 `warnings`。
- 不写死业务：哪些用例、哪些场景号、哪些事实，全部来自存储里的表与用例；插件只带「怎么核」，不带「核什么名单」。

### 3.2 随表用例

**存在哪**：不进表内容。每张表一份用例集，存在插件存储自己的一族键里（`route-table:<存名>:c` 头、`…:c:<k>` 各版、`…:c:s:<save_id>` 随某次存表带来的那一份）。表的文档、内容摘要、版次、存表号与不带用例时**逐字节相同**；读表的任何 op、任何求值都不读这族键。用例集带自己的摘要与「对着哪一版表核过」（`checked_against: {version, save_id, content_sha256}`）。

**一条用例长什么样**：一次真实读方调用 + 期望的答案片段。

```json
{
  "schema": "dmn-json.table-cases/v1",
  "table": "triage.dispatch.route",
  "readers": { "route": { "tool": "evaluate_decision", "params": "<分诊读路由表那份定义包，整套一份>" } },
  "cases": [
    { "id": "ROUTE.COUPON.COMPLAINT.STAGE_1",
      "why": "券投诉第一阶段走在用的券方案（第 9、16 版事故）",
      "reader": "route",
      "inputs": { "scene_id": "M_P_02_04_01", "issue_type": "COMPLAINT", "phase": "STAGE_1" },
      "expect": { "target": { "kind": "SOLUTION_APP", "app_id": "ee1aebd3-…" } } }
  ]
}
```

- `reader` 只能是现网读方真用的两种调用：`evaluate_stored_table`（格式 + 入参）或 `evaluate_decision`（定义包 + 入参，路由表就是这样被分诊、交付编排读的）。定义包按用例集写一份，各条只带入参。
- `expect` 是答案的**子集比**：只比写出来的键；永远不比来源段里的版次、摘要、存表号（每次存都变）。
- 用例集上限：≤ 500 条、≤ 256 KiB（与表内容分开算，不动现有 `MAX_BODY` / `MAX_REQUEST`）。

**怎么跑**：在内存里叠一层存储——这张表读到的是这次要存的候选，别的表读存储里的现头版——然后照读方原路调同一个工具类，拿答案比期望。路由表只编译一次。所以用例跑出来的，就是这一版存进去之后读方会读到的。

**有意改行为**：存表请求可以带 `cases`（整份新用例集）。带了就用新用例集核新版，并在回执里逐条列出用例的增、删、期望改动（「差异逐条说明」）；没带就用现用例集核。这是存表的人自己在同一次存里写明「我就是要它变成这样」，**不找第二个人、不加审批键**。为了顺手，加一个只读的 `op=cases_check`：给一份候选表，不存，回哪几条用例过不了、各自得到什么，并附一份「照新结果改好期望」的整份用例集，照抄进 `cases` 就能存。

**用例集自己的读写**：`op=cases`（只读，读头或某一版）、`op=cases_save`（只换用例集，不动表；新用例集必须对**现头版**全过，过不了拒；写入限制与它的表相同——场景与话题表的用例集同样只收受控入口签名的写入）。

**回滚**：候选内容摘要等于这张表以前某一版时，用那一版当时核过的用例集（随存把它恢复成头），不拿新用例集拦回滚；那一版是装闸以前的，用例不跑、报黄「回滚到装闸前的版次，用例没跑」。0.5.23 可调闸对回滚照旧。

**没有用例集**：报黄「这张表还没有随表用例」，不拦。7 张交付表在装机时首存用例集（见八、十一）；之后新登记的表同样报黄，81 每日读数里数「没有用例的在用表」。

**顺序与断电**：带 `cases` 的存表，先写 `…:c:s:<save_id>`，再写表，最后挪用例集的头。下一次存表先找「挂在当前表头存表号上的那份」，没有再用用例集头——中途断掉也不会拿旧用例拦住已经生效的新表。

### 3.3 跨表核

**通则**：比「这次存的」与「这张表现头版」，**新引入的**问题拒，头版本来就有的报黄并写明个数；被核的登记处（目录、能力表、补充信息项字典）没存过，一律报黄「登记处没有，没法核」。比较一律按场景号的规范写法（`M_` 与旧写法当同一个号，用插件现有的场景号文法），只改写法不算新引入。

**② a 场景号在目录里**（目录 = 场景与话题表 target.scene.topic 头版）：
- 取号按类，不按表点名：路由表的路由键与 `scenes`；补充要求表的场景键；决策表（场景关联实体、场景成立、受理条件、三级资源去向）里所有对参数 `scene_id` 的条件取值（`eq` / `in` / `when_any`，否定条件里的号也算）。
- 新引入的号不在目录 → 拒，文案点名号与位置。
- 存场景与话题表本身时反过来看：别的表还在用、这一版目录里没了的号，**只报黄**（这张表走受控入口，另有入口的回放闸与换号窗口的逐件点名，标准 §五 场景与话题一行；本闸不在这里替它拦）。
- 换号窗口的次序因此被插件自动守住：先存场景与话题表，再存另四张；反了，四张里换来的新号会被拒。

**② b 受理条件表的事实有供给方**（场景成立表同理）：
- 参数的来源只认声明里的 `source`（标准 §六）。写成 `fact:<事实号>` 的，到登记处找供给方：能力表头版（新名 `support.target.capability.catalog`）各行给出的事实号（0.5.41 起叫 `infos` 的，同样认），以及补充信息项字典（立了以后）。
- 声明了来源、登记处存在、这次新引入、找不到供给方 → 拒。
- 没写来源的参数 → 报黄「参数没写来源，供给方核不了」，**不按参数名猜**（`facts.<…>` 只是现在拼事实的写法，不是登记）。
- 今天的实际结果：受理条件表 10 个事实参数全部报黄（没有来源声明，且能力表没存过），一个不拦——这是派单要的「先只报不拦并写明」。等受理条件表补上来源声明、能力表首存（上线单第 ⑤ 步）后，同一套核自动开始拦新引入的缺口，不用再发插件。

### 3.4 路由表：核被指方案应用的现网入参

**什么时候核**：路由表 v3 存表，只核**这次变了**的方案：新有行指着的应用、试验方案、登记里状态改成在用的、`request_contract` 或 `inputs` 改了的。没变的方案不读平台（存得快，也不会因为平台一时读不到而给无关的存表报黄）。

**读什么**：`session.app.fetch_app(<app_id>)`，读应用**已发布**版本的开始表单（变量名、类型、必填、说明）。只读，不运行方案、不留运行记录。每个应用最多 3 秒，一次存表合计最多 8 秒；超时、报错、平台不认这个调用，一律当「读不到」。

**核三件**：

| 核什么 | 对不上 | 读不到 |
|---|---|---|
| 应用在、是工作流、有已发布版本 | （读不到同论） | 报黄，不拦 |
| 开始变量的名字集合 = 登记的 `inputs`；都是文本类 | **拒**（例：登记 `call_id, request_json`，现网开始节点是 `worksheetId, case_json, …`） | 报黄 |
| 登记的 `request_contract` 在应用声明「收哪几版合同」里 | **拒**（第 16、17 版那种：登记写 v5，应用只收 v4 / v4.3） | 应用没声明 → 报黄「方案应用没写收哪版合同，只核了开始变量」 |

**「收哪几版合同」从哪读**：开始表单里看不到代码节点，所以需要方案应用在开始节点 `request_json` 变量的说明里写一行机读声明，例如 `收合同：场景方案调用/v5`（可列几版）。插件只认这一行的写法，不认标签与别处文字。这条是方案应用标准（solution-app.v1 B2）的增补，方案应用归 ESE，要 Brian 定交不交（十一第 2 句）。**没声明之前这一格永远是黄**，第 16 版那类「登记的合同不实」只能靠两样兜：本闸的用例（换去向没改用例就拒），和 81 存后自动回归（评审 3-7）读已发布图核合同——本闸把每个「合同没核」的应用写进闸记录，交 3-7 那条线照单核。

`fetch_app` 由工具与编辑端点注入（`StorageTables` 不碰会话）；单测注入假的。AgentHub 是否实现了这个反向调用，装机前不能在现网实测（装插件要 Brian 放行），所以设计上「读不到 = 黄」是唯一失败去向，最坏情况就是这一项一直黄，不会误拒。
